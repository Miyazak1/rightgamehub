## 1. 文档目的

本文将“墨鱼变更雷达”从单网址变化提醒工具，升级为一个在服务端持续运行的长期新闻观察系统。系统围绕用户定义的一个关注对象，主动监控已知新闻来源、发现候选报道、积累可追溯证据、提取可比较的原子事实、归并现实事件、维护会随时间修订的观察结论，并向不同 Agent 提供统一的历史查询、筛选、统计与比较能力。

本文是产品、数据、服务边界和实施门禁的共同依据，不表示下述能力已经上线。后续实现不得仅凭页面出现按钮就宣称阶段完成；每个阶段必须满足本文列出的数据、恢复、安全、成本和验收要求。

配套实施方案：[《新闻情报流水线升级设计》](./change-radar-news-intelligence-pipeline-upgrade.zh-CN.md)。该方案吸收 AIHOT 在采集、分层筛选、语义事件归组、后台 Worker 和离线评测方面的优点，并保持本文定义的证据、账号隔离、成本与恢复边界。

- 账号隔离的来源、证据和候选事件查询 API，以及页面上的证据档案预览；
- RSS / Atom 只读预览适配器：复用 SSRF 与重定向防护，限制响应体和条目数，拒绝 `DOCTYPE` / `ENTITY`；
- 候选订阅来源状态机与页面确认入口：新来源默认 `candidate`，用户可预览后确认、暂停或拒绝；同一账号复用相同 URL 时，来源身份与权威审核可复用，但每个专题必须独立确认并留下只追加状态决定。专题关系以不可逆的首次启用时间区分“从未确认”和“确认后停用”，从未确认的候选不会继承其他专题已归档的证据、质量抽样或保留策略，确认后停用则继续保留历史可追溯性；
- 已确认订阅源的有界服务端采集：每轮最多读取契约文档预算与平台硬上限中的较小值，按 feed 内容和 entry 身份幂等归档来源版本、新闻材料与最小证据摘录；报道条目本身不生成现实事件；失败来源使该轮进入 `partial`，不会让其他来源丢失；
- GitHub Release 适配器：只接受规范的公开 GitHub 仓库地址，读取仓库官方 `releases.atom`，不需要用户 Token，并复用订阅源的安全、预算和证据边界；
- `research_run_actions` 外部调用账本：请求发送前预约，记录请求哈希、attempt、预计/实际用量、回执与错误；对计费 Search / Fetch 同时冻结币种、每次成功请求的 USD 微单位价格、计费请求数与本次估算成本，历史回执不会因以后调价而重算；worker 在结算前中断时标记 `uncertain` 并停止自动重发；
- 专题运行体检第一增量：账号隔离地汇总最近 7—365 天的运行状态、候选产出轮次、外部行动成功/失败/不确定回执、供应商调用与结算时价格快照成本，并按专题时区显示有活动的日期；“有产出”只表示出现候选变化或候选来源，绝不等同于形成已验收结论；
- DeepSeek Search 新闻发现适配器：默认关闭、仅使用服务端平台密钥、每轮硬上限 2 次查询、每次最多 5 条且固定 `need_content=false`；每条查询由“当前关注对象名称 + 一个观察问题”确定性组成，防止“过去 30 天发生了什么”一类通用问题脱离对象；搜索结果只形成候选来源和不可变发现记录，不进入证据表；
- 候选分层价值评估第一增量：搜索候选归档时先执行确定性 `tier0-prefilter-v1`，保存输入哈希、理由代码和六个维度分数；可选 Tier 1 默认关闭，每轮只选择最多 6 条 Tier 0 相关或待复核候选，向 DeepSeek Chat 发送专题、标题、摘要、发布者、发布时间和 Tier 0 元数据，不发送候选网址或正文。模型结果以 `model/value` 追加保存，并通过独立 `candidate-assess` 行动进入同一预算、熔断、回执与价格快照账本；它只判断后续研究价值，不判断真假、不激活来源、不接纳证据。Tier 2 复评尚未实现；
- 候选模型影子评测第一增量：只读接口从追加式评估账本中选择一个明确的 Tier 1 评估版本，与最新人工复核逐条对齐，计算覆盖率、一致率、相关类精确率/召回率、弃权与混淆矩阵，并按标题/摘要启发式语言和发布来源切片；少于 50 条人工正负标签时不得判定可试运行，任何门禁结果都不自动授予事实接纳、来源启用或自动化权限；
- 候选固定评测集第三增量：既可把专题已有人工正负标签确定性冻结为互斥的开发集或保留集，也可导入 1—500 行外部 JSONL 审计样本。冻结数据仅包含标题、短摘要、来源元数据、人工标签引用或溯源说明、引用 URL 和校验哈希，不保存新闻正文。评测集、样本分区、逐条离线预测和每次评测快照在数据库中不可修改；站内候选和外部语义样本都不能跨两个分区。导入后会审计样本量、标签、语言与来源结构，但报告固定声明 `representative=false`；结构覆盖达标不等于统计代表性。外部样本现可运行确定性的 `tier0-prefilter-v1`，逐条冻结预测、理由、维度分数和输入哈希，且不联网、不产生供应商费用；站内模型评测仍只读取已通过调用账本产生的判断。外部样本的 Tier 1 模型专用预算账本与运行器、独立抽样审核和代表性验收仍未完成；
- DeepSeek Fetch 已确认网页读取适配器：默认关闭、仅使用服务端平台密钥，只替代已进入本轮冻结准入清单的普通网页读取；每个网页一次运行只选择 Direct HTTP 或 DeepSeek Fetch 之一，不做隐藏回退或双重计费；发送前再次执行公开 URL / DNS 安全校验，响应限制 1 MiB，归一化 Markdown 限制 500 KiB，并把供应商、协议、正文哈希和计费用量写入不可变调用回执与来源版本；
- 账号隔离的候选发现评审接口与页面：显示命中的长期问题、搜索排名、标题、短摘要、供应商相关度和权威分，并明确标识这些字段只是线索；用户可直接确认或拒绝候选；
- 普通网页候选可由用户直接添加，用于新闻正文、机构新闻稿和与关注对象直接相关的公开说明页；添加时只执行公开 URL 安全校验，不读取正文，页面要求用户先核对原站再确认。只有确认后的网页才会在后续运行中按冻结来源清单和文档预算读取并归档；
- 专题级来源状态与决定账本：同一账号的规范来源可以被多个专题复用，但每个专题都必须独立确认，专题 A 的确认、暂停或拒绝不会替专题 B 授权。确认追踪、暂停、恢复和拒绝时，在同一数据库事务中先锁定专题—来源关系、追加保存前后状态、操作者、理由与时间，再改变当前状态；重复提交同一状态不伪造新决定。审核记录禁止更新和删除，页面可按来源展开本专题历史，跨账号和跨专题决定不会混入；这份账本只证明谁何时做了状态决定，不证明来源内容真实或彼此独立；
- 搜索候选确认后的普通网页观察：首次及后续受控读取以实际正文哈希建立来源版本，同时只保存有界证据摘录和新闻材料元数据；新闻报道与报道更新都不直接生成现实事件。搜索标题和摘要仍只用于发现与人工确认，不能直接进入证据；内网地址、无效日期及不安全结果在入库前拒绝；
- 每轮出现新证据时自动创建一个只绑定该轮证据的系统分析缺口并排队 Researcher。Worker 只能从冻结证据中返回原子 `fact`、可比较 `metric` 或分析性 `claim`；新闻发布时间与事实发生时间严格分开，缺失发生时间保持 `null`；同一结构化事实以“主体 + 维度 + 谓词 + 值 + 单位 + 发生时间 + 适用范围”确定性归并，多篇报道可累积支持同一事实，而不会因为模型使用不同 findingId 重复建档；
- 已验收事实时间线第一增量：只读取当前修订且已经人工验收的 `fact`，按“主体 + 维度键 + 谓词键 + 值类型 + 单位 + 完整适用范围”形成稳定序列；支持主体、维度、谓词、事件发生时间和单个范围字段筛选。数值事实仅以已知发生时间的最早/最新观察计算绝对与相对变化，文本事实保留按发生时间排序的版本序列；发生时间未知的事实继续显示但排除在变化计算之外，新闻发布时间不替代事实发生时间，缺失不补零，时间先后不解释为因果；
- 搜索、订阅、GitHub Release 与普通网页共享调用账本；订阅、GitHub Release 与普通网页共同遵守契约文档预算和每轮 5 文档读取硬上限，搜索另受每轮 2 次查询硬上限；无密钥时搜索明确降级，不影响已知来源观察；
- R3 协作边界第一增量：契约问题自动转为知识缺口，支持手动补充缺口；兼容 worker 可领取带租约的冻结任务，任务显式包含本次问题、契约版本、已知来源版本和最多 100 条平台证据；
- 深度研究服务默认关闭，只有配置 32 字节以上独立 worker secret 后才注册内部领取/回传接口；已加入一个独立、默认不启动的兼容 Worker 技术预览，它只分析任务冻结证据、以证据 ID 回传候选并由宿主恢复哈希，不自行搜索或读取网页；模型供应商密钥只进入 Worker 容器，不进入 API、任务协议或前端；每个任务在排队事务中预约一次调用及部署方配置的保守成本上限，Worker 必须先通过发送时的 PostgreSQL 共享熔断检查并把调用原子标记为 `sent`，随后才能连接供应商；
- Researcher Worker 运行状态第一增量：每个实例在领取任务、续租和结算时把供应商、模型、最近心跳及当前 `polling / leased` 状态写入 PostgreSQL；能力接口只返回当前供应商/模型的聚合最近心跳，按数据库时间区分“在线 / 心跳过期 / 尚未出现 / 未配置”，不暴露 worker 标识。页面不再把“配置了 secret”冒充“后台节点正在运行”；离线或未出现时仍可保守排队，但明确说明实例恢复前不会执行，在线也不承诺完成时间；
- Researcher Worker 容器健康探针增量：生产 Compose 为 Worker 固定一个部署内唯一实例 ID，并以独立 `--health` 进程通过服务密钥读取该实例的数据库心跳；探针同时核对 Worker 配置的供应商和模型与 API 预约配置一致，最近心跳超过 3 个 Worker 心跳周期、实例从未报到或配置漂移均返回非健康。探针只读，不领取任务、不续租、不刷新心跳，因此不会用健康检查本身掩盖主进程卡死；Compose 的 `restart: unless-stopped` 负责进程退出后的重启，健康状态用于运维观测，不能宣称 Docker 会因 `unhealthy` 自动重启容器；
- 未被 Worker 领取的 Researcher 排队任务可由专题所有者安全取消；专题暂停或归档也会在更新专题状态的同一数据库事务中取消全部未领取任务。两条路径都会保留取消审计记录、把未发送预约结算为 `skipped`、释放月度预算并重新开放原知识缺口；已领取、已发送或已终结任务拒绝假取消，避免把可能已经产生的供应商调用冒充为“未发送”；
- 严格结果验收：只接受冻结专题/契约/来源版本、平台已有证据哈希和契约预算内用量；未知来源、伪造摘录、重复 finding、超预算结果一律拒绝；
- 关键结论一手证据门禁：当冻结契约启用 `requirePrimaryForCritical` 时，`critical` 候选可以保留供继续调查，但没有任务冻结时已确认为 `official-primary` 的证据就不能被人工验收；结论证据会保存当时的来源等级快照，后来调级不能追溯改写旧结论资格；
- 候选结论与不可覆盖修订账本：同一稳定 finding 追加 revision，并将每一版绑定到 Researcher 任务和平台证据；旧修订保留；
- 当前修订人工验收/驳回：必须提交审核理由并携带精确 revision；新修订会重新回到 `candidate`，旧审核历史不会被覆盖；无证据结论不能验收；
- 结论审核事件为数据库级 append-only；跨账号读取、审核以及过期修订审核均被拒绝；
- 结论复核信号第一增量：契约可设置 7—3650 天的已验收结论复核周期；服务端运行会对超过周期的当前已验收修订提出 `stale` 信号，已验收结论出现新修订时提出 `revision-reopened` 信号，Researcher 明示与既有 finding 冲突时提出 `contradiction` 信号。三类信号都只进入人工复核队列，不会自动撤销、降级或覆盖原结论；处理决定与理由只追加保存，`revalidated` 会成为下一次到期计算的人工确认时间；
- 不可变运行报告第一增量：每次服务端运行以冻结契约和观察窗口形成 `research-run-report-v1` 快照；报告分别保存本轮候选事件、生成时已人工验收的结论与指标、冻结来源准入清单、停止原因和内容 SHA-256，且明确声明报告不是新的事实来源；
- 滚动周期报告第一增量：每次运行同时从既有不可变运行报告生成截至该轮的滚动 7 天与滚动 30 天 `research-period-report-v1`；汇总运行状态、调用用量、来源准入次数和去重后的候选变化，并采用最近一轮的已验收账本快照。滚动窗口不冒充自然周/月结算，报告体受数据库 1 MiB 上限保护；
- 自然周期定版与差异第一增量：每次运行按冻结契约中的 IANA 时区检查已结束的上一自然周与上一自然月；仅当周期内实际存在运行时生成一次不可变 `research-calendar-report-v1`，并与紧邻的上一份同类定版报告比较运行次数、候选变化数、调用用量、本期新观察与本期未再观察的候选事件。未再观察不被解释为撤销或失效；没有上一周期报告时明确标记不可比较；
- 指标周期归属第一增量：滚动 7 天/30 天与自然周/月报告在生成时，另从当前仍有效的已人工验收指标观察中冻结 `research-metric-period-attribution-v1`。它只把指标键、方法版本、标准单位及全部维度完全一致的序列与紧邻上期比较，保存两期观察数、首末值、数值绝对/相对变化和最新证据；本期未观察保持未知，不补零、不解释为失效，时间归属也不声称事件因果。每期最多读取 500 条观察、输出 50 个序列并显式记录截断；
- 重要变化提醒第一增量：只把达到该轮冻结契约 `minimumImportance` 的研究事件标为可提醒；提醒仍明确显示为候选变化，支持账号隔离的已读状态，不会把搜索摘要、候选来源或未验收结论包装成正式结论；
- Agent 侧栏上下文 v16 只同步当前专题中已人工验收的结论、至多 8 个指标摘要、至多 3 份不可变报告摘要、每份报告至多 12 个指标周期序列、至多 10 条未读研究提醒、至多 10 条未处理复核信号和至多 10 个有界事件簇来源诊断；报告优先选择最新本轮摘要、自然周定版和自然月定版，不足时再使用滚动摘要，并携带有界的自然周期比较。每个指标最多携带 5 条观察、原始单位/原始值、换算版本与精确比例及其公开证据引用；指标周期序列只携带同口径计数、最新值、变化和公开证据引用，强制标记 `missingIsZero=false`、`causalAttribution=false`。事件簇诊断只携带计数、有限复核原因并强制标记 `independenceVerified=false`，不把人工理由全文或来源正文同步给 Agent。复核信号只表达需要人工注意，显式排除待复核和已驳回结论，并继续把所有网页内容标记为不可信数据；
- Agent 主动指标查询第三增量：`open_change_radar` 可无参数打开雷达目录，让已登录侧栏先提供有界专题摘要；普通专题上下文会列出至多 12 个已保存派生指标的 ID、版本、输入身份和输出单位，以及至多 12 个用户保存的筛选、比较、趋势或矩阵视图配置，便于 Agent 在后续轮次精确复用用户确认过的口径，但不预先传输计算结果。页面现可分别保存普通指标序列、分组比较、单对象时间趋势和多指标矩阵视图。随后也可只携带专题 ID 和保存视图 ID，由登录侧栏验证归属后执行视图冻结的查询配置；或者携带专题 ID、指标键、方法版本、维度与时间窗口，请求一次已验收指标筛选、同口径分组比较、时间趋势，或请求 2–8 个明确指标/方法版本组成的单维度证据矩阵；也可只携带一个当前专题内已经保存的派生指标 ID，请求一次只读评估。派生查询不接受运算符、输入指标或任意表达式，必须复用平台中不可变的公式版本。公开 MCP 端点只构造路由，不读取私有专题；真正查询由已登录侧栏通过账号隔离的 `/v1/me/...` 接口执行，侧栏先验证专题和派生指标都属于当前账号，再把最多 5 个筛选序列 × 每序列 10 条观察、20 个比较分组、60 个趋势桶、50 个矩阵对象行或 50 个派生结果行及公开证据引用作为 `research-agent-analysis-v1` 回传。时间趋势额外携带由服务端确定性计算的最早/最新观察、绝对变化、相对变化与方向摘要；派生结果保留左右输入值、观察时间和证据。定向查询上下文不附带其他专题、URL 监控或收件箱事件；未知专题、未知保存视图和未知派生指标不回退，待审核指标不参与，缺失不补零，结果不声称因果；
- Agent 主动事实时间线第一增量：`open_change_radar` 现在也可携带专题 ID、规范化维度键、谓词键，以及可选主体、范围字段和发生时间窗口，请求一次账号隔离的已验收事实时间线。公开 MCP 端点仍只构造路由；登录侧栏执行私有查询并最多回传 20 个事实序列、每个序列 20 条观察及其一条公开证据引用。返回结果固定声明 `missingIsZero=false`、`unknownTimeExcludedFromChange=true`、`publicationTimeSubstituted=false`、`causalAttribution=false`；候选/驳回事实、新闻正文和其他专题不会进入该定向上下文；
- R4 指标账本第一增量：`metric` 结论必须携带稳定指标键、类型、标准单位、观察时间、维度和固定方法版本，并绑定冻结任务中的平台证据；非指标结论不能夹带指标观察；
- 指标观察先以 `candidate` 入库，只有对应当前结论修订经人工验收后才变为 `active`；驳回和新修订会分别进入 `rejected` / `superseded`，默认统计只读取 `active`；
- 指标事实字段受数据库不可篡改触发器保护，审核流程只能改变状态；查询支持指标键、时间窗口和单维度筛选，缺失值始终保留为未知，不按零计算；页面可查看当前已验收指标的数量、最新值、范围和逐条证据链接；
- 同口径比较第一增量：只允许同一指标定义、同一 `methodVersion`、同一标准单位的已验收数值观察按一个明确维度分组；返回观察数、最新值、最小值、最大值、平均值和最新证据，缺维度记录单独计数，超过安全上限明确标为截断；
- 账号隔离的保存视图：用户可把比较指标、方法版本、维度和可选时间窗口保存到当前专题；配置在服务端规范化、限制大小并防止同专题重名，页面支持应用和删除；
- 时间趋势第二增量：对同一指标、方法、单位及可选维度值按日/周/月分桶；没有观察的周期不补零，每个桶仍可回到最新证据；另以最早和最新的已验收观察生成确定性变化摘要，页面与 Agent 上下文均明确它只是观察方向，不是因果结论。当前同口径比较可导出 CSV，所有文本单元均防止表格公式注入；
- 多指标证据矩阵第一增量：允许选择 2–8 个已验收数值指标，按一个对象维度并排展示每一口径的最新观察；不同单位只并列、不加总，每个非空单元格携带观察时间和原始证据，空白保持未知；矩阵最多 50 行，可安全导出 CSV，并可保存、恢复或删除账号隔离的矩阵视图；
- 方法模板 v1：每个专题内置直接证据观察模板，也可创建新的不可变版本；模板明确允许证据类型、来源等级、必填维度、缺失值政策和比较政策，新 Researcher 任务冻结当时启用的完整模板，回传指标若引用未冻结版本或违反维度/证据政策会被拒绝；模板只能停用不能改写，且专题始终保留至少一个启用版本；
- 确定性单位换算第一增量：指标定义首次建立时冻结标准单位；后续数值观察只有在时间 `ms / s / min / h` 或存储 `B / kB / MB / GB / KiB / MiB / GiB` 的同族白名单内才允许换算，单位大小写精确匹配。平台同时保存标准值、原始值、原始单位、换算算法版本和约分后的精确比例；不兼容单位直接拒绝，货币、百分比、温度和日历周期不会自动换算；指标定义禁止原地修改；
- 可追溯派生指标第一增量：每条公式以稳定键和公式版本不可变保存，首版只允许两个已验收数值指标之间的 `difference`、`ratio`、`percent-change`，且输入必须使用相同标准单位；按一个显式维度读取双方最新观察，缺失输入和零分母返回未知而不是补零。结果在读取时计算，不写成新的原始证据；每个结果单元均保留左右值、观察时间和各自证据链接；不支持任意公式代码、嵌套派生或自动单位推断；
- R5 结构质量体检第一增量：账号隔离的服务端汇总检查已验收结论证据覆盖、关键结论官方一手来源覆盖、当前指标的单位/时间/方法版本/证据链完整性、跟踪来源、证据记录和未处理复核信号；零样本返回 `null` 而不是伪造 100%，结构门禁只代表可追溯字段完整，页面明确声明它不衡量事实真伪、漏报、误报或样本代表性；
- R5 人工质量抽样与纠正第一增量：按 UTC 自然月和稳定 SHA-256 排序，从当时已验收结论与当前有效指标观察中确定性选择至多 20 个样本；同月重复生成幂等，样本冻结目标修订和必要上下文。审核决定及理由只追加保存；失败样本只创建一个 `system` 来源的开放研究缺口，等待用户决定是否排队 Researcher，不会自动撤销结论、停用指标、调用外部模型或覆盖历史；
- R5 纠正确认第二增量：失败样本的“已纠正”不是手工勾选即可完成。平台只在对应研究缺口已完成、且原结论出现更高修订并重新通过人工验收（指标样本则要求同一定义出现更新的有效观察）后，才允许追加保存纠正确认，并记录替代目标与修订；人工也可带理由判定抽样为误报/无需纠正。两类处置都不可覆盖，质量汇总分别显示待纠正、已纠正和无需纠正；
- R5 变化捕获抽样第一增量：从已有前后版本的归档来源中按月确定性选择至多 20 个版本对，冻结来源、哈希、时间、有界前后摘录及最多 5 个已产生候选事件，供人工判断候选事件是否抓住该版本对中的主要变化。它与结论/指标事实准确率分开统计；失败项沿用只追加的纠正缺口与确认账本，不会自动调用 Researcher 或改写事件。该指标只衡量系统已经取得的版本对，不能证明未抓取网页没有漏报，也不是全网召回率；
- R5 事件簇来源体检第一增量：在既有“事件类型 + 规范化标题 + 日期完全一致”的保守事件簇上，统计簇总数、单来源/多来源簇、含官方一手来源簇和含反对证据簇，并列出最多 10 个需要人工注意的单来源或反对证据簇。该体检按事件原始来源去重，绝不把“多个已归档来源”包装成来源相互独立，也不会自动裁定反对证据、拆分事件簇或改变事实状态；
- R5 多账号公平领取与容量门禁增量：观察运行与 Researcher 任务不再采用可被单一账号大量任务占满的全局 FIFO。领取时每个账号只提供其最早待处理任务，再优先选择最久未获得服务的账号，账号内部仍保持创建顺序；数据库在同一领取事务中锁定账号行并统计仍有效的活动租约，分别执行可配置的观察运行和 Researcher 账号级硬上限，同时以独立事务级 advisory lock 串行检查部署全局上限，多个 API 实例和 worker 同时竞争也不能越过任一上限。专题运行体检和 Researcher 能力响应只返回当前账号的排队数、活动数、账号上限及可用槽位，不泄露其他账号活动量；既有租约超时、`uncertain` 和不自动重发边界不变。这是执行准入，不是平台总吞吐量、完成时限或资源容量承诺；
- R5 月度外部调用预算门禁增量：DeepSeek Search / Fetch 与 Researcher 模型任务在请求发送前，从部署配置冻结本次预计计费请求数和 USD 微单位成本；数据库使用账号行锁与同一个事务级 advisory lock，把冻结运行契约中的专题月度上限、账号月度上限、部署全局月度上限的“保守已用量 + 本次预计量”检查和行动/任务预约插入组成同一原子步骤。预算按 UTC 自然月计算；`reserved`、已发送、`failed`、`uncertain` 调用按预计值与实际值中的较大者占用额度，未发送即失败或租约过期的 Researcher 任务进入 `skipped` 并释放预约；超限调用不创建任务且不会发送。Researcher 首版按“每任务一次调用 + 运维配置的保守最大成本”计费，供应商 token 回执只用于核对，不冒充实时价格换算。专题契约可分别设置月度计费请求数和 USD 微单位成本上限，保存新契约只影响之后创建的运行；预算摘要分别返回当前专题和当前账号的已用、已预约、上限和剩余额度，不暴露平台全局用量。该门禁是部署配置与契约快照上的预防性上限，不等于供应商账单对账，也不能证明长期成本模型已经验收；
- R5 供应商熔断与恢复探针增量：Search / Fetch 与 Researcher 模型调用的近期可重试失败和不确定回执会写入跨实例共享的 PostgreSQL 熔断状态；默认 5 分钟窗口内连续 3 次失败后停止发送 5 分钟。Researcher 排队时先拒绝仍在冷却或半开的供应商，但真正的单探针资格只在 Worker 即将发送模型请求、原子写入 `sent` 水位时取得，避免队列等待耗尽探针租期。冷却结束只允许一个带 2 分钟租期的半开探针，其他 worker 继续停发；探针成功关闭熔断，失败重新打开，worker 在探针结算前中断则由相同请求的恢复路径记为 `uncertain` 并重新打开。非重试型 4xx 被视为请求问题而不是供应商故障。能力与运行体检只公开供应商的保护状态、重试时间和最后错误码，不公开其他账号调用量；该状态是防止故障风暴的保护机制，不是供应商 SLA 监控；
- R5 失效行动回收增量：每轮调度先以有界批次和 `FOR UPDATE SKIP LOCKED` 清理已超过恢复宽限期、且所属运行没有有效租约的 `reserved` 行动。尚未发送的行动转为 `skipped` 并释放月度预算预留；已有 `sent_at` 但没有结算回执的行动转为 `uncertain`，继续按预估值与实测值的较大者保守占用预算。半开探针随同一事务释放或重新打开，清理幂等且不会自动重发；仍持有效租约的运行不参与回收。默认宽限期 120 秒，用于避免慢请求与租约边界竞态；
- R5 供应商账单核对增量：用户可为自己的专题录入某供应商、已结束且最长 366 天账期的计费请求数与 USD 成本汇总、账单编号和核对说明。系统在同一事务中冻结当时 Search / Fetch 行动与 Researcher 模型任务两个账本的保守用量（失败、不确定、已发送未结算和预约中调用按预计/实际较大值），计算“供应商 − 平台”差异；完全相同的输入以 SHA-256 幂等去重。对账快照与“已核对/有争议”人工复核均只追加保存，不能更新或删除，也不会反向修改行动、预算或自动恢复额度。普通账号只能读取和复核自己的专题；页面明确禁止粘贴密钥或完整发票。这是人工汇总对账，不是供应商 API 自动验真；
- R5 只读存储与保留评估增量：每个专题可盘点来源版本元数据、最多 2,000 字的证据摘录、ChangeRadar 关联快照中的真实内联 `body_text`，以及尚未验证存在性的外部正文引用。评估按当前契约保留天数列出过期版本，并将仍被证据、事件、后继版本链或同账号共享来源的更长保留策略引用的版本标为受保护；只有无正文载荷、无引用且同时越过所有共享策略期限的元数据版本才进入“可清理候选”。当前接口和页面只预览，不删除、不迁移、不改写任何记录；64 MiB 内联正文阈值只触发对象存储评估提示，不是生产容量结论。普通 HTTP/RSS 研究版本目前并未保存完整正文，因此内部 `storage_ref` 不能被宣传为已完成全文归档；
- R5 外部漏报对照集第一增量：用户可导入平台之外整理的已知事件，来源 URL 先通过公开网络地址校验，事件身份以规范化输入哈希幂等冻结。每条事件只能由人工审核为“已检出 / 漏报 / 排除”；“已检出”必须绑定同一专题中真实存在的雷达事件，复核记录只追加且不可覆盖。质量汇总只对“已检出 + 漏报”的有限已审核样本计算检出率，零样本继续返回 `null`。平台记录来源类型与整理说明，但不会自动证明清单独立、完整或具有代表性，因此页面和 API 明确禁止把该数值外推为全网召回率；整个流程不自动搜索、不调用模型，也不产生外部费用；
- R5 来源关系账本与事件簇诊断增量：用户可在同一专题的两个来源之间记录“同一发布主体 / 共同原始来源或转载 / 组织上有关联 / 人工判断编辑独立 / 关系未知”。来源对按稳定顺序保存，每次改判只追加新修订，历史记录禁止更新或删除。事件簇诊断把最新人工关系覆盖到每个保守事件簇，展示已审核/未审核来源对、已知关联边、人工编辑独立判断、支持/反对证据，并仅依据已知关联边计算“暂定谱系组”；该数字用于发现转载链，不能证明剩余组相互独立。页面与 API 均明确这些不是自动所有权核验、语义聚类、统计独立性证明或冲突裁决；
- 租约超时进入 `uncertain` 并重新开放知识缺口，但不自动重发未知结果的外部调用；页面明确区分未接入、排队、研究中、已回传、失败和状态未知；

- 防止一个 URL 监控被其他专题静默抢占的关联冲突约束；
- 平台 API 客户端方法，以及账号隔离、契约边界、版本冲突、关联冲突和迁移测试。

尚未进入代码，因此不能宣称可用：开放网页中的自主实体抽取、来源等级自动判定、更广泛的单位目录/口径变换、嵌套或任意公式派生，以及任意聚合的通用 Agent 查询语言。兼容 Researcher Worker 已有技术预览代码和容器 profile，也已接入数据库月度成本预约、发送水位、保守结算和人工账单快照，但仍未完成目标服务器真实 PostgreSQL、真实供应商调用、供应商账单差异和长期崩溃恢复验收，因此不得作为生产能力启用或宣称已部署。当前来源等级能力是有审计历史的人工判定，不是系统自动评级；当前实体能力只包含人工登记与 GitHub URL 的确定性项目候选；事件归并只采用可解释的精确规则，不使用语义相似度自动合并。R3 当前完成的是安全的异步协议、队列、结果验收、候选结论修订、人工审核账本、保守的复核信号，以及只消费冻结证据且不自动重试的最小 Worker，不等于自动判断结论失效；R4 当前完成直接观察型指标账本、基础筛选、单指标同口径维度比较、多指标证据矩阵、首版可追溯算术派生、时间趋势、CSV 导出、比较与矩阵保存视图、方法模板 v1、时间/存储白名单精确单位换算，以及 Agent 被动上下文与一次性筛选/分组比较/趋势/矩阵/已保存派生指标查询，不等于完整统计比较产品。默认环境不会真正运行深度研究。启用平台 Search 密钥后，观察 worker 会按契约问题做有界主题搜索并提出候选网页；**搜索摘要只是线索，不是证据，候选网页必须由用户确认，并在后续运行中完成一次受控读取后才具备来源版本**。DeepSeek Fetch 只在管理员显式启用时取代这些已确认网页的 Direct HTTP 读取，不会自动抓取候选搜索结果。当前增量仍不是无边界全网研究器；Researcher 回传永远先成为候选结论，只有当前修订经人工验收后才会进入 Agent 上下文和指标统计。

## 2. 产品判断

### 2.1 不与基础模型竞争

墨鱼不重新实现 GPT、Claude、DeepSeek 等模型已经擅长的即时搜索、阅读、推理和写作。模型作为可替换的研究引擎；墨鱼负责模型会话之外的长期能力：

- 无人值守的定时运行；
- 跨日、跨月、跨 Agent 的研究状态；
- 来源版本、证据和结论历史；
- 新闻档案内部的统一计数、趋势和周期比较；
- 预算、限额、失败恢复和审计；
- 重大变化通知及对 Agent 的有界查询接口。

若最终产品只是“输入对象，搜索一次新闻，生成一次性摘要”，则本项目没有独立价值。产品成立的前提是：同一关注对象能够持续积累历史，并能回答“新发生了什么、多篇报道是否属于同一事件、旧观察是否需要修订、变化节奏如何”。

### 2.2 产品定义

> 墨鱼变更雷达围绕用户选择的一个关注对象，持续发现和读取相关新闻；新闻正文只作为有界、临时的分析输入，长期沉淀的是可追溯的原子事实、归并事件、维度变化与可修订观察结论，让用户和 Agent 能在未来任何时间继续筛选、比较、统计和复盘，而不必每次从零搜索。

### 2.3 自主等级

| 等级 | 能力 | 本路线 |
| --- | --- | --- |
| L1 | 定时检查已知来源 | 已有 V2 基础，继续完善 |
| L2 | 主动搜索新的新闻来源和候选事件 | R2 目标 |
| L3 | 根据知识缺口补充阅读、交叉验证并修订结论 | R3 目标 |
| L4 | 对外发帖、发信、购买、修改第三方系统 | **不做** |

目标是有边界的 L3 只读自主研究。自主不代表无限循环，也不授权系统登录网站、绕过付费墙、执行外部代码或代表用户对外采取行动。

### 2.4 首要研究范围与非目标

首阶段只解决一个明确问题：用户选择一个关注对象，系统跨周、跨月持续收集相关新闻，合并重复报道，整理事件演化，并保留每次判断对应的来源和时间。关注对象可以是公司、产品、人物、技术、机构、政策或边界清楚的公共议题，但一个专题必须有单一、可描述的观察边界。

当前新闻来源只包括公开新闻网页、RSS / Atom、机构新闻稿、搜索发现的候选报道，以及少量已有专用适配器。GitHub Release 仅在它确实构成相关新闻的一手来源时使用，不是产品中心；数据模型和界面不得要求所有专题都有 `repository`、`release` 或 `star`。

第一阶段的统计只描述平台新闻档案本身，例如：已收录报道数、候选事件数、来源数、来源关系覆盖、按日/周/月的新增事件、同一事件的来源支持数、首次与最新报道时间、未再观察事件。报道篇数和搜索命中数只是平台观察量，不能直接解释为现实事件规模、公众共识、社会趋势、经济影响或因果关系。

论文全文与引用网络、官方统计数据库、结构化经济指标、政策法规数据库、付费数据库和通用研究对象适配器暂不进入当前产品范围。首阶段也不承诺全文版权存储、自动事实裁决、自动立场判断、自动因果推断或代表性样本证明。未来若扩展，必须作为独立适配器与独立验收阶段加入，不能由通用新闻网页读取冒充。

## 3. 当前基线与缺口

### 3.1 已实现的 V2 基线

当前变更雷达已经具备：

- 创建、暂停、恢复和删除 URL 监控；
- 手动检查与后台检查所需的服务接口；
- 页面快照、结构化行级差异和历史列表；
- 任意变化、关键词出现、关键词消失、数字变化规则；
- 常见时间、浏览量等噪声归一化；
- 变更收件箱、未读计数、重要命中和已读状态；
- SSRF 防护、重定向复查、响应大小和超时边界；
- Agent 侧有界上下文同步；
- MCP 工具入口与内容寻址的 UI 资源。

### 3.2 尚未实现

- 自主实体抽取、实体合并审核、更广泛单位目录与指标定义管理界面；
- 其他搜索 / 抓取供应商适配与按专题选择供应商；
- 从开放网页和搜索结果中自主发现候选实体（当前仅有人工登记与 GitHub URL 确定性候选）；
- 来源等级自动判定与结论版本；
- Researcher 异步深度研究接入；
- 多输入、嵌套、跨单位或任意表达式的派生指标，以及非白名单单位换算；
- 自动结论加强、减弱、冲突、替代和失效；
- 指标级因果归因、货币成本面板、自动生成且可验证独立性的代表性对照集和长期准确性指标（当前指标周期归属只比较同口径已验收观察及其时间变化，不推断事件因果；人工外部对照集只能测量用户导入并审核的有限样本；变化捕获抽样只覆盖已归档版本对）；

### 3.3 兼容原则

现有 URL 监控不得因新设计失效。首轮迁移采用增加式结构：旧 `tool_change_watches` 与 `tool_change_snapshots` 继续工作，新专题可以引用旧监控作为来源；不得先删除旧接口再重建新界面。

## 4. 核心概念

### 4.1 专题 Topic

长期研究的顶层对象，不限于 GitHub 项目。专题可以是产品、公司、政策、技术方向、论文主题、行业、竞争集合或用户自定义问题。

专题包含：

- 目标和范围；
- 关注实体；
- 初始来源；
- 长期问题与当前知识缺口；
- 方法模板；
- 指标定义；
- 来源政策；
- 运行频率、预算和通知规则；
- 当前结论与历史版本。

### 4.2 研究契约 Research Contract

用户首次配置并明确授权系统长期运行的边界。每次运行冻结一份契约版本，至少包括：

```json
{
  "topicId": "uuid",
  "objective": "持续跟踪 AI 编程工具的产品与价格变化",
  "scope": {
    "entities": ["Codex", "Claude Code", "Cursor"],
    "allowNewEntityCandidates": true,
    "languages": ["zh", "en"]
  },
  "questions": [
    "主要功能发生了什么变化？",
    "价格和套餐发生了什么变化？"
  ],
  "method": "comparative-trend-v1",
  "sourcePolicy": {
    "preferOfficial": true,
    "allowWeb": true,
    "allowGithub": true,
    "allowPdf": true,
    "blockedDomains": []
  },
  "schedule": {"cadence": "daily", "timezone": "Asia/Shanghai", "localTime": "09:00", "weekday": 1},
  "limits": {
    "searchesPerRun": 5,
    "fetchesPerRun": 10,
    "deepResearchRunsPerMonth": 4,
    "monthlyBudgetCents": 10000
  },
  "alertPolicy": {
    "minimumImportance": "important",
    "quietOnNoChange": true
  }
}
```

契约修改只影响后续运行；历史运行继续引用当时的契约版本，不能用新配置重写旧结果。

### 4.3 来源、来源版本与证据

- **来源 Source**：官网、网页、仓库、Release、RSS、PDF、API 或用户材料的稳定身份。
- **来源版本 Source Version**：某一时间点读取到的不可变内容。网页以抓取时间和正文哈希定位，GitHub 以 commit 定位，PDF 以文件哈希和版本元数据定位。
- **新闻材料 News Material**：某次运行中读取到的一篇报道或订阅条目，只保存标题、URL、发布时间、内容哈希及与最小证据的关联；它是待分析输入，不是现实事件。
- **证据 Evidence**：来源版本中的有界原文片段，包含定位、用途和内容哈希。

搜索结果摘要只能作为发现线索，不自动获得证据资格。只有读取到正文或结构化原始响应，完成来源身份与内容绑定后，才能产生证据。普通新闻正文不作为长期全文资产保存：当前长期保留的是来源元数据、哈希、最多 1,200—2,000 字的必要摘录和结构化分析结果。

### 4.4 实体、事件、指标与结论

- **实体 Entity**：产品、公司、人物、项目、政策、技术、论文、机构或地区。
- **事实 Fact**：从一条或多条证据中提取的原子观察，显式包含主体、维度、谓词、值、单位、事实发生时间、方向和适用范围。新闻发布时间不能替代未知的事实发生时间。
- **事件 Event**：发布、更新、价格变化、政策修订、合作、安全事件或来源冲突等时间性变化。
- **指标 Metric**：按稳定定义和单位保存的可统计观察。
- **结论 Claim**：基于一组证据、事件或指标形成的当前判断，拥有状态和版本，不是不可修改的文章句子。

五层对象必须保持分离：

| 层 | 保存内容 | 能否直接用于长期结论 |
| --- | --- | --- |
| 新闻材料 | 标题、URL、发布时间、哈希、最小证据关联 | 否，只是输入 |
| 证据 | 有界原文摘录、定位、哈希 | 否，只用于溯源 |
| 原子事实 | 主体—维度—谓词—值—时间—范围 | 候选，需审核 |
| 现实事件 | 多事实、多报道归并后的时间性变化 | 候选，需审核 |
| 分析结论 | 对事实、事件、指标的解释与判断 | 版本化，需审核 |

同一事实的稳定身份不依赖模型临时生成的 `findingId`，而由主体、维度、谓词、值、单位、发生时间与适用范围确定。后续报道命中同一身份时追加新修订并累积证据；值、时间或范围变化时形成可比较的新事实，而不是覆盖旧观察。

## 5. 系统边界与职责

### 5.1 变更雷达控制面

平台内的变更雷达负责：

- 专题、契约、来源、计划和预算配置；
- 定时调度、任务公平性和并发控制；
- 已知来源的低成本检查；
- 版本、事件、指标、结论和报告的长期存储；
- 收件箱、时间线、统计、筛选、比较和通知；
- 用户权限、配额、审计和 Agent/MCP 查询；
- 触发并接收外部 Researcher 任务。

### 5.2 独立 Researcher 研究面

Researcher 负责：

- 围绕问题规划搜索与阅读动作；
- 判断知识缺口；
- 选择官网正文、固定 commit 源码或其他合格来源；
- 有界阅读和交叉验证；
- 生成带证据的事件、指标候选、结论和未解决问题；
- 模型预算、请求回执和研究阶段恢复。

Researcher 当前仍是独立产品实验，不与墨鱼共享数据库、凭据或内部表结构。变更雷达不得复制其整个工作流，也不得直接写入其数据库。

### 5.3 集成原则

双方仅通过版本化异步协议连接：

```text
Radar Research Controller
        │ submit sealed job
        ▼
Independent Researcher
        │ return bounded result + receipts
        ▼
Radar Result Ingestor
        │ validate, deduplicate, persist
        ▼
Timeline / Metrics / Claims / Agent tools
```

Researcher 不可用时，已知来源监控仍可继续；平台必须明确标记“深度研究未运行”，不得把普通差异摘要冒充深度研究结果。

## 7. 自主运行状态机

### 7.1 运行状态

`queued → admitted → observing → discovering → reading → extracting → verifying → applying → completed`

可进入以下终止状态：

- `no_change`：没有新内容，安静结束；
- `partial`：部分来源失败，但已有结果可安全保存；
- `budget_exhausted`：达到契约成本或调用上限；
- `blocked`：登录、验证码、付费墙或来源政策阻止；
- `uncertain`：远程请求可能已发生但回执不完整，停止自动重发；
- `failed`：确定失败，可按策略重新排队；
- `cancelled`：用户停止后不再进入后续阶段。

### 7.2 单次周期

1. 读取专题当前契约、预算、上次水位和未解决问题。
2. 执行准入检查：状态、租约、配额、并发、月度预算、来源政策。
3. 检查已知来源；使用条件请求、哈希和去噪规则避免无效分析。
4. 根据计划执行主题搜索，识别新 URL、新实体和新事件候选。
5. 对候选去重、规范化 URL、判断来源身份和读取资格。
6. 只读取新来源、已变化来源和当前知识缺口需要的来源。
7. 生成来源版本和有界证据；原始网页内容始终视为不可信数据。
8. 提取事件与指标候选，执行确定性类型、单位和范围校验。
9. 对重要发现搜索第二来源、官方来源或反对证据。
10. 必要时提交 Researcher 深度研究任务。
11. 验证返回协议、证据绑定、预算与来源资格。
12. 更新事件、指标和结论版本；不覆盖历史。
13. 生成本次摘要，仅在达到通知门槛时通知。
14. 记录完整运行水位、成本、停止原因和下一次计划。

### 7.3 探索与收敛

每个专题维护三类队列：

- **已知来源队列**：稳定、低成本地重复检查；
- **知识缺口队列**：针对未解决问题寻找具体证据；
- **探索队列**：发现新来源、新实体和反例。

每轮优先保证已知来源，再在剩余额度中分配缺口和探索。探索候选必须经过阈值或多轮观察后才能升级为正式实体，不允许一次低质量搜索结果永久改变专题范围。

## 8. 来源适配与证据资格

### 8.1 首批适配器

| 适配器 | 主要用途 | 正式版本锚点 |
| --- | --- | --- |
| Direct HTTP | 已知公开网页 | 抓取时间、最终 URL、正文哈希 |
| RSS / Atom | 更新发现 | feed、entry id、发布时间、正文哈希 |
| GitHub | Release、README、固定源码 | repository、commit/tag、blob SHA |
| DeepSeek Search | 主题发现 | 查询、运行时间、结果排名；仅作线索 |
| DeepSeek Fetch | 网页正文提取回退 | URL、读取时间、Markdown 哈希 |
| PDF Reader | PDF 和扫描页 | 文件哈希、页码、OCR 引擎版本 |
| JSON / CSV API | 公共结构化数据 | endpoint、参数、时间、响应哈希 |

DeepSeek Search / Fetch 严格按[官方 Search 指南](https://api-docs.deepseek.com/guides/search/)和[Fetch API](https://api-docs.deepseek.com/api/fetch/)接入：Search 使用 `POST /v1/tools/search` 并固定 `need_content=false`，Fetch 使用 `POST /v1/tools/fetch` 且请求体只包含已确认的公开 URL，二者都使用 Bearer 鉴权。以 2026-10-21 官方英文文档为准，只有 HTTP 200 且产生结果的 Search / Fetch 请求计费，失败、空搜索结果和超时不计费；408、429 和 5xx 可重试，其余 4xx 不应原样重试。当前官方标价均为每千次成功请求 0.75 美元。平台用整数 USD 微单位保存部署时价格和每次调用成本快照，不使用浮点货币；价格以后变化时只更新运行配置，历史账本不重算。平台实现不在单次运行内自动重试，也不在同一网页读取中混用 Direct HTTP 与 DeepSeek Fetch，避免 worker 中断、超时或回退造成重复调用和隐藏成本；失败由下一研究周期重新评估。

生产配置默认关闭：

# 以下配置只给独立 researcher-worker 容器，不给 API。

Search / Fetch 的 DeepSeek 密钥只进入 API 容器环境；Researcher 模型密钥则只进入独立 Worker 容器。两者都不写入专题、运行记录、调用回执、前端响应或日志。首版使用平台统一额度，不支持用户自带密钥。`RESEARCHER_WORKER_TOKEN` 是平台与兼容 Worker 之间至少 32 字节的独立服务密钥，不是模型供应商密钥，不能通过任务协议传入平台。Worker 使用 DeepSeek Chat Completions JSON mode，一次任务只发送一次模型请求；超时、连接中断、非完整结束、HTTP 错误或无效 JSON 都将当前任务记为失败/不确定并重新开放知识缺口，但不会由 Worker 自动重发。模型只返回证据 ID，Worker 使用冻结任务包恢复来源版本、定位和引文哈希，API 完成接口还会再次进行权威校验。`documentsRead=0` 表示 Worker 没有另外读取文档，只分析平台已经冻结的摘录。

技术预览只能用 `COMPOSE_PROFILES=researcher` 显式启动，同时必须设置 `RESEARCHER_WORKER_ENABLED=true`、共享 Worker token 和独立 `RESEARCHER_DEEPSEEK_API_KEY`。API 侧还必须用 `RESEARCHER_PROVIDER_MODEL` 固定预约模型，并用 `RESEARCHER_ESTIMATED_COST_USD_MICROS_PER_JOB` 为每个任务设置保守成本上限；生产 Compose 会把同一个 `RESEARCHER_PROVIDER_MODEL` 映射为 Worker 的 `RESEARCHER_DEEPSEEK_MODEL`，避免两处配置漂移。脱离 Compose 单独运行 Worker 时，才需要显式设置后者，而且必须与 API 预约模型一致；不一致会在发送前失败。模型任务现已和 Search / Fetch 共用专题、账号、全局三层月度预算与 PostgreSQL 供应商熔断状态；token 数作为供应商回执保存，但首版不会根据 token 数实时重算价格。目标服务器真实 PostgreSQL、真实供应商账单差异和崩溃恢复验收完成前，生产环境仍必须保持该 profile 关闭。

生产 Compose 默认使用 `RESEARCHER_WORKER_ID=researcher-worker-1`；同一部署扩为多个 Worker 时，每个实例必须设置不同且稳定的 ID，不能让两个进程共享。容器健康检查调用 `node apps/api/src/researcher-worker-cli.mjs --health`，通过内部服务密钥向 API 查询该实例的只读心跳，并核对供应商和模型；它不会接触 DeepSeek、领取任务或产生费用。连续失败只会把容器标为 `unhealthy`，Docker Compose 本身不会仅因健康状态自动重启仍在运行的进程，生产告警或编排器动作仍需在目标环境单独配置和验收。

四个并发配置分别限制账号级与部署全局的有效租约数，默认都为 1；全局领取使用事务级 advisory lock 串行完成“检查 → 占用”，未取得锁的 Worker 留到下一轮，不会越限或忙等。四个月度预算配置默认分别为每账号 100 次 / 1 美元、全部署 1000 次 / 10 美元，均按 UTC 自然月在请求发送前执行硬门禁；价格是运行配置快照而非供应商实时账单。供应商熔断默认阈值/窗口/冷却/探针租期为 3 次、300 秒、300 秒和 120 秒，状态保存在 PostgreSQL，所有 API 实例共享。失效行动恢复宽限期默认 120 秒：只有所属运行已经没有有效租约、且行动超过宽限期时才会结算为未发送跳过或已发送不确定，恢复器绝不自动重发。调高并发或预算、缩短冷却或恢复宽限期前必须先做目标服务器混合负载、供应商账单差异和恢复验收，不能把配置数字当作整机可承载并发、成本承诺或供应商可用性证明。

### 8.2 来源等级

- `official-primary`：官方公告、法规原文、产品文档；
- `official-implementation`：官方仓库、固定 commit、Release；
- `institutional`：研究机构、标准组织、监管机构；
- `independent-reputable`：可信媒体或专业作者；
- `community`：论坛、个人讨论、用户反馈；
- `unknown`：身份或原文无法确认。

搜索提供方的权威度字段只能作为候选排序信号，最终等级由平台的来源身份规则和证据决定。

### 8.3 禁止自动获取

- 包含用户名、密码、token 或签名参数的 URL；
- 回环、私网、链路本地、云元数据和其他 SSRF 目标；
- 需要登录、验证码、付费墙或绕过访问控制的内容；
- 可执行文件和不受支持的二进制内容；
- 用户未授权提交给外部搜索提供方的私人问题或材料。

## 9. 数据模型

以下为逻辑模型，实施时按现有 migration 规范细化。重要查询字段使用真实列和索引，不能把所有内容塞进单个 JSONB。

### 9.1 专题与配置

#### `research_topics`

`id, owner_id, title, objective, status, current_contract_version, created_at, updated_at`

状态：`active | paused | archived`。

#### `research_topic_contracts`

保存不可变契约版本：范围、问题、方法、来源政策、计划、预算、通知和保留策略。

#### `research_entities`

`id, owner_id, entity_type, canonical_name, aliases, external_ids, confidence, discovery_basis`

这是账号级规范身份，不承载某个专题的当前确认状态。

#### `research_topic_entities`

专题与实体的关系、角色、加入原因、专题级状态与不可逆首次启用时间。状态为 `candidate | tracked | rejected | muted`；每次人工变化另写入不可覆盖的 `research_entity_status_reviews`，不能改写实体身份，也不能影响同账号其他专题。

### 9.2 来源与证据

#### `research_sources`

`id, owner_id, canonical_url, source_type, publisher, authority_tier, status, first_seen_at, last_seen_at`

#### `research_topic_sources`

记录来源属于哪个专题、为何加入、监控频率及是否由用户固定。

#### `research_source_discoveries`

保存搜索运行、调用账本、查询哈希、候选来源、排名、供应商评分和短摘要。该表不可变，但不是证据表；供应商摘要不得被事件、指标或结论直接引用。

#### `research_source_versions`

`id, source_id, fetched_at, published_at, content_hash, normalized_hash, locator, content_type, storage_ref, previous_version_id, fetch_receipt`

版本不可原地修改。大正文后续可以迁移到对象存储，但数据库必须保留哈希、定位和审计元数据。

#### `research_evidence`

`id, source_version_id, locator, quote, quote_hash, evidence_kind, allowed_uses, created_at`

`locator` 对网页可为标题路径/字符区间，对 GitHub 为 commit/文件/行号，对 PDF 为页码与块坐标。

### 9.3 事件、指标与结论

#### `research_events`

`id, topic_id, entity_id, event_type, title, occurred_at, detected_at, importance, confidence, status, run_id`

事件与证据使用关系表连接，避免在事件行内复制长正文。

#### `research_metric_definitions`

`id, topic_id, metric_key, label, value_type, canonical_unit, dimensions_schema, method_version`

#### `research_metric_observations`

`id, metric_definition_id, entity_id, observed_at, value_number, value_text, unit, source_value_number, source_unit, conversion_version, conversion_numerator, conversion_denominator, dimensions, confidence, evidence_id, run_id`

缺失值是未知，不得记为零。比较只允许同一指标定义版本，或经过明确单位与口径转换的观察。当前实现仅允许时间与存储白名单中的确定性同族换算，并保留原始值、原始单位、算法版本及精确有理数比例；首次创建后的指标定义不可原地修改。

#### `research_claims`

保存结论稳定身份和当前状态：`proposed | active | weakened | disputed | superseded | invalidated`。

#### `research_claim_revisions`

`id, claim_id, revision, statement, scope, method, confidence, valid_from, valid_until, reason, run_id`

结论修订不得删除旧版本。支持证据、反对证据和相关指标分别通过关系表绑定。

### 9.4 运行与展示

#### `research_runs`

保存契约版本、触发原因、状态、阶段水位、计数、成本、停止原因、输入和结果摘要。

#### `research_run_actions`

每个 Search、Fetch、直接读取和模型请求在发送前预约，保存请求哈希、attempt id、回执状态和结算用量。`uncertain` 动作不得自动重发。

#### `research_reports`

周期摘要与专题报告；报告引用事件、指标、结论和证据 ID，不成为新的事实来源。`tool_research_reports` 对每个 `run_id` 最多各保存一份不可变 `run-summary`、`weekly-summary` 和 `monthly-summary`，分别对应本轮、截至本轮的滚动 7 天和滚动 30 天窗口；对于已结束且有运行的自然周期，还会按“专题、报告类型、起止时间”唯一保存 `calendar-week-summary` / `calendar-month-summary`。全部报告保存契约版本、结构化内容和内容 SHA-256，报告体数据库硬上限为 1 MiB。内容严格区分 `observedEvents` 候选变化与生成截止时的 `acceptedClaims` / `acceptedMetrics` 账本快照；任何候选事件都不得因进入报告而自动转为正式结论。所有周期汇总只读取此前不可变运行报告，最多处理 100 轮并显式标记截断。

研究事件上的 `notification_eligible`、`notified_at` 与 `read_at` 只表达提醒投递和阅读状态。资格由该轮冻结契约的 `notifications.minimumImportance` 决定；更新已读状态不得改写事件事实、证据、重要性或报告快照。

### 9.7 `tool_research_claim_review_signals` / `tool_research_claim_review_signal_resolutions`

复核信号绑定专题、结论和精确修订，类型限于 `stale | revision-reopened | contradiction`。信号只说明“需要人工注意”，不得直接修改结论或指标状态；矛盾信号可引用另一条相关结论，但不把该引用解释为自动推翻。信号和处置记录均为数据库级 append-only，处置必须包含 `acknowledged | dismissed | revalidated` 之一及人工说明。到期信号以最近一次验收或 `revalidated` 时间为起点计算，去重键包含该起点，因而同一修订在人工重新确认后仍可于下一周期再次进入复核。

#### `research_saved_views`

保存筛选、排序、列和比较对象，不保存未经权限检查的结果副本。

## 10. 事件与结论生命周期

### 10.1 事件

事件先作为候选，经来源、时间和证据校验后转为正式事件。重复报道同一事件应聚类，不应在统计中重复计数。

事件重要性由可解释规则产生，至少考虑：

- 是否来自官方一手来源；
- 是否影响用户配置的核心问题或指标；
- 是否改变已有结论；
- 是否涉及价格、可用性、政策、安全或重大版本；
- 是否得到多个独立来源支持。

模型可以建议重要性，但程序保存规则输入和最终原因。

### 10.2 结论

每条结论必须包含：

- 明确陈述；
- 适用对象、时间、地区和范围；
- 使用的方法版本；
- 支持与反对证据；
- `direct | corroborated | inferred | unverified | conflicted` 置信类型；
- 生效时间、复核时间和当前状态。

新证据可以：

- 加强结论；
- 减弱结论；
- 产生冲突；
- 缩小或扩大适用范围；
- 用新结论替代旧结论；
- 使旧结论失效。

系统不以一个不透明的百分比分数冒充真实性。需要排序时可以计算内部信号分，但用户界面必须展示来源、方法和冲突原因。

## 11. 方法论引擎

方法模板定义采样、口径、缺失值、比较条件和停止规则，而不是只提供一段模型提示。

### 11.1 `trend-v1` 趋势观察

- 固定实体和指标；
- 记录观察频率、统计窗口和基线；
- 区分真实为零与未观察；
- 标记单位、定义或来源变化造成的断点；
- 只有达到最小观察数后才生成趋势结论。

### 11.2 `comparison-v1` 多对象比较

- 预先定义比较对象、指标和权重是否存在；
- 所有指标使用同一版本和时间窗口；
- 不以缺失值自动判负；
- 输出事实矩阵与分析结论分离；
- 每一格可回到来源与证据。

### 11.3 `before-after-v1` 事件前后分析

- 明确事件时间、前后窗口和观察指标；
- 输出相关变化，不自动声称因果；
- 记录同期其他重大事件和数据缺口；
- 样本不足时只输出观察，不产生趋势结论。

### 11.4 `triangulation-v1` 多来源核验

- 主张至少寻找官方来源、独立来源或反对证据；
- 相互转载的来源不能当作独立支持；
- 来源冲突必须保留，不能由模型静默择一；
- 无第二来源时允许保存 `unverified`，但不进入高置信结论。

首版只实施以上四类，不建立无限扩展的“方法市场”。每个模板必须有可复现的测试夹具和缺失数据反例。

## 12. 统计、筛选与比较

### 12.1 统计规则

- 统计只读取结构化事件与指标，不从报告正文临时数数；
- 每个派生指标保存公式和版本；
- 时间统一保存 UTC，展示按用户时区；
- 货币、周期、地区、套餐和税费是维度，不得仅比较裸数字；
- 去重后的事件才进入频率统计；
- 被撤回或纠正的观察保留记录，但默认不进入当前统计；
- 所有图表提供数据表和证据入口。

### 12.2 首批筛选维度

- 专题、实体、来源、来源等级；
- 时间范围、事件类型、重要性；
- 结论状态和置信类型；
- 指标、单位、地区和方法版本；
- 未读、已处理、存在冲突、需要复核；
- 本次新增、相对上期变化、历史全部。

### 12.3 比较输出

比较由三层组成：

1. 事实矩阵：结构化观察和缺失状态；
2. 变化矩阵：相对基线或上一周期的变化；
3. Agent 分析：解释差异、限制和可能影响。

Agent 分析不得回写事实矩阵。若发现矩阵错误，应创建纠正候选，由确定性校验和新证据生成新版本。

## 16. 调度、成本与资源

### 16.1 调度原则

- 用户关闭 Agent 后，服务端仍按契约运行；
- 没有变化的运行不调用深度分析；
- 条件请求、内容哈希和任务内去重优先；
- 新用户和高频专题受公平队列与并发上限约束；
- 失败退避带抖动，HTTP 408、429 和 5xx 才按政策重试；
- 其他 4xx 不在请求不变时重试；
- 暂停专题后不创建新运行，正在读取的任务在安全检查点停止。

日/周计划是契约时区中的墙上时间，不是从上次完成时刻机械增加 24/168 小时。这样用户选择的当地 09:00 不会在夏令时切换后漂移；每次成功入队后直接计算当前时刻之后的下一次日/周发生点，服务停机期间错过多个周期也只补一轮，不集中创建历史欠账。夏令时回拨造成同一时间出现两次时取当前之后最早的一次；春季跳时导致所选时间不存在时顺延到当天第一个有效分钟。旧契约缺少新增字段时按当地 09:00、星期一解释，首次按旧 `next_run_at` 触发后再进入新规则，避免迁移时突然提前产生运行。

专题调度器与 API 同进程运行，并在 API 开始监听前启动。生产容器沿用 `/ready` 健康检查，因此调度器从未启动、被显式停止、连续 3 轮顶层失败或循环长期卡死会使 API 容器进入非健康；空队列不会误报，循环内已经捕获并落账的来源失败也不会误报为调度器停止。默认“空闲过期”门槛为 3 个一分钟轮询周期，“单轮卡死”门槛为 15 分钟。该信号只能证明本 API 进程中的循环近期推进，不证明某个专题按时完成、外部供应商可用、通知送达或长期 SLA 达标。

### 16.2 预算层级

- 平台全局供应商预算；
- 用户月度预算；
- 专题月度预算；
- 单次运行 Search、Fetch、模型和总时限；
- 深度研究次数上限；
- 通知频率上限。

预算检查必须在请求发送前进行；实际用量与供应商账单不一致时保存差异并停止后续高成本阶段，不能自动重置额度。

### 16.3 初期资源

初期继续使用现有 PostgreSQL 和 API 部署，增加独立后台 worker；不需要 GPU。主要成本来自搜索、抓取和模型调用，而非 CPU。大正文增长到影响数据库备份、查询或磁盘门槛后，再将正文迁移到对象存储，数据库保留索引和哈希。

## 17. 安全、隐私与内容治理

- 外部供应商密钥只保存在服务端密钥存储；
- 每个查询、来源、证据、事件和报告都绑定 owner 与 topic；
- Agent 工具和保存视图不能绕过现有用户权限；
- Fetch 延续 DNS 解析、私网阻断、重定向重验和响应大小限制；
- 搜索查询可能被发送给外部提供方，创建契约时应明确提示；
- 私人文件默认不发送给外部搜索服务；
- 不执行被研究仓库代码，不安装外部依赖；
- 不绕过 robots、登录、验证码或付费墙；
- 保存正文遵循容量与保留策略，导出内容继续受原来源权利约束；
- 用户可暂停、归档和删除专题；删除流程必须覆盖派生数据并保留最小合规审计。

## 18. 可观测性与质量指标

### 18.1 运行指标

- 待运行、运行中、失败、部分完成和不确定任务数；
- Search / Fetch / 模型请求量、成功率、延迟和费用；
- 每个专题新来源、新版本、事件和证据数量；
- 重复来源与重复事件拦截率；
- 无变化运行比例；
- 通知数量和用户打开/处理率。

### 18.2 研究质量指标

- 正式事件拥有证据的比例，目标 100%；
- 正式指标拥有单位、时间、定义版本和证据的比例，目标 100%；
- 比较单元可回溯证据比例，目标 100%；
- 结论中 `unverified` 与 `conflicted` 的可见率，目标 100%；
- 新阅读产生有效事件、指标或结论修订的比例；
- 重要变化样本中的漏报、误报与重复通知；
- 每个有效发现的 Search、Fetch、token 和费用成本。

模型输出通过 schema 不等于研究质量通过。真实专题验收必须有人对样本证据和结论做独立核对，并保留失败样本。

## 19. 迁移路线

### R0：设计与兼容基线

交付：

- 本文评审通过；
- 冻结核心术语、责任边界和 `research-job-v1` 草案；
- 记录现有 V2 数据和接口兼容矩阵；
- 不改变线上 URL 监控。

通过条件：产品、数据、安全和 Researcher 边界无相互矛盾；未将未实现能力写入上线说明。

### R1：专题控制面

交付：

- 专题、契约版本、实体和来源关系；
- 计划、预算、运行状态和专题时间线；
- 现有 URL watch 可挂入专题；
- Agent 查询专题和事件。

通过条件：迁移后现有 watch 数量、状态、历史和未读数一致；暂停、恢复、并发和跨用户隔离通过真实数据库测试。

### R2：自主发现

当前进度：已落地受限的 Search / Fetch、不可变调用回执和专题运行体检，可按日期、供应商和行动类型观察成功率、不确定率、计费调用及冻结价格成本。该体检只衡量运行可靠性和候选产出，不把候选数量解释为研究质量，也不能替代下面要求的 10 个专题、14 天真实连续运行验收。

交付：

- RSS / Atom、普通新闻网页、机构新闻稿、DeepSeek Search / Fetch 适配；GitHub Release 仅作为可选的一手发布来源；
- 新闻候选的标题、链接、发布时间、首次发现时间、来源身份和转载/共同原始来源关系；缺失字段保持未知，不由模型猜测；
- 候选来源、候选实体、去重和来源等级；
- 证据与事件结构；
- 每次运行调用、成本与停止原因。

通过条件：Search 摘要不能进入正式证据；SSRF、重定向、限额、不确定回执和恢复测试通过；10 个内部专题连续运行 14 天，不出现无限循环或静默超预算。

## 20. 首批内部试点

首批只验证“关注一个东西的长期新闻变化”，不同时承担论文库、统计数据库或通用研究平台的验收。选择 3 个边界明确但新闻形态不同的关注对象，共用同一套专题、来源、证据、事件与结论账本：

### 20.1 产品或公司

- 示例：一个 AI Agent 产品或一家科技公司；
- 来源：官方新闻稿、官方博客、可靠媒体、RSS 和搜索候选；
- 关注：发布、价格、合作、组织、安全事件和公开战略变化；
- 输出：去重后的事件时间线、来源关系、周/月新增事件和结论修订。

### 20.2 人物或机构

- 示例：一个公开人物、研究机构或行业组织；
- 来源：机构官网、公开声明、采访和可靠媒体；
- 关注：任职、公开主张、项目、合作与争议事件的时间演化；
- 输出：按时间排序的事件档案、原始说法与后续报道的证据链。

### 20.3 技术或公共议题

- 示例：一个边界清楚的技术方向或公共议题；
- 来源：机构新闻稿、可靠媒体、公开说明页和 RSS；
- 关注：关键事件、参与者、事件簇、来源转载关系和长期变化节奏；
- 输出：事件趋势、来源覆盖、待核实缺口和周期报告。

试点成功不是“生成了一篇看起来不错的报告”，而是连续两周后仍能回答：

- 这个关注对象新增了哪些候选报道和经确认的重要事件？
- 多篇报道是在讲同一事件，还是相互独立的新变化？
- 哪些来源是原始发布，哪些可能是转载或引用？
- 哪些旧观察被加强、修订、反驳或长期未再观察？
- 每条回答能否回到当时的报道、摘录、发布时间和归档版本？
- 相比每次从零搜索，是否减少重复阅读和模型成本？

## 21. 明确不做

首轮路线不包括：

- 无范围的全网爬虫；
- 登录态抓取、验证码绕过和付费墙规避；
- 运行外部项目代码；
- 自动对外发布、发信、评论或购买；
- 无预算上限的多 Agent 循环；
- 用模型自由文本直接生成正式统计数字；
- 将搜索排名或供应商权威分直接当作事实；
- 在没有规模证据时引入向量数据库、复杂 BI 或分布式消息系统；
- 宣称所有领域都能自动形成可靠结论。

以下决策不阻塞 R0 文档定稿，但必须在对应实施阶段前确定：

1. Researcher 以本机服务、独立云服务还是受控 worker 运行；
2. DeepSeek Fetch 与后续深度研究是否继续使用平台统一额度；Search 首版已确定只使用平台统一额度，不接收用户密钥；
3. 网页全文、PDF 和 OCR 内容的默认保留期限与容量；
4. 首版通知仅站内，还是增加邮件等渠道；
5. 深度研究何时自动触发，何时只生成候选等待下一计划周期；
6. 第一个公开试点专题及其指标定义；
7. 用户删除专题时，研究审计与供应商用量记录的最小保留范围。

## 23. 开发前完成定义

开始 R1 编码前必须同时具备：

- 数据表与索引草案；
- 现有 V2 兼容和回滚方案；
- 专题、运行、来源、事件和结论状态机测试表；
- `research-job-v1` 与 `research-result-v1` JSON Schema；
- Search / Fetch 数据发送与隐私说明；
- 配额、成本和不确定请求处理规则；
- 首个试点的固定方法、实体、指标和人工参考样本；
- 每个阶段的非目标与停止条件。

只有同时满足这些条件，才从“产品想法”进入可实施工作包。

## 24. 全球新闻来源目录与地区来源包

新闻追踪不把“订阅全部媒体 RSS”视为默认策略。不同媒体对 RSS、商业聚合、自动化读取和全文再利用的许可不同，因此首版采用以下可审计流程：

1. 平台维护 `research-news-source-catalog-v1` 来源目录，记录媒体、地区、语言、域名、官方说明链接、访问策略和仅供审核的 RSS 候选；
2. 契约通过 `sourcePolicy.searchPacks` 选择 `global-core`、`europe`、`americas`、`asia`，新专题默认选择全球核心包；
3. 每轮运行按运行 ID 在来源包的域名组之间确定性轮换，并通过 DeepSeek Search 的 `site:` 条件发现新闻候选；
4. 搜索结果和摘要只用于候选发现，不自动成为证据，也不保存媒体全文；
5. RSS 候选不自动订阅，必须先核查媒体条款，再由用户确认加入专题；
6. 旧专题未设置来源包时继续使用原有不限站点搜索，避免契约升级突然改变既有追踪口径；
7. 搜索行动回执记录来源包和域名组，便于复现、统计覆盖率和排查来源偏差。

当前目录是可版本化的种子清单，不宣称覆盖所有国家或语言。后续应把目录更新纳入独立审核流程，并定期检查失效域名、RSS 状态和许可变化。

## 25. 增量新闻搜索与覆盖审计

新闻搜索必须绑定不可变运行窗口，避免每轮反复发现相同旧闻：

- 首次运行最多回溯 30 天；后续从上次成功运行时间向前重叠 24 小时，降低边界漏报风险；
- 搜索请求使用 `after:YYYY-MM-DD`，运行摘要同时保存精确到秒的 `after` / `before` 审计窗口；
- 供应商返回了明确发布时间且落在窗口外的结果不归档；没有发布时间的结果可以保留为候选，但必须单独计数；
- URL 入库前移除常见广告追踪参数、片段标识、尾部斜杠并排序查询参数；同一运行内规范化 URL 重复的结果只归档一次；
- 已经存在于账号来源库中的 URL 不重复创建来源，只记录再次发现次数；
- 运行摘要记录供应商原始结果数、归档结果数、重复数、窗口外结果数、无日期结果数、实际媒体域名、标题组数量，以及每个地区来源包的计划域名与实际返回域名；
- 标题组只是候选覆盖诊断，不等同于事实事件聚类。正式事件聚类仍必须发生在网页读取、证据归档和分析之后。

这些统计用于识别搜索偏差与覆盖缺口，不用于给媒体质量自动打分，也不把“没有搜到”解释为“没有发生”。

## 26. 独立 Agent 插件边界

变更雷达以独立插件接入 Agent，不再要求用户安装整套游戏与创作插件。首版采用“薄插件 + 托管研究服务”：

- 插件包位于 `plugins/change-radar`，有独立的插件清单、Skill、宿主支持声明和 MCP 配置；
- 专用 Streamable HTTP 入口为 `/mcp/change-radar`，只暴露 `open_change_radar`，不会把游戏搜索、PDF 阅读器或其他平台工具一并加入 Agent 工具列表；
- 插件只负责理解用户意图、打开侧栏、预填监控任务和定向到有界只读分析，不保存账号令牌、模型供应商密钥或研究正文；
- 私有专题、证据账本、定时调度、Search / Fetch、Researcher Worker 与数据库继续由托管服务负责，因此 Agent 和设备关闭后仍能运行；
- 公开 MCP 端点不读取私有专题。私有数据由已登录托管侧栏通过账号隔离 API 解析，并只向 Agent 返回有界、可追溯、已验收的上下文；
- 创建监控等有状态操作仍要求用户在侧栏确认；工具调用成功只表示页面已准备，不能冒充任务已经启用；
- 原 `/mcp` 中的 `open_change_radar` 暂时保留，保证已安装 GameHub 插件和历史会话继续可用；独立插件通过新端点并行发布。

首版不拆数据库和 Worker。只有当独立插件的安装、登录、创建专题、后台运行、跨会话回看和卸载回归都通过后，再把研究服务从平台 API 进程与数据库中物理拆分。这样先验证产品边界和用户价值，避免一次迁移同时引入插件、认证、数据和调度四类风险。
