## 实际发现并修复的问题

GitHub 查询 `browser ui helper tool` 返回 HTTP 200、合法 JSON、10 条结果，但解码后大小为 **681087 字节**。旧适配器只允许 262144 字节，且把超限错误包装成 `AGENT_GITHUB_SEARCH_RESPONSE_INVALID`，导致候选搜索失败。

调整原始响应上限为 1 MiB，并使用流式读取，在超过上限时立即取消响应体；保留专门的 `AGENT_GITHUB_SEARCH_RESPONSE_TOO_LARGE` 错误。工具输出仍按原合同规范化，描述截断为 1000 字符，条目和输出大小上限不变。该修改没有扩大 URL、工具、发布或账号权限。

新增回归覆盖合法大响应、规范化结果大小、无 Content-Length 的超大流取消，以及无效 JSON 分类。相关工具/发现单元测试 18 项通过，四条 GitHub 数据库链路回归通过。

## 扫码页故障修复及恢复（北京时间 21:05 后）

用户截图中的 `QQ_GATEWAY_UNAVAILABLE` 有两个已确认原因：

1. 验收页每两秒新建网关客户端，重复请求 `/auth/login`，触发网关实际返回的 `login rate limit`。改为按网关地址复用客户端；底层鉴权并发合并，限流后等待 60 秒再尝试。页面明确显示读取失败/冷却状态，不再一直显示“读取中”。
2. 网关随后停在 `reconnecting`。源码及实际接口确认 `/RefreshQRcode` 返回 `{restarting:true}`，并未生成二维码；后续读取自然返回 `QRCode Get Error`。现在分别保留 `QQ_GATEWAY_RESTART_REQUIRED` 与 `QQ_QR_UNAVAILABLE`，二维码未就绪不会清除有效鉴权凭据。

确认测试账号离线、旧 worker 没有待处理消息后，只重启原测试网关以重建 QQ 登录服务。恢复记录验证：同一镜像、同一挂载、原 worker 未重启、数据库未重启、旧消息历史不变；本轮等待型 worker 为加载鉴权修复单独重启，独立业务库保留。网关新本机端口自动记录到私有配置，用户扫码页地址仍为 51712。

实际复验：状态连续三次返回 HTTP 200、`waiting_qrcode`；刷新二维码返回 HTTP 200，确认包含有效 HTTPS 二维码 URL，二维码内容未输出到日志。单元验证并发十次状态只鉴权一次、限流冷却后恢复、重启需求及二维码未就绪分类。浏览器验证错误提示、限流恢复、二维码显示和已登录后隐藏二维码通过。

恢复证据：本轮证据目录中的 `gateway-recovery-20261120130528029.json`。仍需用户刷新扫码页并手机确认，尚未完成真实 QQ 群内验收。

## 正确账号就绪后的消息接入复验

后续确认正确测试账号已登录、测试群可用，才备份原消息路由并激活新 worker。第一次群消息在网关日志和真实群历史中均存在，含正确的 @ 与文字，但新业务队列为空，没有模型调用。同期网关反向 WebSocket 日志持续出现 HTTP 403；不能把单一 `connected=true` 指标当作消息已接通。

在确认新 worker 无待处理消息后，仅重启新 worker 清理旧 socket，QQ 网关及账号登录保持不变。加入签名控制接口下的聚合入站诊断：握手拒绝类别、消息计数，以及仅指定测试提问者的消息形状，不保存消息正文或认证头。重连后观察到一次有效握手、连续心跳，无新握手拒绝；仍需用户重发真实消息验证业务接收。

同时修正连接维护的异步竞态：不再把进入检查前的连接布尔值沿用到配置写入，而是在检查及读取配置之后重新读取当前连接。连接已恢复时，不再重写其路由。单元用例覆盖检查期间和读配置期间恢复连接的两种情况。测试 worker 重启后的随机本机端口也改为重新发现并保存，避免控制接口引用旧端口。

此时研究写作权限仍未授予测试提问者，权限拒绝用例尚待真实回复确认。没有为了让验收通过而放开权限、导入旧群消息或重放那条未接收的消息。

### 写作纠正的边界

交互草稿注册 `blog.project.single.draft-shadow@3`，保留 v2 的记录及验收合同。v3 仍只有原有私有阶段，不装配发布 Gateway；没有增加发布权限。新增独立的 `blog.article.composition-attempt@1`，在持久账本中区分模型尝试与通过校验的文章。无效输出最多保留 256 KiB，最多发起一次受原预算约束的纠正；再次失败即停止，不补造字段、不手改模型文章、不无限重试。

本次真实成功运行的两次 composition 尝试都通过了 JSON 字段结构校验；第一稿标题含 `finder`，不满足既有中文标题合同，纠正后才通过完整正文与引用规范化。因此这次真实运行验证的是内容合同纠正；缺少字段的纠正及连续两次失败不落文章，通过离线数据库回归验证，不能混为同一真实用例。
