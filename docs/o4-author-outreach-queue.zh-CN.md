# O4.5 GitHub 作者联络队列

更新日期：2026-10-12。

## 目标

把“找到适合联系的作者、准备一封基于真实资料的邀请、避免重复打扰、记录后续结果”变成可运营流程。系统负责筛选、起草和记录；管理员负责核对仓库、选择渠道、实际发送和处理回复。

## 候选门槛

同步操作只纳入同时满足以下条件的作品：

- 游戏已经公开发布；
- 发布关系为“平台代收录，可认领”；
- 已关联格式有效的 GitHub 仓库；
- 已记录明确许可证；
- 不存在待审核、已认领、争议中或暂停中的认领关系。

同一个规范化仓库只创建一条联络记录。后续同步只增加新候选，不覆盖管理员已经编辑的草稿，不重置状态，也不会再次发送。

## 工作流程

```text
待核对 → 可联系 → 已联系 → 已回复 / 不参与
   │         │          │
   └─────────┴──────────┴→ 暂缓 → 重新核对
```

每条记录包含作品、仓库、仓库所有者、许可证、联系标题、个性化正文、联系渠道、实际联系记录、内部备注和版本。所有状态变化写入不可更新、不可删除的事件表。

系统生成的草稿明确说明：

- 正文固定提供英中双语版本，英文在前、中文在后；
- MOOYU.FUN / 墨鱼工坊的身份和产品用途；
- 作品页与原仓库地址；
- 当前页面属于平台代收录、等待作者认领；
- 作者可以核对、认领、维护或要求停止展示；
- 这是一封针对具体作品的人工邀请，不会自动重复发送。

## 人工发送边界

“在 GitHub 核对并发送”只打开 GitHub 的新 Issue 编辑页面并预填标题、正文，不调用 GitHub 写接口。管理员仍需：

1. 确认仓库允许用 Issue 联系，优先遵守仓库 README、贡献指南和社区规则；
2. 检查草稿事实、称呼、许可证和作品页面；
3. 在 GitHub 页面亲自确认并提交；
4. 将实际 Issue、Discussion 链接或邮件主题写回队列，再记录“已联系”；
5. 作者拒绝、要求下架或不适合联系时立即停止后续触达。

本阶段不爬取邮箱、不自动创建 Issue、不批量私信、不根据公开提交记录推断私人联系方式，也不实现自动催促。

迁移 `0066_author_outreach_bilingual_template.sql` 为联络记录增加草稿模板版本。管理员再次执行“同步合格候选”时，系统只会将仍处于“待核对”、版本为 1、从未联系且从未编辑的旧草稿升级为英中双语；人工修改过或已经进入联络流程的内容不会被覆盖。

迁移 `0067_author_outreach_brand.sql` 会把历史联络草稿中面向作者的旧 `GameHub` 品牌统一替换为英文 `MOOYU.FUN`、中文“墨鱼工坊”，包括已经进入后续状态的记录；它只替换标题和正文中的品牌文字，不改变作品、仓库、联系人、状态或联络记录。

## 数据与接口

迁移 `0065_author_outreach_queue.sql` 增加：

- `author_outreach_records`：每个作品、每个仓库唯一的当前运营状态；
- `author_outreach_events`：只追加的发现、编辑、联系、回复、拒绝、暂缓和重新开启记录。

管理员接口：

```text
GET   /v1/admin/author-outreach
POST  /v1/admin/author-outreach/sync
PATCH /v1/admin/author-outreach/{outreachId}
GET   /v1/admin/author-outreach/{outreachId}/events
```

所有接口要求管理员账户并返回 `Cache-Control: no-store`。更新使用记录版本做乐观并发检查；记录“已联系”时必须同时提供联系渠道和实际联系记录。

## 验收清单

1. 不符合发布关系、许可证、仓库或认领状态门槛的作品不会进入队列。
2. 同一仓库重复同步不会创建第二条记录。
3. 草稿使用真实作品标题、许可证、仓库和正式作品地址。
4. 打开 GitHub 只到可人工检查的编辑页，不发生服务端写操作。
5. 没有实际联系记录时不能标记“已联系”。
6. 状态和草稿并发修改受版本保护，历史事件不可更新或删除。
