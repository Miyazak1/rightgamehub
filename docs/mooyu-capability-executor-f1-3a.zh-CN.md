# 论文版面与 OCR 本地能力准入 F1.3a

版本：v1.0
状态：合同、确定性路由、可运行参考包、冻结评测及本地结果出站审计闭环已完成；生产 OCR 引擎尚未接入
更新日期：2026-10-29

## 1. 本阶段目标

F1.3a 把 `research.paper.layout@1` 作为通用能力执行织网的第一个真实本地能力消费者。它不建立 OCR 专用队列，也不在单台 4 核 8G 服务器常驻 PaddleOCR。服务端继续只承担身份、权限、调度、预算、版本与审计；用户 PDF 和版面计算默认留在用户桌面端。

本阶段解决四件基础问题：

1. 哪些页面可以直接使用文字层，哪些只需本地版面重排，哪些确实需要 OCR；
2. 本地能力进程怎样在严格授权下读取用户选中的 PDF；
3. 版面块、页面坐标、阅读顺序、置信度和引擎来源怎样形成不可伪造的严格输出；
4. 能力包怎样复用现有签名、沙箱、资源限制、内容寻址产物和桌面更新链。

## 2. 已冻结的边界

- 能力 ID：`mooyu.research.paper.layout`；
- 合同：`research.paper.layout@1`；
- 第一执行位置：`desktop/windows-x64`；
- 文件权限：仅用户明确选中的只读文件；
- 网络与设备：全部为空；
- 数据策略：`localOnly=true`、`upload=never`；
- 默认资源预算：2 CPU、3072 MiB 内存、4096 MiB 临时磁盘、0 GPU；
- 可离线、可后台运行，但首次选择文件要求用户在场；
- 不允许云端静默降级。

这不是 PaddleOCR 专用合同。PaddleOCR、PP-StructureV3 或未来其他引擎只能作为合同后面的实现适配器，不能改变任务、权限和证据语义。

## 3. 确定性路由

路由只使用严格页面信号，不让模型决定是否上传或是否启动 OCR：

| 页面情况 | 路由 | 说明 |
| --- | --- | --- |
| 文字量、字符质量和定位信息正常 | `text-layer` | 继续使用轻量文字层路径 |
| 文字层完整，但有双栏、表格或公式信号 | `local-layout` | 本地做阅读顺序和结构恢复，不重复 OCR |
| 无文字、低密度、替换字符过高或扫描页 | `local-ocr` | 仅处理必要页面，不对整本 PDF 粗暴 OCR |
| 文件、页数、OCR 页数或政策超限 | `blocked` | 失败关闭，不自动放宽预算或上传 |

混合 PDF 可以同时包含三类页面，输出 `mixed`。每一页只能进入一个集合，页码必须完整、连续、无重复。冻结样本覆盖原生文本、扫描件、混合文档、损坏文字层、复杂版面和 OCR 预算超限。

## 4. 严格结果合同

正式版面结果必须包含：

- 原 PDF 的 SHA-256；
- 引擎名、版本和 OCR 模型摘要；
- 每页宽高、处理方法和版面块；
- 每个块的类型、正文、归一化坐标、置信度和阅读顺序；
- 覆盖率、最低真实块置信度、质量等级和原因码。

坐标使用万分比归一化，必须处于页面边界内。块 ID 在整份结果中唯一；同页阅读顺序不可重复。只要存在 OCR 页，就必须提供 64 位十六进制模型摘要。最低置信度必须等于实际块最低值，质量等级由确定性阈值推导，能力引擎不能把低质量输出自行标记为“可信”。结果页集合和处理方法还必须与准入决策逐页一致。

## 5. 本地包骨架

`scripts/build-paper-layout-capability-package.mjs` 生成自包含 Windows 参考包：

- 包含当前受信 Node 运行时、参考 worker 和合同模块；
- 生成严格 `capability-package-v1` 清单与逐文件哈希；
- 使用 `{{PACKAGE_ROOT}}` 可移植入口参数，安装目录变化后仍能运行；
- runner 每次启动前复验清单中的全部文件，而不只复验 `node.exe`，脚本或合同模块被改写会在进程启动前失败关闭；
- worker 读取沙箱请求，对获授权 PDF 重新计算大小和 SHA-256；
- 只产出确定性路由决策和内容寻址产物，不冒充已经执行 OCR。

能力进程属于低信任执行域。它写出的 JSON 不会因为进程退出码为 0 就直接进入本地产物库：正式 Windows
bootstrap 会在入库前调用桌面宿主的可信合同校验器，重新检查路由集合、坐标、阅读顺序、模型摘要、质量
阈值与元数据摘要。校验器使用平台随签名桌面发布包分发的同一份 `agent-capabilities` 合同代码；合同版本或
媒体类型不匹配、附加字段、虚报质量和元数据串线均失败关闭。

Windows runner 现在只把明确授权的 `sourcePath` 写入能力请求。路径仍受用户选择、文件身份复验、只读 ACL、AppContainer、Job Object、断网和资源上限约束；未授权路径不会进入请求。

参考构建命令：

```powershell
node scripts/build-paper-layout-capability-package.mjs `
  --output C:\Temp\mooyu-paper-layout-1.0.0
```

该目录是开发与验收骨架，不是生产发布包。生产分发仍需归档、Ed25519 发布签名、产品目录、HTTPS/CDN 和最终 Authenticode。

## 6. 自动化证据

当前自动化覆盖：

- 6 组冻结路由样本；
- 严格字段和附加字段拒绝；
- OCR 模型来源、坐标边界、阅读顺序和质量等级自洽；
- 桌面唯一放置、零网络、仅本地和禁止云降级；
- 自包含 Windows 包构建、清单规范化和真实 worker 运行；
- 沙箱请求只暴露明确授权文件路径；
- 可移植包根参数在安装目录内展开。
- 参考包真实穿过文件授权、原生 runner、本地产物库、结果出站门禁、远端完成与双阶段本机审计；远端提交体
  不含私有 PDF 字节或本机路径，网络中断时保留同一提交 ID 恢复，不把不确定结果误报为失败。
- 可信校验发生在 worker 产物进入本地内容寻址库之前；定向测试证明校验失败时存储调用次数为 0，实际参考包
  也穿过相同校验器。校验器、runner、参考消费者、出站审计与桌面发布组成检查合计 25/25 通过。

## 8. F1.3b-1 引擎与模型目录基座（已完成）

生产引擎接入前的两层合同已经冻结：

1. `paper-layout-engine-descriptor-v1` 明确引擎名、版本、适配器版本、模型集合摘要、支持方法、语言、组件、
   CPU/内存/磁盘/GPU 预算和页面像素上限；宣称支持 OCR 却缺少检测模型、识别模型或模型集合摘要会失败；
2. `paper-layout-engine-plan-v1` 只从已经验证的准入决策生成，把具体页码确定性分配给 `local-layout` 和
   `local-ocr`，绑定 PDF 摘要、引擎、语言、组件、模型摘要和资源上限。被阻止的决策、纯文字层任务、语言或
   方法不支持以及模型摘要漂移均失败关闭；
3. `capability-component-catalog-v1` 为大模型组件提供独立 Ed25519 签名目录。组件按 ID、角色、版本、引擎、
   平台、语言、SHA-256 和字节数精确选择，支持目录有效期、签名 key 生效窗口和摘要撤销；选择函数自身先验签，
   不能误用未经验证的目录；
4. 合同保持浏览器可导入，不静态依赖 Node 原生模块；大模型不会进入网页包、API 镜像或基础桌面安装包。

引擎计划、共享包导入与签名组件目录定向回归 10/10 通过；与此前可信产物和出站链路合计验证均为零新增失败。
本段只完成可替换引擎和按需模型的安全基座，尚未下载或运行真实 OCR。

执行器当前全量回归为 104 项：88 通过、14 条按明确环境条件跳过、2 条仍是当前命令沙箱无法创建受限令牌
（Win32 87）导致的既有真实 helper 健康验收失败；本阶段新增的合同、目录、可信校验和参考消费者没有新增失败。
独立签名 Windows 发布包也完成一次实物构建、隔离安装与包内 Node 导入验收。受限令牌两项仍必须在普通用户
Windows 发行环境复验，不能记作通过。

## 9. F1.3b-2a 组件本地安装闭环（已完成）

模型和原生组件现在具备独立于基础桌面包的本地生命周期：

1. 组件目录在任何缓存命中或网络请求前都必须完成 Ed25519 验签、有效期、key 窗口、撤销列表和精确身份选择；
2. 组件下载支持 HTTPS Range、ETag 和中断续传。运行时 ZIP 与组件文件共用同一下载内核，但保留各自固定的文件后缀、
   元数据版本和错误命名空间，避免两套实现分叉；
3. 安装采用 `componentId / version / SHA-256` 内容寻址目录，复制到暂存区后重新检查类型、字节数和 SHA-256，再原子切换；
4. 本地存储有全局安装锁、空间配额、活动版本和上一版本保护。清理只能删除未被活动状态、回退状态或调用方保留集合引用的
   已验证目录；正在使用的组件不能卸载；
5. 组件清单只回传身份、大小和活动状态，不把绝对路径暴露给控制面；绝对路径只在可信桌面执行器内部交给引擎适配器；
6. `paper-layout-engine-runtime-v1` 已能消费冻结的引擎计划，逐个确保组件可用，并在交给适配器前再次验证普通文件、大小和摘要。
   引擎计划若缺 PDF 渲染器、版面模型或 OCR 检测/识别模型会失败关闭。

组件目录、存储、断点续传、旧下载器兼容和引擎计划物化定向回归 15/15 通过。其中包含一次真实本地 HTTP 连接中断，第二次
请求使用精确 Range 续传后完成安装；篡改目录、篡改签名、超配额、删除在用组件和组件集合不完整均被拒绝。

这一步仍未下载或运行 PaddleOCR / PP-StructureV3，不把“组件可安全安装”描述为“OCR 已可用”。

## 10. F1.3b-2b-1 组件解析与只读投影（已完成）

冻结引擎计划现在能在可续租执行期内解析为已复验的本地组件，并通过升级后的 Windows helper 以只读 ACL 投影到 AppContainer。组件在启动前复验普通文件、大小、摘要和 Windows 文件身份，能力进程只看到必要身份与路径；旧 helper 会因协议版本不匹配失败关闭。详见 [F1.3b-2b-1 实施文档](./mooyu-capability-executor-f1-3b-2b1.zh-CN.md)。

这一步仍未运行真实 OCR。当前组件是单个内容寻址文件，生产模型目录和推理运行时还需要可验证多文件组件包。

## 11. F1.3b-2b-2a 多文件组件包合同（已完成）

`capability-component-bundle-v1` 已冻结，安全解包器会同时验证外层签名摘要、精确根布局、内部逐文件摘要、声明文件全集和展开资源上限，并拒绝路径穿越、链接、特殊文件、未声明文件与内容替换。详见 [F1.3b-2b-2a 实施文档](./mooyu-capability-executor-f1-3b-2b2a.zh-CN.md)。

## 12. F1.3b-2b-2b 签名多文件存储与目录投影（已完成）

签名组件目录已升级为 v2，直接绑定内部清单摘要、文件数和展开大小；多文件组件能够内容寻址持久安装，并在每次使用前从已验签 release 重新验证外层归档、内部清单和全部文件。论文引擎与 Windows helper 协议 v4 已支持目录最小权限投影：目录只遍历，普通文件只读，明确可执行文件单独获得执行权。详见 [F1.3b-2b-2b 实施文档](./mooyu-capability-executor-f1-3b-2b2b.zh-CN.md)。

当前受管开发会话无法创建 Windows 受限令牌，真实 AppContainer 验收仍需在普通桌面发行环境完成；这一步也仍未运行真实 OCR。
