# F1.3b-2b-2a：可验证多文件组件包合同

状态：已完成
日期：2026-10-29
边界：本阶段冻结并实现安全解包器；尚未把多文件目录接入活动组件存储、Windows 沙箱或真实 OCR 适配器。

## 1. 为什么必须单独建设

F1.3b-2a 的 `component.bin` 可以可靠保存单文件组件，但 PP-StructureV3 模型、PDF 渲染器和本地推理运行时通常包含多个文件。直接解压下载包会留下四类风险：

- 外层 ZIP 摘要正确，但内部文件不完整或被替换；
- 路径穿越、绝对路径、链接或特殊文件逃出安装目录；
- 未在清单声明的文件进入模型目录；
- 压缩炸弹消耗用户磁盘和内存。

因此不能用“下载成功”或“ZIP 能打开”代替组件安装成功。

## 2. 冻结格式

`capability-component-bundle-v1` 固定只有两个根条目：

```text
component.bundle.json
payload/
```

清单包含：

- 组件 ID、角色和版本；
- 按字节序严格递增的相对路径；
- 每个文件的 SHA-256、字节数和可执行标志。

外层 ZIP 的 SHA-256 和字节数继续由签名组件目录及引擎计划绑定；内部清单不重复外层摘要，避免自引用摘要。

## 3. 安全解包与复验

实现 `extractVerifiedCapabilityComponentBundle`：

1. 解包前验证外层普通文件、字节数和 SHA-256；
2. 目标目录必须不存在，失败时只删除本次新建的暂存目录；
3. 复用通用安全 ZIP 解包器，拒绝加密条目、绝对路径、反斜杠、路径穿越、重复条目、链接和特殊文件；
4. 限制文件数、清单大小和总展开字节数；
5. 根目录必须精确包含清单与 `payload/`；
6. 实际文件集合必须与清单一一对应，未声明或缺失文件均失败；
7. 逐文件重新计算大小和 SHA-256；
8. 返回值包含已验证绝对路径，但不会进入控制面或服务端。

路径字符和排序规则固定为跨平台 ASCII 合同，避免 Windows、本地桌面和未来其他执行节点对同一清单产生不同解释。

## 4. 验证

新增回归覆盖：

- 正常多层模型目录；
- 外层归档摘要漂移；
- 内部内容替换；
- 未声明文件；
- 清单路径穿越；
- 失败后的暂存目录清理。

组件包与既有能力包安全解压组合回归 7/7 通过。

## 5. 后续状态

安全解包器还不能单独进入生产，下一阶段必须一起完成：

1. 组件签名目录 v2 直接绑定内部清单摘要、文件数和展开大小；
2. 内容寻址的持久多文件组件存储，活动/回退、配额和清理语义与单文件组件一致；
3. 每次使用前从签名目录重新取得内部清单身份并逐文件复验，不能只信本地元数据；
4. Windows helper 对目录只授予遍历，对清单文件分别授予只读或明确可执行权限；
5. 完成后才允许 OCR 引擎适配器取得模型目录。

以上 F1.3b-2b-2b 项目已经实现，详见 [签名多文件组件存储与最小权限目录投影](./mooyu-capability-executor-f1-3b-2b2b.zh-CN.md)。

F1.3b-2b-2c 才接独立引擎子进程和 PP-StructureV3/PaddleOCR CPU 实现；真实引擎和质量门槛通过前，后台不得显示“OCR 已就绪”。
