# 公开调研发布系统：架构与边界评估

日期：2026-11-17。基线：`9f3ae847`。独立分支：`codex/audit-blog-system-boundaries`。

本轮是代码与系统边界评估，不是一次新的生产修复发布。没有修改业务代码、历史迁移、数据库约束、线上数据、配置、任务或论文开关。所有新探针使用本地合成资料、任务专属 PostgreSQL 或 Compose 的只读配置解析。

## 结论与此前验证的不足

现有系统已经具备工作流、能力与发布权检查、不可变证据、费用账本、幂等发布事务，以及失败暂停保护。主要缺口是跨层契约没有收敛：资料采集、模型上下文、动作账本、执行取消、控制台投影和部署身份各自执行局部规则，组合后的输入与状态缺少统一验证。

此前模块回归和真实数据库端到端测试验证了固定夹具。公开流水线数据库夹具只有一个仓库、一份较短 README；没有覆盖合法最大候选数、多份长中文资料、纠正上下文膨胀、多层回滚配置和已展开阶段详情的刷新。此前将这些通过结果当成生产完整链路可靠性的充分证据，验证范围估计不足。测试数量和条件跳过数量都不能替代这组边界覆盖。

## 一、P0：模型上下文与动作账本容量契约冲突

证据位置：

- `apps/api/migrations/0123_agent_runtime_foundation.sql:246`：动作 `request_json` 必须是对象，且 `octet_length(request_json::text) <= 65536`。
- `apps/api/src/agent-provider-gateway.mjs:47`：将完整模型请求连同策略、提示词版本、schema、时限等放进动作请求。
- `apps/api/src/agent-runtime-repository.mjs:660`：未执行对应大小准入，直接插入动作表。
- `apps/api/src/agent-blog-foundation-generation.mjs:165`：每份资料截取 2400 字符，另有最多 4800 字符的项目总摘录；请求再次包含材料列表，部分文本重复。
- 同文件的选题、写作、两种纠正请求均走此存储路径。纠正还会追加原回复。模型策略、单条消息和动作账本的大小边界并不相同。

新复现使用真实选题处理器：5 个合法候选，每个仅有 README，文字、许可和结构均符合现有验证；无需触及采集上限或执行外部模型调用。

| 检查 | 结果 |
| --- | --- |
| 候选数 | 5 |
| 完整动作请求的紧凑 UTF-8 JSON | 80,829 字节 |
| 真实 PostgreSQL JSONB 文本 | 80,867 字节 |
| 动作表限制 | 65,536 字节 |
| 请求对象类型 | object |
| 真实数据库结果 | SQLSTATE 23514，agent_run_actions_request_json_check |
| 该请求计算的输入 token 估计 | 25,990 |

数据库探针使用同一检查表达式的临时表，真实尝试插入并捕获约束错误，随后回滚。它没有还原截图中失败请求的精确内容；它证明普通合法输入即可触发同类内部错误。截图的检查约束同时包含类型和大小两项，生产请求的具体字节数仍需失败上下文才能审计还原。

进一步风险：只验证 4 次调用和 18000 输出 token，不能证明两种纠正均能在 90000 输入 token、单消息字节、模型上下文和阶段总时间预算下完成。`estimatedTokens` 对业务 payload 估算，没有将最终全部消息与系统提示词作为统一输入预算单位。

整改方向：

1. 定义唯一的“已编译请求”契约，包含实际消息、完整哈希、提示词/schema/投影视图版本、UTF-8 字节、输入 token 保守估算和截止时间；网关、账本及模型适配器使用同一结果。
2. 将大请求正文保存为受权限控制的不可变输入产物，动作行记录产物引用和完整请求哈希。优先评估现有产物存储与类型约束的兼容性；需要新表时采用新增迁移，不修改历史迁移。幂等比较必须绑定完整正文，不能仅比较缩短后的描述。
3. 资料原文保留在证据层；选题使用有总预算的候选视图，写作仅使用已选证据视图。截取和缩减须保留来源定位、原始哈希及截取标记，不能悄悄伪造摘要或丢失引用血缘。
4. 在派发前检查完整序列化、输入/输出 token、调用次数和剩余时间；无法容纳时明确拒绝，避免让数据库约束成为业务验证器。

不建议直接删除或放宽 64 KiB 检查：这会留下消息、token、纠正和审计存储之间的其他冲突。

## 二、P1：预检展示与实际命令准入不一致

`agent-blog-public-operations-readiness.mjs:27` 的 `manualRun.ready` 仅取决于 runtime blockers。计划暂停加入的是另一组 scheduler blockers。`AgentAdmin.jsx:150` 用 `manualRun.ready` 启用“立即运行”，但 `agent-blog-public-schedule.mjs:111` 实际要求计划 enabled，并继续检查心跳和运行中的 fire。

本地探针得到：计划暂停、runtime 预检通过且心跳正常时，`manualRun.ready=true`，`scheduler.ready=false`。按钮会允许一项实际命令必然拒绝的操作。上一轮 409/503 修复使错误可读，但没有统一这两套准入。

整改：明确区分“模型执行器具备能力”“请求立即调度”“启用每天计划”三种操作。建立共享准入规则，UI 读取该操作的同一份准入结果；写入端在事务锁内重新核验相同条件。保留显式恢复语义，不让点击立即运行偷偷解除暂停。

## 三、P1：运行终态与阶段详情缓存不一致

`AgentAdmin.jsx:107` 刷新运行列表和概览，未更新 `runtimeDetails`；109 行发现已有详情时只切换展开状态，不重新请求。152 行同时渲染新运行状态和旧详情阶段状态。因此能出现列表“运行失败”、阶段仍“运行中/blocked”的组合。

数据库 `agent-runtime-repository.mjs:549` 的失败处理已在事务中更新失败阶段、取消剩余阶段并设置运行终态，本轮没有证据证明这些持久状态同时损坏。读服务 timeline 另有多查询快照可能跨越一次状态提交的问题。

整改：详情按运行更新时间/版本失效，运行终态后读取最终详情；读端提供同一快照版本或一致性事务。将“数据尚未刷新”与真实运行状态分开显示，不能让已失败的顶层记录继续搭配无提示的活动阶段缓存。

## 四、P1：阶段取消没有贯通到外部调用

Worker 在超时或租约丢失时中止自己的 signal，并将 signal 交给 handler；选题/写作到 Provider gateway 的调用没有转发它。DeepSeek 适配器新建独立 AbortController，仅受自身 timeout 控制。GitHub 材料读取也使用独立超时 signal。

本地无网络探针确认：外层 signal 已 abort，适配器 fetch signal 未 abort，调用仍可完成。这里证实的是取消边界缺失，不是生产已经发生重复发布。

整改：贯通阶段截止时间、租约取消和适配器超时。对已经派发的请求，取消不能被当作“没有发生调用”；继续保存已确认、未确认和费用结算事实，使用现有 uncertain 及对账机制。保留现有发布事务、唯一回执和 CAS 防护。

## 五、P1：多层回滚配置与镜像身份不够明确

上一轮修复固定了项目目录，但 `prepare-unified-release.sh:55` 仍按 `rollback-images.yml` 文件名过滤覆盖层。再次备份会把配置改名为 `compose-N.before.yml`；该名字被当成普通覆盖文件继续传入，旧 image 指定就可能遗留。

真实 Compose config 最小复现：主文件的 API image 是 `mooyu-audit-new-release`，叠加一份名为 `compose-1.before.yml` 的旧镜像配置后，实际 image 为 `mooyu-release-rollback:older-api`。不需要启动容器即可确认重命名不会消除覆盖内容。线上是否经过该具体路径，还需读取其部署文件链；不能仅凭 rollback 标签推断版本成功或失败。之前六项文件哈希一致只证明那六项内容一致。

整改：为基础配置、人工覆盖、发行资产、回滚镜像覆盖分别保存明确来源和角色；根据结构及来源重建发布配置，不靠文件名推断。新构建使用唯一发行标签，部署后记录实际 image ID/digest、代码和工作流版本及配置摘要；回滚记录引用不可变身份，禁止新构建覆盖历史回滚标签。

## 六、发布验证与故障分类需要升级

现有 `/ready`、练习目录、迁移及工具检查验证了应用就绪，不能证明下一批真实 GitHub 资料能完成公开发布。小资料端到端测试同样没有覆盖上述大请求边界。SQLSTATE 23514 目前可能以底层数据库错误直接进入运行失败、连续失败暂停和 UI。

建议分为：

- 安装就绪：迁移、配置、论文关闭、实际镜像及工作流版本一致。
- 数据路径就绪：零 Provider 派发的请求编译预演，真实数据库检查产物、动作引用、序列化字节、来源和预算契约。
- 故障收敛：模型格式、网络、输入过大、预算耗尽、租约丢失、内部契约错误和人工暂停使用稳定的分类，不将所有失败归为同一种“机器人不工作”。系统性失败保留暂停保护，不通过反复恢复计划来掩盖。
- 可观测性：以同一 run/stage/action 关联 release ID、请求哈希、最终序列化字节、token 估计和剩余预算；在动作插入被拒绝前也保留有界诊断元数据。诊断不输出密钥和原始业务正文，避免失败请求只留下无法复原上下文的 SQL 错误。
- 发布验收：脱敏的真实资料结构夹具及合成边界矩阵，通过后才进行受控生产验证。不得自动补跑历史失败或重复公开文章。

## 修复顺序与验收门槛

1. **先解决数据通路**：统一请求编译与预算，分离正文产物和动作账本；同时覆盖选题、写作、两种纠正、工具请求和领域写入。保留原文和历史审计。
2. **再统一运行控制**：共享命令准入、终态详情刷新、一致快照、取消传播和未决结果对账。
3. **收敛发行系统**：配置角色可追溯、唯一发行镜像、连续两次及三次回滚后重试，验证旧回滚仍可恢复原内容。
4. **按矩阵验收**：候选数 1/3/5、材料数 1/6、短/长资料、中文/英文/emoji/转义字符、最大人格与记忆、无纠正/单纠正/双纠正、临界字节、预算不足、阶段超时、断连、提交确认丢失、重试、进程重启和重复点击。

完成标准：合法输入不触发内部 SQL 约束；所有合法请求或被明确接纳、或在派发前按契约拒绝；拒绝不产生未记账的模型调用；同一任务重放不重复计费或发布；终态和界面一致；回滚不改变历史恢复材料；论文持续关闭。

本轮未实施这些整改，不能把本报告或探针复现结果当成新版本已经修好。业务基线仍是 `9f3ae847`。
