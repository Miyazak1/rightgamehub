# 自动调研发布：编辑记忆与连续运行修复

## 行为与历史兼容

- 固定兴趣标签保存在项目编辑意图中，不再生成“场景冷却”；选题理由不再冒充事实主张。新主张记录来自实际文章摘要，继续绑定引用证据。
- 旧事件、主张关系、项目版本关系及文章均不删除、不重写。旧 `payload.signal` / `payload.rationale` 记录保留为历史，不再否决新选题；已发布主项目的永久排除、主题和比较组合冷却继续有效。
- 选题格式、编号和冷却冲突共用原有的一次纠正机会，不扩大模型调用、令牌或 GitHub 请求预算。仍然冲突时保存不可变的跳过决定；事务内将后续四阶段置为 `skipped`，不写草稿、不发布，也不增加调度连续失败数。
- 公开工作流升级为 v3，结果契约为 `blog-publication-result-v2`。原工作流定义和运行历史保留；只有声明此契约且具有同运行、同阶段的有效跳过产物，才能提前正常结束。
- 同一请求在准入和新快照之前核对原运行、交接关系与不可变发布回执/跳过决定。即使后来日限额已满，也返回原结果，不再次调研或发布。
- 历史标题只在读取快照时统一空白、限制长度并去重，避免同名历史文章破坏下游唯一值契约。
- 搜索词的有效超额提议最多保留五条原始建议，服务器只准入冻结上限内的前若干条；产物记录 proposed/admitted/omitted 数量。非法词及超大建议集仍拒绝，回退搜索仍共用原上限。
- 写作纠正明确列出标题中的违规英文词，包括 KB 等单位缩写；继续由实际模型重新生成，不改写引用、不替换模型回复、不放宽校验。

## 边界矩阵

| 边界 | 预期与验证 |
| --- | --- |
| 同一机器人连续发布 | 三个不同文章 ID，三个发布回执；历史记忆仍存在 |
| 相同兴趣、不同选题 | 正常通过，不因固定兴趣触发 90 天冷却 |
| 旧理由/兴趣记录 | 历史不变，不作为新主题的否决条件 |
| 真实主题冲突 | 第二次受治理选题换角度后，正常写作、核验和发布 |
| 两次均冲突 | 保存跳过决定；compose/verify/persist-draft/publish 均 skipped，无领域写入 |
| 伪造跳过决定 | 拒绝并回滚当前阶段事务，不能提前完成其他工作流 |
| 跳过后的调度 | fire 成功，result.publicationState=skipped；计划仍启用，下一次时间保留 |
| 同请求重放 | 日限额用尽后也返回原结果；不增加模型调用、文章或回执 |
| 发布提交后确认丢失 | 从已提交运行事实恢复；每篇仍只有一个回执与发布事件 |
| 选题索引/格式与冷却混合 | 共用两次总调用，不发生第三次纠正 |
| 搜索词 5 条、上限 1/2/3 | 审计省略数量，实际搜索不超过对应上限 |
| 英文项目名/KB 标题 | 精确反馈违规字段，与引用纠正共用一次写作修复预算 |
| 大证据、Unicode、转义符 | 原请求容量与输入预算矩阵继续通过 |
| 原工作流定义 | v2 定义哈希不变，v3 单独登记，不改历史运行 |
| 论文 | 本地公开流程没有 paper.* 运行；上线继续验证四个论文开关关闭 |

## 验收证据

最终真实验收使用独立 PostgreSQL 17、实际 DeepSeek `deepseek-flash` 和真实 GitHub 搜索/固定版本资料；没有连接生产数据库。

真实模型连续流程产生三篇文章，之后正常跳过；共 13 次模型调用。对冷却换题与跳过分支，通过受治理的模型请求明确要求生成一个已有主题，用来稳定触发服务器检查；没有修改模型回复。四个请求重复提交以及运行结果重放均没有新增模型调用或发布回执；临时模型凭据已移除。

- `.runtime/blog-public-live-ddohfs/report.json`：实际模型、调用、结果和重放报告。
- `.runtime/editorial-continuity-release-verified/result.json`：371 个文件，1635 项通过、0 失败、94 项按环境跳过。
- `.runtime/editorial-db-matrix/`：23 个文件分别使用独立数据库，68 项通过、0 失败、0 跳过。
- `.runtime/editorial-continuity-manifest-guard-db.tap`：最终结果契约绑定及重放复验。
- `.runtime/editorial-continuity-admin-browser.tap`：两项管理台检查通过；运行状态刷新与“本次跳过”使用真实 Edge，设置载荷检查使用单元测试。

按环境跳过的用例没有计作通过；相关数据库与浏览器路径按上述方式单独执行。本文不把先前失败的验收报告计作通过证据。

## 发布方式

使用 `deploy/update-blog-editorial-continuity.sh`，先从固定发布提交提取到 `/www/backup/gamehub/update-editorial-*` 私有日志目录运行。脚本复用经过校验的现有统一安装包及原有统一发布/回滚流程，不要求另传工具包。

脚本保留 `.env.prod` 副本并核对更新前后哈希，继承运行中的助手开关，不删除数据卷或备份。验证 API 与调度器中的修复文件哈希、论文关闭状态后，幂等登记新版工作流；`RESUME_BLOG_SCHEDULE=true` 才显式恢复计划，不立即补发旧任务。部署、登记、恢复、退出码、阶段及两个服务的日志均保存在同一私有日志目录。
