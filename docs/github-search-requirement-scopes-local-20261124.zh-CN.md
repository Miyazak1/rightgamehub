## 修复结果

此前，“生成 DOM CSS selector、浏览器可用、偏好 MIT、排除资料合集”与“逐项核验、证据链接、说明无法确认原因、不写文章”进入同一个条件数组。核验器因此要求仓库 README 证明我们的回答方式，导致实际项目条件已有支持证据的候选仍标为待确认。

现在规划单独记录 `criteria`（项目筛选条件）与 `responseRequirements`（执行及回答要求）。后者有自己的8项额度、a1至a8编号、原文引用和格式校验，不占项目条件额度。元数据过滤器仍只能来自明确的项目硬条件，回答要求不能授权添加筛选器。

候选核验模板只包含项目条件；元数据仍由服务端重算。回答要求通过证据链接、未知理由和结果格式落实。需要补充的回答要求单列 `unhandledResponseRequirements`，显示提醒而不改变候选判定；真正遗漏或弱化的项目条件仍进入 `unhandledRequirements` 并阻止完整匹配。核验器给候选添加 a1 等回答要求检查时会拒绝，不能重新污染候选结论。

结果支持列表、表格与简短展示。简短展示最多在正文列出2个候选，并明确说明全部候选的核验保存在任务证据中；不会删除完整结果。表格转义单元格中的分隔符、换行和 HTML 标记，保留固定版本证据链接与逐项理由。不写文章继续由搜索工作流和结果渲染实现，没有新增文章写入或发布路径。

旧规划与旧核验 JSON 仍可读。新接收任务若遇到旧式规划，把独立完整句中的“给出证据链接、无法确认的说明原因、不写文章”等明确回答指令移入回答要求。这个兼容规则只匹配有限的完整中文表达并检查上下文；混合项目句、嵌在工具功能中的词语或同时出现两种含义的原文不自动移除。相同原文同时归入两个范围的歧义会拒绝，避免静默丢失项目条件。旧已保存任务、回执及历史不会批量重写或自动重试。
