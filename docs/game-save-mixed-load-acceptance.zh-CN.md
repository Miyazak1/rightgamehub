# 存档与权威对局混合负载验收

日期：2026-10-07。关联 [存档设计](72-game-save-platform-infrastructure-design.zh-CN.md) 的 S3 与跨服务容量门槛。

本轮建立可复现的本地验收入口，并发现在线流量与数据库备份之间的资源争用。**这不是生产上线验收；productionReady 始终为 false，生产 cloudSave 继续关闭。** 本文中的延迟门槛是实验开始前声明的本地筛查值，不是已经承诺的生产 SLA。

## 复现

在安装好仓库依赖、Node 22 和使用 Linux 容器/cgroup v2 的 Docker Compose 的仓库根目录执行：

~~~powershell
node scripts/run-save-mixed-load.mjs --smoke
node scripts/run-save-mixed-load.mjs
node scripts/run-save-mixed-load.mjs --backup-uncompressed
~~~

三个命令分别是短冒烟、完整默认压缩备份、完整不压缩备份对照；逐个执行。脚本失败会返回非零退出码，具体失败检查保存在 report.json；备份恢复正确也不能抵消延迟或漏发失败。

脚本始终从当前工作树通过正式 Dockerfile 构建 API 与 Realtime。镜像标签、Compose 项目、数据库卷均使用随机项目名。只使用 [compose.mixed-load.yml](../deploy/compose.mixed-load.yml)，不能与生产 Compose 文件叠加。需要本机 55739、55790、55793 端口空闲，全部只绑定 127.0.0.1；不会连接、清空或迁移既有生产数据库。

随机测试密码和 OTP 密钥保存在被 Git 忽略的 .runtime/mixed-load/<project>/test.env；这是本地测试凭据，不应提交或分享。日志、每阶段请求时序、源码 SHA-256、镜像 ID、资源配置和验收报告也放在该项目目录。正常结束与可捕获失败时撤销测试 grant，以 60 秒等待停止该项目容器并检查退出码，保留卷和容器内 /tmp/mixed-backup-*.dump 供复查，不自动删除数据。强制杀死脚本时可能来不及清理，操作者应按报告里的准确项目名检查。

## 负载与资源

完整测试使用 16 个测试账号、4 场双人迷阵对局、64 MiB 不可压缩随机数据库背景正文。12 个账号使用 50 KiB 存档，4 个使用 256 KiB；背景正文是明确标记的独立测试表，不伪装成用户存档。

| 服务 | CPU 配额 | 内存上限 |
| --- | ---: | ---: |
| PostgreSQL（含 pg_dump） | 0.60 | 640 MiB |
| API | 0.65 | 384 MiB |
| Realtime | 0.50 | 192 MiB |
| Redis | 0.10 | 160 MiB |
| 只读磁盘探针 | 0.05 | 64 MiB |
| 周期维护（仅混合阶段） | 0.10 | 128 MiB |
| 合计 | 2.00 | 1568 MiB |

迁移进程在发负载前退出。启动维护后再次从 Docker inspect 检查实际配额；采样同时记录 Docker CPU/内存、PostgreSQL 数据库/WAL 大小与锁等待，以及 PG、Realtime、Redis 的 cgroup v2 CPU 限流计数。

本次 Docker 宿主可见 20 核、约 12.4 GB 内存，压测客户端运行在配额外的 Windows Node 进程。CPU 上限相加为 2 核**不等于**整机只有 2 核；不限制共享文件系统 IOPS、宿主页缓存或其他本机程序。不得把本结果推广成真实 2 核 4 GiB 线上机器的容量承诺。

| 阶段 | 时长 | 活动 |
| --- | ---: | --- |
| baseline | 40 秒 | 存档写入/读取、权威对局、心跳、磁盘探针 |
| mixed | 100 秒 | 同上；启动真实维护 CLI，每 25 秒启动一份 pg_dump |
| recovery | 40 秒 | 停止维护与新增备份，保持同一在线流量 |

每账号每 6 秒写一次、每 4 秒读一次；每场对局每秒一次行动，8 个连接各每 2 秒发心跳。按固定时间表错开发起，同一流最多一个在途操作；来不及发起的请求计入 missed 并使验收失败。对局结束后使用真实房间 API 新开一场，该调度槽不计为对局 ACK 样本。样本数和实际数量均在报告内。

冒烟缩为 4 账号、1 场对局、8 MiB 背景数据、12/30/12 秒；冒烟通过只说明链路可运行。

## 测量与正确性

- 存档使用真实 Bearer 认证、game session、CAS 与幂等回执。账号和服务审批只在新建测试库准备；没有开放生产审批。HTTP 读写均校验 SHA-256，最终读取还必须等于最后一次已确认写入的 ETag 与摘要。
- 对局使用仓库签名的迷阵规则、真实票据、Redis 协调与 WebSocket。机器人只根据玩家可见状态挑选合法动作；双方都须收到新修订并拥有相同的权威 stateHash。
- command 是发送动作到 ACK，fanout 是发送到双方快照到达；与 HTTP、心跳一样在客户端测量，包含本机网络转发开销。database 指标只是每 5 秒一次观察查询的往返耗时，**不是所有业务 SQL 的 P95/P99**。
- Realtime /metrics 新增最近一个完整 5 秒窗口的 event loop P99、最大延迟、窗口时间及 RSS。报告里的最大窗口 P99 不等于整个阶段的事件循环 P99，也可能漏掉两次抓取之间的窗口。客户端事件循环另行记录，用于判断发包机是否拥塞。
- 源库与从第一份混合阶段备份恢复的新库，分别检查当前指针、当前正文、所有保留正文摘要/长度、回执关系、容量计数、live/history 用量、对局事件序号，共 7 项不变量。恢复前再次核对备份 SHA-256。
- 最终脚本额外核对备份开始前**已收到成功回执**的存档修订和对局 command ID 都存在于恢复库，防止空库或不完整恢复仅凭“异常数为零”通过。源库所有成功回执/command ID 必须与客户端记录精确相等。
- 该并发备份检查未逐表比较整个数据库快照，不能替代 [独立完整恢复演练](../scripts/rehearse-save-database-restore.mjs)。账号登录交互、游戏 SDK/iframe、本机 outbox 和 Cursor 安装界面不在本次负载范围。

固定门槛（毫秒）：

| 测量 | P95 | P99 |
| --- | ---: | ---: |
| 存档写入 | 300 | 1000 |
| 存档读取 | 150 | 500 |
| 对局 ACK | 150 | 500 |
| 心跳 | 100 | 250 |

另要求双方快照 P99 ≤ 500 ms、采到的完整窗口 event loop P99 ≤ 100 ms；零请求错误、零漏发、无 OOM/重启、至少两份备份、维护实际执行、源库及恢复不变量全零、所有确认身份核对通过。单轮约三分钟、有限样本只适合发现阻塞，不能证明长期可用性或最大吞吐。

## 2026-10-07 实测记录

最终脚本复测默认压缩备份仍未通过，失败项为 mixed 的读取 P99、对局 ACK P99 与双方快照 P99，均超过 500 ms。基线与恢复阶段通过。没有放宽门槛，也没有将失败压测描述为已完成容量验收。

| 阶段 | 写入 P99 ms | 读取 P99 ms | 对局 ACK P99 ms | 双方快照 P99 ms | 心跳 P99 ms | 漏发 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline | 149.8 | 160.3 | 139.8 | 143.5 | 14.4 | 0 |
| mixed | 788.9 | 723.1 | 768.1 | 770.6 | 79.5 | 0 |
| recovery | 154.6 | 176.6 | 137.6 | 138.3 | 9.2 | 0 |

最终运行 gamehub-save-mixed-1791381087185-600ffd：497 份存档成功回执、709 个对局动作全部与数据库精确匹配；各阶段请求错误均为 0。源库与恢复库的 7 项异常计数均为 0。第一份备份开始前已确认的 123 份存档修订、159 个对局动作均存在于恢复库。维护执行成功 3 批，未发现异常、OOM 或重启。

混合阶段生成 4 份自定义格式备份，每份约 88.4 MB、耗时 11.7–12.1 秒；恢复首份，SHA-256 为 851a560494aadbb2b2d60d0ef386f3c6f13d9af742f0935e42d25b53efb18b21。这不是生产异地备份或 RTO 测量。

PG cgroup 的 throttled_usec 在 baseline/mixed/recovery 分别增加 0 / 39.18 秒 / 0；混合阶段 986 个调度周期中有 439 个发生限流。这是 cgroup 限流计数，不是业务查询等候时间。Realtime 完整窗口 P99 最大约 22.1 ms，压测客户端各阶段 event loop P99 约 34–35 ms。在线请求尾延迟与备份、PG 限流同时出现，停止备份后回落，支持存在资源争用的判断；尚未分离 CPU、I/O、数据库多次往返与锁竞争各自的贡献。

关闭压缩的对照也失败：mixed 写入/读取/对局 ACK P99 分别为 1382.0 / 1293.2 / 1306.4 ms，出现 11 次漏发。PG 限流增加 8.23 秒，备份缩短为 4.2–5.1 秒，但文件增至 156–159 MB。请求无错误，确认操作与恢复不变量正常。减少压缩 CPU 并未消除延迟峰值，不能据此直接修改生产备份策略。

早期默认压缩试跑也失败：mixed 读取/对局 ACK P99 为 634.5 / 730.1 ms，baseline 与 recovery 的对局 P95 也略超门槛。短冒烟曾通过，但使用早期门禁版本；它不包含最终新增的备份前确认操作保留检查，不能冒充最终版完整验收。

证据 JSON 只含指标、标识和摘要，未提交测试密码、Bearer token、玩家正文或数据库备份。负载报告中的 finalContainers 是停止前的状态，不能用它证明正常关闭。收尾检查发现旧版默认停止流程在检查点完成前终止 PG，退出码 137、OOMKilled=false。随后仅修改压测脚本的清理逻辑：停止等待 60 秒，检查停止后的退出码并把异常纳入失败门禁；负载与生产应用代码未变。报告保留当时的源码字节摘要，不改写为清理修复后的摘要。

[关闭修复验证](evidence/save-mixed-load-20261007/shutdown-verification.json) 记录重新打开本轮四个测试 PG、对各自源库和恢复库复查不变量，再以同一 Compose 命令正常停止的结果；该记录另附修复后脚本摘要。[首次复查记录](evidence/save-mixed-load-20261007/shutdown-first-attempt.json) 保留了一个旧库未在初设约 15 秒内就绪的结果，后续将恢复就绪等待延至约一分钟。最终所有本轮测试容器已停止，PG 退出码为 0，卷与容器内备份保留。完整仓库回归 375 通过、8 项环境条件跳过，合同校验通过；专项测试覆盖事件循环指标窗口、固定节拍漏发与门禁拒绝不完整/损坏证据。没有重复客户端安装验收。

## 尚未完成的发布条件

这轮没有竞赛 verifier 的真实实现，未以模拟 CPU 任务替代；也未覆盖源码/规则构建、全局后台任务调度、TLS/反向代理、生产磁盘与宿主、异地自动备份及生产 RPO/RTO。没有新数据库迁移，没有修改生产备份脚本或生产 cloudSave 开关。

下一步先落实后台重任务共享准入与备份资源隔离，保留在线数据库、Realtime 的预算；备份应在压力上升时推迟或降低资源使用，同时保证可验证的恢复点。随后以真实竞赛 verifier、构建任务和线上等价环境重复混合负载。仅修改压缩参数或将本地门槛放宽，不能视为此项完成。
