## 1. 方案是否够用

**足以启动开发。**13—19 已覆盖产品范围、宿主分工、数据和 API、上传隔离、Windows 分发、部署及验收。下一步通过小原型验证接口和限制，再据实修订；无需先扩写更多完整方案。

当前不等于具备上线条件，也不能承诺任意 EXE 在侧栏运行。以下问题须在各自模块实施前解决，不阻塞已确定部分：

| 问题 | 关闭条件 | 对实施的影响 |
| --- | --- | --- |
| 三宿主安装与生命周期 | 独立测试包、真实侧栏、关闭/隐藏清理、目标版本记录 | M0 必须逐宿主通过；Harness 结果不能代替 VS Code/Cursor |
| 插件内文件流与下载 | 本机/远程来源正确、真实进度、断点/校验、受限 Host 服务 | 未通过前不能称“全部在软件内完成” |
| 原生 EXE 功能区游玩 | 09/19 的画面、声音、输入、焦点、稳定性同时通过 | 尽早独立实验；可能只支持部分引擎或作者适配包 |
| Windows 安装器检查 | 扫描器选型、格式覆盖、扫描不完整时拒绝公开、容量实测 | 开放 Windows 投稿前必须完成 |
| 海外运行资源 | 域名、邮件、存储和扫描资源配置及实测预算 | 本地原型可先做，公开服务部署前确定 |

服务器和商业化不作为本轮原型前置；首版仍免费，统一后台加宿主扩展，继续使用宿主自己的更新渠道。

## 4. 方案中的一项落地修正

该 Harness 版本的客户端不是普通 ESM 文件：必须提供 `window.__ModuleLoader__.load({id,factory})` 工厂，外部 React 通过宿主模块表的 `require('react')` 取得。依据是本机官方 `packages/client/tsdown.client.ts` 与 `packages/client/modules/src/client/manifest.ts`，当前构建脚本已实现这一格式。

M0 使用随包自有 HTML 的 `srcdoc`，sandbox 只开 `allow-scripts`，无宿主桥、无任意外网、无持久存档。这只验证容器及交互。正式作品仍须执行 15—16 的远程独立域、发布网关、消息协议和安全头，不把演示容器当成 UGC 托管完成。

0.0.2 的文件控件只显示名称和大小，用户截图反映的是这一限制。0.0.4 已补齐真实本机文件传输，见下方记录；账号页面、发布后台和上传作品运行仍未接入。

## 5. 如何运行

本机双击项目根目录的 `start-gamehub-m0.bat`，等待 Harness 打印本机地址。浏览器访问该地址，跳过模型 Key 配置，打开右侧栏并选择“游戏大厅”。关闭测试在启动窗口按 Ctrl+C。端口 3081 需空闲，不同时启动两份测试实例。

默认使用用户已提供的 `E:\DEEPSEEKHARNESS`。其他电脑通过 `GAMEHUB_HARNESS_ROOT` 环境变量或启动参数指定已构建的官方源码位置：

```powershell
node scripts/start-harness-m0.mjs "E:/other/deepseek-harness"
```

修改插件源码后先执行 `npm run pack:harness`；发布测试更新时增加插件版本，避免包缓存歧义。测试包和 `.runtime` 均为本地产物，源码保留在项目中。

### 2026-09-24：修复双击 BAT 找不到 pnpm

首次验证继承了 Codex 提供的 pnpm 路径，用户从普通终端启动时出现“pnpm 不是内部或外部命令”。启动器现将 Harness 自己的 `node_modules/.bin` 和当前 Node 目录加入子进程 PATH，并统一 Windows 的 Path/PATH 键；不修改系统环境变量，不依赖全局 pnpm。错误也按依赖检查、包检查、安装、服务启动分别提示，避免所有故障都误报成“先构建包”。

回归方式：仅保留 Node 和 Windows 系统目录，先确认 PATH 中没有 pnpm，再通过 `cmd.exe /d /c start-gamehub-m0.bat` 启动。结果使用 Harness 本地 pnpm **11.7.0** 完成插件检查，服务成功监听 3081，使用本轮启动授权访问页面返回 HTTP 200。无授权请求返回 401，认证仍有效。

## 6. 紧接着的开发顺序

### 2026-09-24：补齐真实上传、下载与校验

当前“游戏大厅”可选择 ZIP/EXE 并点击“上传”，显示字节传输进度、服务确认结果和取消操作；成功文件进入持久列表。支持浏览器下载、HTTP Range，以及重新选择下载文件核对大小和 SHA-256。浏览器负责最终保存，点击下载不能记为保存完成。上传文件一律显示“未扫描 / 未发布”，不会解压或执行。

界面不再是文件选择探针。数据流是：可信插件 UI → Harness 已认证的 `connection.fetch` → 本机流式文件存储；不另开无认证上传端口，不借用聊天附件服务。默认 BAT 存储位置为 `.runtime/m0/gamehub-storage`，使用随机 ID 文件和独立元数据。单文件最多 500 MiB，已提交文件最多 2 GiB / 50 个，单实例串行接收，超时 30 分钟。仅用于单机试运行，尚无云存储、垃圾回收、跨进程写锁、作品 ACL 或扫描发布系统。

本轮验收：

- Harness 独立测试 profile 在 3082 运行，保留用户原 3081 实例；官方管理器安装插件成功，右侧功能区显示上传按钮。
- 在真实文件选择器中选择 `E:\GAME\桌猫.exe`，点击上传，页面显示“上传成功”及已上传文件 1 项。实际保存 **61,151,835 bytes**，不是模拟上传。
- 点击界面下载触发浏览器下载，但自动化未返回浏览器保存位置；另用已认证下载接口流式保存测试副本，再与原文件比对，大小和 SHA-256 全部一致；同一副本通过校验接口。未把浏览器下载事件误记为保存完成。
- SHA-256：`4967f9e183a311193f8b2f0fd33f5a40b8b2a1ff7a575c2d412b2e4640c69912`。
- 真宿主请求验证：未登录读取返回 401，携带其他 Origin 的请求返回 403。测试没有关闭宿主认证。
- 自动测试 13 项通过，其中新增 7 项覆盖流式持久化、重新打开存储、下载 Range/HEAD、内容篡改识别、非法名称/格式、大小与容量限制、取消/超时后清理和重试。测试源码为 [harness-transfers.test.cjs](../tests/harness-transfers.test.cjs)。
- 可重复的 HTTP 集成检查：[verify-harness-transfers.mjs](../scripts/verify-harness-transfers.mjs)。本地结果保存在 `.runtime/m0/transfer-check-report.json`，不记录会话凭据。
- 最终 0.0.4 已通过官方管理器安装到默认测试 profile 和独立验收 profile。重启验收服务后界面显示 `GAMEHUB · 0.0.4`、已上传文件 1 项；再次下载与校验通过，证明升级与重启未丢失文件记录。

本轮宿主的大文件响应曾输出 Gzip 的 `MaxListenersExceededWarning`；传输内容校验仍通过，但不据此宣称长期并发稳定性已通过。后续性能验收需检查宿主压缩与断开连接清理。

使用当前版本：在原 Harness 启动窗口按 Ctrl+C 停止旧实例，再双击项目 `start-gamehub-m0.bat`，启动器会安装当前包；重新打开/刷新游戏大厅，页头应为 `GAMEHUB · 0.0.6`。选择文件后点击“上传”，成功后下方列表可下载；网页 ZIP 检查通过后还有“开始游戏”。更新插件不删除已上传数据。
