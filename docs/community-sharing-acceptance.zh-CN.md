# 分享板块发布前验收（2026-10-08）

本轮完成受限资源混合负载，并在 Cursor 独立安装版中复现、修复投稿卡住的问题。首版代码已推送至 077b130，以下原始验收记录对应当时版本；后续默认开放投稿的验证与更新方式见文末。本文不作为生产部署完成证明；云存档继续关闭，评论未开放。

## Cursor 实装与修复

用户在“GameHub 分享安装版验收”窗口通过真实邮箱验证码登录，数据库记录客户端为 cursor。VSIX 连接独立的 127.0.0.1:3087 和 community_test 测试库，没有连接线上。

首次提交一直显示“保存草稿…”及“处理中…”，后台没有产生帖子或等待中的事务。原因是共享编辑器的 AbortController 在 React.StrictMode 的 effect 清理后被复用，已经取消的请求没有发出；catch/finally 又因取消状态跳过了错误提示和 busy 复位。

修复为每次 effect setup 创建新的控制器，cleanup 只取消该次控制器，提交过程捕获自己的 signal。浏览器用例改为实际宿主相同的 StrictMode；修复前稳定复现失败，修复后带图投稿→审核→公开→点赞→收藏通过。另注入一次 503，验证错误可见、按钮恢复、正文保留，重试复用同一幂等键。

修正版 VSIX 重装并核对安装目录的 bundle 摘要。用户重新加载窗口后确认“已提交，显示待审核”。其测试 PNG 为 400×400、107,263 字节，处理为 44,330 字节 WebP。通过本地管理员真实认证/API 审核，匿名公开读取及缩略图读取成功。后台已核对用户点赞 1 次、收藏 1 次、like_count=1；图片视觉显示和私人收藏页的最后一次人工确认仍待用户回复。审核是通过真实 API 操作，未冒充管理员界面人工验收。

原生窗口自动控制工具报 `windows sandbox failed: helper_unknown_error`，因此 Cursor 操作由用户配合，浏览器自动测试不冒充 Cursor UI 自动测试。Harness 仅完成构建验证。

## 受限资源混合负载

使用独立 Compose 项目、随机本地凭据和三个 loopback 端口。API、PostgreSQL、Redis、Realtime、worker、图片容器的 CPU 配额总计 2.0 核，内存上限总计 2,144 MiB；图片容器为 0.5 核/256 MiB、无网络、只读根文件系统。宿主 Docker VM 本身有 20 核和约 11.6 GiB 内存，因此这只是各服务配额之和，并非完整生产机器隔离。

16 个测试账号、4 场实际签名规则联机；基线 40 秒、混合 120 秒、恢复 40 秒。每账号每 4 秒读列表、每 5 秒读详情和缩略图、每 12 秒切换一次点赞/收藏；每场每秒发一条实际合法指令，8 个联机客户端每 2 秒心跳。混合阶段另有 4 条图片任务流，每 24 秒一轮，共 20 次完整创建草稿、上传、处理、提交审核、批准。输入 JPEG 分别为 1600×900/172,192 字节及 4000×3000/1,428,277 字节。

完整运行通过预先定义的 59 项本地检查。无请求错误、定时负载漏发、非预期 WebSocket 错误、OOM 或容器重启；640 次缩略图读取成功。所有已确认指令身份均在数据库中，点赞计数、公开修订、媒体归属、资产完成状态、联机事件序列均一致，云存档行数为 0。全部压测容器正常停止，测试卷保留用于审计；独立的 Cursor 本地验收服务仍保留供查看。

各容器 cgroup 内存峰值相加约 462.2 MiB，其中图片进程所在容器 71.5 MiB。峰值发生时间不同，这个和不是整机实测峰值，也不包含系统、代理、runtime 和其他生产服务。采样到的实时事件循环窗口 P99 最大为 79.2 ms。

保留失败记录：第一轮在准备阶段因 Node 未引用的 fetch 超时/连接导致顶层 await 提前退出，未开始负载，已停止该轮容器；脚本补充运行期引用并消费 readiness 响应后重跑。短测（4 账号/1 场，12/30/12 秒）无功能错误，但指令 P95 及一次互动 P95 超门槛，明确判为不通过。完整负载使用相同门槛，未为通过而放宽。短测抖动仍说明上线后应观察冷启动与尾延迟。

复现命令：`node scripts/run-community-mixed-load.mjs --smoke` 或不带参数运行完整负载。门槛见 `scripts/community-mixed-load-gate.mjs`；云存档测试共用工具默认行为不变，分享测试显式传入 cloudSaves=false。

## 正常登录用户默认投稿（2026-10-08 后续调整）

用户明确要求“正常登录用户都能投稿，内容审核通过后公开，保留限额和封禁机制即可”。本次移除逐账号授权和公开个人主页的投稿前提：正常账号无需 community_members 记录，私密主页账号也能发布分享；编辑器说明昵称与内容审核后公开，私密主页不返回跳转 handle。新内容和修改仍逐版本审核，草稿、待审正文和附件不会提前公开。

原有显式 posting_allowed=false 记录作为投稿限制保留。管理员入口改为“投稿限制管理”，可限制或解除限制并记录理由；后端对创建、编辑、提交、图片预留、上传和上传完成统一校验，和限制操作使用同一用户事务锁。受限用户仍可查看、撤回和删除已有内容。账号封禁、双向屏蔽、每日提交 10 次、每人待审 3 条、全站待审 200 条及原图片额度保持有效。

新增 0051_community_open_posting.sql，不修改已执行迁移。旧修订保留依赖主页隐私的 profile 策略；新修订采用 post 策略。旧待审内容由管理员批准后仍遵守旧隐私。作者主动提交旧草稿时才复制新修订，复用已有图片引用，再经过审核公开。迁移不修改个人主页、历史限制或审核记录。

验证包括无白名单的私密主页账号图文投稿、审核前不可读、审核后列表/详情/图片可读、点赞/收藏、限制与解除、限额、账号停用、50→51 带历史数据升级及幂等重跑。平台回归和客户端回归的实际计数、源码与构建包摘要见 [默认投稿验证记录](evidence/community-sharing-20261008/open-posting-verification.json)。浏览器继续使用 StrictMode，覆盖 503 重试及管理员限制操作；版本为 VSIX 0.3.30、Harness 0.1.12。

保留测试过程中的失败：升级测试夹具最初重复使用同一 SQL 参数写入 integer/bigint 列，已补显式类型转换；全量测试发现旧迁移数量断言仍为 50，已更新为 51。并行运行的浏览器与后端测试曾共用数据库而使用不同图片目录，图片被另一处理器领取导致失败；两类测试现改为每次创建、清理独立临时数据库，再验证通过。上述变化不重置用户正在使用的测试库。

本轮未重复整套混合负载，文中 59 项压测结论仍对应原报告源码；新版安装包完成构建，本轮不冒充 Cursor/Harness 人工安装验收，也不宣称已部署生产。
