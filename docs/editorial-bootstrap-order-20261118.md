# 新版工作流登记与调度器收尾

生产更新 `650d2e26` 已通过统一发布与主程序验收，随后在额外调度器校验阶段退出。调度器日志明确报告 `AGENT_BLOG_PUBLIC_RUNTIME_WORKFLOWS_NOT_READY`，因此无法保持运行。

旧脚本在 API、调度器均执行源码检查后，才进入调度器容器执行 bootstrap。新版公开工作流 v3 尚未登记时，调度器启动准入拒绝并退出，形成“等待调度器启动才能登记、等待登记才能启动”的循环依赖。

修复只涉及主机侧发布控制：

- 先核对健康 API 的源码哈希与论文关闭状态，通过 API 容器登记工作流。
- 登记失败即停止，不进入调度器、不恢复计划。
- 登记后再处理调度器；只对已处于 restarting 状态的进程执行一次 restart，正常运行的进程不重启。容器可进入性采用有限等待，失败保留诊断日志。
- 调度器源码、论文开关均校验后，才运行现有幂等恢复计划命令，不请求立即发文或补发历史任务。
- `MOOYU_RELEASE_FINISH_ONLY=true` 用于此次已激活版本：不读取统一包、不构建镜像、不备份或迁移数据库、不重启主站。只允许快进安装主机脚本、测试和文档；如发现业务代码、配置或 schema 变化则拒绝，现有业务字节仍须与目标提交一致。
- `.env.prod` 仍备份并核对哈希；记录所有阶段、退出码和服务日志。

验证：`tests/platform/editorial-release-control.test.cjs` 在隔离临时仓库和 Bash/Docker 替身中执行六个场景：正常登记、仅收尾、已运行调度器、登记失败、源码不符、包含业务变化的收尾请求。确认 API 登记先于任何调度器 exec，拒绝路径不恢复计划，配置与历史材料保留。

全量报告 `.runtime/editorial-bootstrap-order-full/result.json`：373 个测试文件，1637 项通过、0 失败、95 项按环境跳过。专项报告为 `.runtime/editorial-bootstrap-order.tap`。

机器人 API、工作流定义、数据迁移、预算和客户端代码相对于 `650d2e26` 未改动；原有真实数据库/实际模型的发文和幂等验收仍对应相同业务代码。本次额外覆盖的是此前缺失的冷启动发布控制顺序。
