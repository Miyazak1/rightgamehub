# 公开文章引用编号越界修复

## 生产证据

2026-11-16 用户提供的只读结果显示，运行 `5d934abc…` 的 freeze-input、collect-evidence、select-subject 均成功，compose 因 `AGENT_BLOG_COMPOSITION_CITATION_INVALID` 失败，后续阶段取消。选题原候选编号为 `[2]`，实际所选来源只有 1 个；模型部分段落却使用了 `[1,2]`、`[1,3]` 和 `[3]`。

这与先前的日期归档错误不同：本次已完成证据采集，错误发生在文章引用归一化。写作请求原本同时携带原候选编号与重新从 1 编号的已选来源，提示词也没有明确区分仓库来源编号和同仓库多项资料的编号，存在混淆空间；不能从编号反推模型具体如何产生了错误。

## 修改边界

- 写作提示词升级到 `blog.article.compose@3`，显式传递 `citationContract.allowedIndexes`，说明引用对应 `verifiedSources.sourceIndex`；同一仓库的多项资料共用该来源编号，单来源只能引用 `[1]`。
- 写作请求移除原候选 `selectedIndexes` 和内部资料 UUID；原始选题记录及最终审计产物仍完整保留，不改写历史。
- 公开文章的引用校验失败时，最多追加一次模型纠正，使用原已选资料和原错误草稿。纠正使用单独的 action/idempotency key，仍经过原模型网关、权限与预算准入，保留两次原始输出和实际费用。
- 写作第一次调用时限 480 秒，纠正 90 秒，沿用原 compose 阶段 600 秒及现有 token/call 预算。预算不足直接拒绝，不扩大配额；影子验收仍保持原精确调用次数要求。
- 纠正后重新执行所有原有校验，仍有越界、缺引用或其他错误则停止，不保存可发布文章，不自动把错误编号映射成来源 1。
- 写作输入使用规范 JSON 文本，避免 PostgreSQL JSONB 重排字段后，同一纠正请求的幂等摘要发生变化。

运行详情卡片会缓存已展开的阶段，列表刷新不会同步重取展开详情；因此截图中的“采集运行中”不是这次数据库的最终状态。整页刷新后可重新读取阶段。本次修复仅涉及服务器写作逻辑及测试，不改动桌面端和插件包。
