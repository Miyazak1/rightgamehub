# 从平台启动普通 EXE（独立窗口）

日期：2026-09-24 · 插件：0.0.12 · 状态：代码与 73 项自动测试通过；用户随后确认启动成功 · [目录](./README.md)

**后续用户反馈（2026-09-24）**：“我启动错版本了。现在 OK 了，测试能启动。”据此将当前体验更新为用户确认启动成功。下面的自动测试及 build-report 记录的是此前助手执行的验证，仍保留其“未运行真实 EXE”的事实，不改写历史证据。此反馈不代表所有 EXE 兼容或通用侧栏运行通过。完整平台设计和任务交接见 [27](./27-platform-design-and-handoff.zh-CN.md)。

## 已确认的体验

用户已接受普通 EXE 由平台按钮启动，并在独立游戏窗口游玩。平台现在采用两个入口：网页游戏和侧栏适配包在右栏游玩；普通 EXE 下载到本机后，点击平台内的“启动（独立窗口）”。不需要玩家自己寻找下载文件。

这一确认改变了普通 EXE 的产品形式，不会把以前的窗口捕获实验变成已通过的侧栏方案。真正标注“在右栏游玩”的能力，仍须满足对应的画面、输入、焦点和无独立窗口要求。

## 使用方法

1. 双击 [start-gamehub-desktop-test.bat](../start-gamehub-desktop-test.bat)。它构建并安装 0.0.12，使用独立 **3085 / gamehub-desktop-check** 配置，不自动打开浏览器或执行游戏。
2. 打开控制台输出的登录链接，在 Harness 右栏进入游戏大厅，确认页头 `GAMEHUB · 0.0.12`。
3. 上传单文件 EXE，在该文件卡片点击“下载到本机”。文件写入平台管理的目录，进行大小、SHA-256 与基本 PE 格式检查；此时不执行程序。
4. 下载完成后，点击“启动（独立窗口）”。平台再次校验副本，直接启动它。安装包会打开其安装向导，平台不会替用户确认安装或自动提权。
5. 在游戏自己的窗口退出。关闭、隐藏平台右栏或停止 Harness 服务不会终止独立游戏。右栏每 3 秒更新仍在跟踪的入口进程状态；启动器退出不代表它创建的游戏子进程也结束。

“下载文件”仍是浏览器另存为入口，和上述平台管理的本机下载分开。这个版本的服务与玩家必须按同机方式使用：程序运行在 **Harness 服务所在的电脑**。未来接入云端平台时，需要玩家本机扩展负责下载与启动，不能把此后端直接部署到云服务器来启动玩家的程序。

普通启动默认不开启 EXE 执行能力。新 BAT 显式设置 `GAMEHUB_DESKTOP_LAUNCH=1`，清除历史窗口捕获及离屏样本配置；不用安装独立 Electron 运行时。此前 3081—3084 测试服务及其文件没有被替换。

## 当前支持范围

| 类型 | 本轮行为 |
| --- | --- |
| 单文件 Windows GUI EXE | 下载、校验、用户点击后从平台启动；实际兼容性仍需逐程序验收 |
| 图形界面的 EXE 安装器 | 可尝试打开安装入口；不自动安装，也不记录安装完成后的游戏路径 |
| 依赖同目录 DLL/资源的多文件游戏 | 单独上传 EXE 不足以运行；本轮没有便携 ZIP 解包启动功能 |
| 控制台 EXE、DLL、驱动、非 PE 文件 | 当前 GUI 启动入口拒绝，普通文件下载保留 |
| 网页 ZIP / 侧栏适配包 | 保留既有右栏流程；不走此 EXE 启动接口 |

基本格式检查接受 x86/x64/ARM64 的 PE32/PE32+ 桌面图像标识，最终架构和依赖兼容性由 Windows 决定。检查依据 [Microsoft PE 格式说明](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)，不是完整加载器、病毒扫描或安全认证。

## 实现约束

- [desktop-launcher.mjs](../extensions/harness/src/desktop-launcher.mjs)独立于历史捕获桥和离屏运行组件，不捕捉桌面、不操作系统键鼠、不改挂窗口。
- 下载缓存为 `<GAMEHUB_STORAGE_DIR>/desktop-downloads/<文件 UUID>/game.exe`；本次默认位于 `.runtime/m0/gamehub-desktop-check-storage`。启动目标由后端根据已上传记录确定，页面不能传路径、参数或命令。
- 流式下载到随机临时文件，完成大小和 SHA-256 校验、检查 PE 文件头后提交。准备阶段可取消、超时；不会自动执行。每次启动再次验证缓存；副本被改动时要求重新下载。
- 明确重新下载只替换受管理的 `game.exe`，不递归删除整个目录，保留游戏可能写入的其他存档文件。重命名为固定 `game.exe` 可能影响依赖原始文件名的程序，此类程序暂不保证兼容。
- 新接口为 `POST /api/gamehub/desktop-prepare?id=…` 与 `POST /api/gamehub/desktop-launch?id=…`。继承 Harness 认证和 Host/Origin 检查，要求客户端标记；启动还要求 `X-GameHub-Launch: independent-window-v1` 与随机 UUID 请求标识。不允许 GET 启动、请求正文、额外 URL 参数或未知文件 ID。
- 启动请求在本次服务进程内按请求 UUID 去重，相同请求返回原结果，不重新执行；正在运行的同一入口进程也拒绝新启动。最多保留 1000 个请求，达到限制要求重启服务，不偷偷丢弃旧请求后重新执行。
- 使用绝对 EXE 路径、空参数数组、`shell:false`、独立进程和忽略的标准流；只隐藏额外控制台，GUI 窗口由游戏自己创建。收到 Node 的 `spawn` 事件仅代表入口进程已创建，不能宣称已进入可玩画面。进程与父服务的分离机制依据 [Node child_process 文档](https://nodejs.org/api/child_process.html#optionsdetached)。
- 不向游戏继承 Harness/模型密钥、`NODE_OPTIONS`、代理或开发工具环境；仅保留必要 Windows 用户目录和系统目录变量。这不构成原生程序沙箱，程序仍具有当前用户权限，界面明确提示只启动信任的文件。
- 不请求管理员权限、不调用安装静默参数、不自动重试失败或结果不明的启动。若网络断开时程序已经启动，界面提示先检查独立窗口；平台不会因页面卸载而杀掉游戏。

本机 EXE 缓存另有 2 GiB / 50 个受管理 EXE 的上限，与上传存储配额分开。此额度不包含游戏自行写入的其他文件；尚未提供清理下载、存档备份、崩溃残留回收和跨服务进程写锁。不要让两个服务同时使用同一存储目录。

服务重启后不自动启动，需手动重新校验或复用已有副本。重启也会丢失入口进程跟踪和请求去重记录；原游戏可能仍在运行，因此用户再次启动前需先检查游戏窗口。尚无进程树管理、强制结束、更新或卸载功能。
