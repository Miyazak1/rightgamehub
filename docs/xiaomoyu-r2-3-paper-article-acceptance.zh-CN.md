# 小墨鱼 R2.3：三篇真实论文闭环验收

状态：验收编排代码完成，等待生产环境选择三篇真实开放论文执行。

范围：只验证“发现/收件 → 全文解析 → 语义分析 → 私有科普草稿 → 引用回跳”。

明确不做：自动选题、定时运行、公开发布、桌面端 UI

## 1. 为什么需要这一关

R2.2 已经能把一个 `analysisId` 写成私有科普草稿，但单次成功不能证明系统可重复工作。R2.3 要求一次提交三个不同的真实 arXiv 论文分析，逐篇生成私有草稿，并把完整链路压成一份不可变验收收据。任何一篇不满足门禁，整组都不通过。

这不是新建第二套论文机器人。验收器只编排现有论文发现、研究执行、语义分析、通用 Agent 运行时和博客草稿能力。

## 2. 验收门禁

### 输入论文

- 必须恰好三个不同的 `analysisId`；
- 三个分析必须对应三个不同的论文身份、论文版本和 arXiv ID；
- 来源必须是平台发现队列中的真实 arXiv 候选；
- 研究执行、发现运行和队列状态必须全部成功/完成；
- 全文访问级别必须是 `fulltext-open`；
- 解析质量必须是 `trusted-text`，且允许分析、引用和对比；
- 必须有页级证据、语义发现和证据关系。

### 私有草稿

- 工作流只能是 `paper.article.draft-shadow@1`；
- 五个阶段全部成功，无重试、失败或不确定动作；
- 每篇恰好一次论文分析读取和一次模型生成；
- 草稿状态必须是 `draft`，修订状态必须是 `working`；
- 不得出现发布动作、发布事件或发布收据；
- 组合产物必须指回对应的分析和论文版本；
- 每个事实段落/列表必须绑定唯一论文引用；
- 引用 URL 必须是同一论文的 arXiv 地址，并带页码定位。

## 3. 生产执行

先在后台通过论文发现/收件和研究执行，取得三个已经完成语义分析的 UUID。然后在服务器仓库目录执行：

```sh
cd /www/gamehub/deploy
./agent-blog-public-ops.sh paper-accept ANALYSIS_ID_1,ANALYSIS_ID_2,ANALYSIS_ID_3
```

命令会：

1. 核对并注册已评审的工具、模型和工作流；
2. 在任何模型调用前检查三个来源是否真实、开放、不同且证据完整；
3. 顺序生成三篇私有草稿，避免单服务器同时抢占资源；
4. 读取数据库中的运行、证据、草稿和发布边界；
5. 写入 `agent_paper_article_acceptance_reports` 不可变收据；
6. 仅当整组通过时退出码为 `0`。

重复使用同一个 `AGENT_PAPER_ARTICLE_ACCEPTANCE_REQUEST_ID` 会复用同一组运行和收据；输入或结果漂移会失败，不会悄悄覆盖。

## 4. 通过标准与后续

通过后仍然不会自动发布，也不会创建论文定时计划。下一步才是 R2.4：在保留人工可见治理边界的前提下，设计论文候选竞争、去重、节流和公开发布策略。

桌面端 D1 在生产环境真实执行本验收并修完暴露的问题后启动。D1 是可安装、可登录、可看任务、可调用本地能力、可更新的最小图形产品；当前已有的 Windows 执行与更新代码仍只是安全运行内核，不等同于桌面端已经交付。
