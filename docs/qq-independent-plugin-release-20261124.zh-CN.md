# QQ 独立插件完整发布与验收

本包准备了发布文件和宝塔终端命令，尚未执行线上部署。不能将本地通过或部署安装完成写成真实 QQ 收发、手机确认登录或线上故障恢复已验收。

## 宝塔操作顺序

1. 执行 `server-create-upload-directory.txt`，创建全新的 `/www/backup/gamehub/qq-independent-plugin-release-20261124-r1`。
2. 将 `qq-independent-plugin-20261124-r1.tar.gz` 和同名 `.sha256` 两个文件上传到该目录。
3. 执行 `server-update-and-enable-guardian.txt`。它核对固定归档校验值、内部清单、镜像标签冲突及现场；复用经过 SHA 和版本验证的私有 Node 22，不改旧 Node 权限。
4. 命令在新维护记录中先准备回退入口和禁用状态的守护器，校验 systemd 单元，再停止 QQ worker 和 API，留出 70 秒鉴权冷却。数据库和登录网关保持运行。
5. 创建并完整解码校验新的 API/QQ 数据库备份及登录卷归档。两应用写入入口已停止，但不宣称所有数据库写入者均停写，也不宣称跨库原子备份；登录卷归档明确为在线备份。
6. 依次启动新 API、QQ worker、Web，核对配置、权限/计划/历史、旧锁及状态采样持续推进。然后安装守护器，执行一次健康/no-op 检查，再启用定时器并检查实际启用状态。

正常过程会有 API/Web/QQ 回复维护窗口；现有 QQ 登录网关及数据卷持续保留。命令不自动重试，失败会打印阶段、错误码和新维护记录路径。停止后未完成切换时，使用该记录的 `rollback.sh` 或随包的回退命令，不要再次运行上传/解包命令。

完成标记：`QQ_INDEPENDENT_DEPLOYED_GUARDIAN_ENABLED_ACCEPTANCE_PENDING`。`qqApplicationReady=true` 表示当次实际状态为已登录、账号/群匹配及消息连接正常；若为 false，应按状态继续扫码/恢复验收，不能冒充已经收发通过。

## 自动恢复的边界

- 每 20 秒检查一次 worker 已有控制快照，不新建 NapCat 管理客户端，不依赖网站 API 进程。
- 只有新鲜快照明确指出原生登录恢复失败，且至少 3 个不同采样持续 60 秒，才允许处理。API 不可用、查询超时、群查询失败、正在正常等待扫码及已经登录均不触发网关重启。
- 同一故障只处理一次；恢复后需连续健康 10 分钟才允许新故障处理，两次尝试至少间隔 15 分钟，滚动 24 小时最多 2 次。动作前持久化计数，进程中断不能清掉预算。
- 重启前后均核对同一容器、镜像、配置、登录卷、账号及群；先校验备份并确认没有发送中消息。停机备份失败也会尝试启动原容器；中断有一次只启动补偿，继续失败转人工复核。
- service 使用 `Requisite=docker.service`，不启动或重启 Docker daemon，从而不借恢复 QQ 操作其他容器。未知锁、未知配置或未知会话状态不被自动删除/改写。
- 新发布器及未来生成的 GitHub 更新器留下带 PID/进程启动标识的维护租约。守护器只回收已证明死亡的本协议租约；历史未知锁继续保留。
- 不删除登录数据、不自动请求密码、不自动生成一串二维码、不修改白名单，不恢复数据库、不重试历史任务、不自动重发结果不确定的消息。

私有状态目录为 `/www/backup/gamehub/qq-independent-guardian-20261124-r1`。配置和恢复计数保持 root 私有；归档及摘要均保留。到达上限或身份/备份验证失败时查看错误，不通过清空状态文件重置次数。

## 更新后的真实验收

先刷新后台，核对群号和原白名单保留。由原来已允许的账号在原群发送一条新消息：

```text
@小墨鱼 QQ独立插件验收20261124R1 请只回复：QQ通道验收成功
```

等看到实际回复后，执行 `server-check-status-and-new-message.txt`。它只读取这次部署完成后、带该标记的新消息，要求 QQ 远端发送确认及预期回复已经投递；“任务已保存”的受理通知、旧成功任务、只生成未发送的回复都不能算通过。期望结果：`QQ_NEW_MESSAGE_ROUNDTRIP_CONFIRMED`。

执行 `server-check-scan-entry.txt` 检查扫码入口。已登录时应返回 `ALREADY_LOGGED_IN_QR_GUARD_CONFIRMED`，保留当前登录；确需登录时返回 `QR_READY_USE_WEB_UI`，到后台显示二维码并在手机确认，再重复状态/新消息验收。终端不打印二维码内容、密码、令牌或原始登录错误。

恢复方面，部署命令验证真实 systemd 定时器启用、真实守护器可读取 worker 快照及持久状态；故障判断、备份、熔断、中断补偿和扫码恢复链路另由本地隔离故障演练验证。没有在生产伪造掉线或清空当前登录。真实异常发生时，可从守护器状态、恢复备份和新消息确认继续核验；不能把“定时器已启用”写成线上真实故障已经恢复过。

## 回退

新维护记录的 `rollback.sh` 使用本次验证过的私有 Node 和原完整 Compose 链。只停用本包拥有的恢复定时器、等待当前恢复动作结束，再回退 API/Web/QQ worker 镜像；不重启网关、数据库、桌面或调度器，不还原数据库、不回放任务，不删除新增历史。

守护器确实完成过的同一网关容器重启，可通过其持久记录被回退检查识别；其他未知服务漂移继续阻断。回退保留新私有配置、计数、备份和维护记录，停用新增单元；旧锁定记录不变。回退后的旧 worker 不具备本轮全部稳定性修复，仍需验收实际 QQ 状态。

## 本地验证类型

包括实际 API/worker 镜像内测试、隔离 PostgreSQL 权限/业务回归、实际生产 Web bundle 的桌面/手机和二维码恢复入口、真实 Compose 三服务更新/回退及受保护模拟网关/卷保留，以及宿主恢复策略的私有文件和 tar 校验。测试组有重叠；真实腾讯登录与生产收发不在本地模拟中冒充通过。完整数字和镜像 ID 在包内 `proofs/`。
