# GameHub 开放游戏计划：免费体验、作者增长与社区共建策略

状态：战略基线 1.4（来源与认领已上线；发现页开放属性与固定版本展示已进入发布候选）
更新日期：2026-10-10

## 1. 文档目的

本文定义 GameHub 如何以开放游戏为内容基础，为玩家提供免费、低门槛的游玩体验，同时把曝光、反馈和贡献机会带回原作者，并以此形成平台的长期推广与增长策略。

本文讨论的是**开放游戏生态与开源精神**，不是要求 GameHub 平台自身代码开源。平台代码采用何种许可证、是否公开，以及平台商业化方式，均属于独立决策，不影响本计划成立。

## 2. 核心定位

> 让玩家在“发现”中遇见更多可以直接玩的好游戏，同时让每款游戏的发布来源和作者关系都清楚可信。

GameHub 不是代码仓库的替代品，也不是未授权的游戏搬运站。代码、Issue 和 Pull Request 继续由原仓库承载；GameHub 负责降低体验门槛、组织可信信息、提供安全运行环境、帮助作品传播，并将反馈与贡献重新连接给原作者。

平台的差异化不是“拥有最多游戏”，而是同时做到：

1. **免费体验**：玩家不需要理解仓库、安装依赖或配置环境即可开始游戏。
2. **来源可信**：作品展示作者、原仓库、许可证、固定 Commit 和平台构建信息。
3. **作者受益**：平台流量能够转化为作者曝光、反馈、赞助和贡献者。
4. **参与递进**：用户可以从试玩开始，逐步进行反馈、测试、翻译、设计、代码贡献或 Remix。
5. **长期开放**：免费游玩是基础承诺，增值服务不破坏公开作品的基本可访问性。

## 3. 用户价值

### 3.1 玩家

- 免费发现和体验有趣的独立游戏、实验作品与网页 3D 项目；
- 无需下载源码、安装工具链或阅读复杂 README；
- 能判断作品来源、作者和开放许可；
- 可以收藏、分享、提交反馈或参与挑战；
- 愿意进一步参与时，可以看到清晰且低门槛的贡献入口。

### 3.2 开放游戏作者

- 获得可直接游玩的作品页和稳定分享链接；
- 保留显著署名、原仓库链接、许可证和版本来源；
- 获得曝光、启动、有效试玩、复访、收藏与反馈数据；
- 可以认领作品、修改介绍、控制同步、暂停发布和请求下架；
- 获得玩家反馈、测试者、翻译者、设计者和开发贡献者；
- 可以展示个人主页、赞助入口和其他作品。

### 3.3 共建者

- 从试玩后的真实问题进入贡献，而不是先理解整个代码库；
- 找到适合新人的测试、翻译、美术、文档或开发任务；
- 将贡献记录沉淀到公开资料；
- 创建保留来源、许可证和修改说明的 Remix。

## 4. 产品位置：发现中的统一游戏目录

开放游戏仍然是游戏，不建立脱离主产品的“开放游戏馆”，也不放入社区作为内容分类。三个一级区域的职责必须保持清楚：

- **发现**：面向所有玩家的公共游戏目录、专题、推荐和筛选；
- **游戏库**：具体玩家已经收藏、安装或玩过的个人游戏集合；
- **社区**：围绕游戏发生的讨论、活动、组队、反馈和共建。

“免费游玩”“开放源码”“可二创”“可自托管”“浏览器即玩”是发现中的属性、筛选条件和运营专题，不是另一套游戏实体。所有游戏继续使用统一的游戏卡片、详情页、启动入口和收藏动作。

每款公开游戏都必须同时记录“进入平台的方式”和“当前权益关系”，不能把上传者自动等同于作者：

- `ingestion_method`：`zip_upload`、`github_import`，官方内置内容在公开接口中显示为 `platform`；
- `attribution_kind=publisher`：作者、团队或合法发布者自己上传/导入；
- `attribution_kind=community_catalog`：平台代为上传或导入的公开项目，等待原作者认领。

因此，同一款游戏可以是“ZIP 上传 + 社区收录”，也可以是“ZIP 上传 + 发布者自有”；GitHub 导入同样可能属于发布者本人或平台代收录。详情页统一展示运行方式、进入平台方式和权益状态。存在源码仓库时再展示仓库、许可证和版本来源；没有仓库时明确写明“没有关联 GitHub 仓库”，不因此降低其作为游戏的可发现性。社区收录的游戏显示认领入口，发布者自有游戏则显示既有发布关系。

## 5. 内容供给策略

### 5.1 首批内容规模

正式对外推广前，优先准备 **10—20 款精选作品**，不以批量收录为目标。首批作品至少覆盖：

- 无构建步骤的 HTML/CSS/JavaScript 游戏；
- 使用固定构建模板的现代 Web 游戏；
- 一款视觉表现突出的网页 3D 作品；
- 一款轻量多人游戏；
- 一款适合 Agent 场景的互动作品；
- 一款具有明确新手贡献任务的共建案例。

从中选择三款作为完整示范案例，分别展示“导入即玩”“受控构建”“从试玩到贡献”的端到端流程。

### 5.2 入选标准

首批精选应满足：

- 核心玩法完整，打开后能在短时间内理解；
- 加载、输入、声音、存档和移动端边界明确；
- 许可证清晰，素材来源能够核对；
- 原作者和仓库真实可追溯；
- 当前版本通过平台安全校验和人工体验；
- 有可用于截图、录屏和社交传播的视觉记忆点；
- 作者仍活跃，或平台获得明确的展示与托管授权。

### 5.3 获取方式

按信任程度采用以下顺序：

1. 作者主动发布；
2. 平台定向邀请作者并获得确认；
3. 社区成员推荐，平台联系作者；
4. 许可证允许的公开策展，但必须标记“未认领”，保留认领和下架入口。

不以爬取数量作为增长目标，不把“公开仓库”直接等同于“允许平台托管、修改或再分发”。

## 6. 作者优先与开放治理原则

### 6.1 必须遵守

- 没有许可证或授权依据的仓库，不直接托管其构建产物；
- 保留版权、作者署名、许可证、原仓库和来源 Commit；
- 未认领项目不得暗示为官方版本或平台自有作品；
- 平台修改过的代码、资源和配置必须披露修改范围；
- 作者可以认领、纠错、停止同步、暂停展示和申请下架；
- 自动构建或同步失败不得覆盖上一稳定版本；
- 反馈回流、Issue 草稿和仓库写操作必须经过明确的用户或作者确认；
- Remix 必须保存来源链、适用许可证和修改说明。

### 6.2 作者关系

平台应提供：

- 作者认领和身份校验；
- 作品介绍、封面、分类和版本控制；
- 私有数据看板；
- README “在 GameHub 免费游玩”徽章；
- 可复制短链接、分享卡片和嵌入入口；
- 可控的反馈收件箱与 GitHub Issue 预填；
- 个人主页、赞助链接和其他作品展示；
- 清晰、可响应的纠错与下架流程。

### 6.3 认领机制先行

首期不以“已经有真实作者完成认领”作为发现页上线前提，但每款游戏都必须进入统一来源机制。用户上传自己的 ZIP 或导入自己的 GitHub 项目时默认具有发布者关系；平台代为上传或导入的开源项目标记为 `community_catalog` 并显示认领入口。认领流程必须可审计、默认不授予权限，并为后续作者进入平台保留可信入口。

认领状态建议为：

```text
publisher（发布者直传或导入）

community_catalog
  → unclaimed（未认领）
  → pending（待验证）
  → verified（已认领）
  → suspended（认领暂停）

pending → rejected（未通过）
pending → cancelled（申请人撤回）
verified → disputed（存在争议）
disputed → verified / revoked（恢复或撤销）
```

首期机制要求：

1. 每款游戏明确显示平台官方、发布者直传、GitHub 导入或社区收录状态；
2. 只有社区收录且未认领的游戏提供“我是作者/维护者”入口；
3. 申请人必须登录，提交身份、与游戏的关系和公开证明；有仓库时可使用 GitHub App，无仓库时可使用官网、作者主页、商店发行页或其他公开证据；
4. 优先使用强证据验证，但 GitHub 不是认领资格的必要条件；
5. 自动证明不足时进入人工复核，不允许仅凭同名账号、公开邮箱或自述直接通过；
6. 申请处于 `pending` 时不授予作品编辑、同步、发布或下架权限；
7. 只有 `verified` 状态可以管理作品介绍、封面、同步策略、版本和下架；
8. 组织仓库要区分组织所有权、仓库管理员和普通贡献者，普通贡献记录不能证明控制权；
9. 每次申请、证据摘要、审核决定、权限变更和撤销都写入只追加审计记录；
10. 作者可以撤回认领，平台也可以在授权撤销、仓库转移或争议出现时暂停权限；
11. 作品下架申诉与作品认领分开处理，权利人无需先成为平台作者才能提出下架请求。

已实现的数据边界：

- `works.ingestion_method`：记录 ZIP 上传或 GitHub 导入；
- `works.attribution_kind`：独立记录发布者自有或平台代收录，避免把上传动作误当成作者证明；
- 迁移对既有作品只采用安全默认值 `publisher`，不会根据管理员身份、上传方式或是否存在仓库自动推断作者关系；社区收录必须由管理员依据授权和公开证据逐款确认；
- `project_claims`：作品、申请人、证据类型、可选 GitHub 仓库或公开证明页面、证据快照、状态、申请时间、决定时间和当前审核版本；
- `project_claim_events`：申请、通过、拒绝、暂停、恢复、撤销和争议事件，只追加且由数据库触发器禁止更新或删除；
- GitHub 证据只保存安装和仓库的非秘密摘要，不保存安装令牌；其他证据只保存申请人主动提交的公开 URL 和说明；
- 当前有效认领关系由受约束的状态索引确定，同一作品最多只有一条 `verified`、`disputed` 或 `suspended` 权属链。

已实现的首期接口：

```text
GET  /v1/works/{workId}/claim
POST /v1/works/{workId}/claims
GET  /v1/me/project-claims
POST /v1/project-claims/{claimId}/cancel
GET  /v1/admin/project-claims
GET  /v1/admin/project-claims/{claimId}/events
GET  /v1/admin/work-provenance
PATCH /v1/admin/works/{workId}/provenance
GET  /v1/admin/works/{workId}/provenance-events
POST /v1/admin/project-claims/{claimId}/decision
```

首期允许由管理员人工作出最终决定；后续可以对证据充分、GitHub App 安装归属和仓库权限都一致的申请增加自动通过，但自动通过不是 O1 的必要条件。

当前代码位于“发现”的统一游戏详情页、创作者中心和管理后台：游戏详情展示来源状态并为社区收录游戏提供认领入口；创作者中心提供个人申请列表与待审撤回；管理后台提供全部状态筛选、审核、争议、暂停、恢复、撤销及认领审计历史。后台还可以逐款核对并修正“发布者自有 / 平台代收录”、公开仓库与许可证；实际 ZIP 上传或 GitHub 导入方式保持只读，所有有效修正写入不可更新、不可删除的来源审计事件。已有活跃认领时发布关系会锁定，固定 GitHub 导入也不能改指向其他仓库。通过或恢复审核前会重新检查创作者资格；GitHub 证据还会重新检查连接、仓库访问状态和目标仓库，避免使用过期证据。

截至 2026-10-10，实施状态必须按以下边界理解：

- **代码已完成**：来源字段与安全迁移、公开认领状态、公开证据申请、创作者申请列表与撤回、管理员全生命周期治理、管理权转移与回退、只追加审计查询和界面；
- **自动化证据已补齐**：路由和服务单元测试、API 客户端与界面契约测试、可在专用 PostgreSQL 测试库运行的全生命周期集成测试、可在 Playwright 环境运行的创作者/管理员双账号浏览器验收；浏览器二进制不由仓库下载，必要时通过 `GAMEHUB_COMMUNITY_BROWSER_PATH` 指向本机受控 Chrome 或 Edge；
- **本地真实验收已执行**：2026-10-10 使用一次性 PostgreSQL 16 `community_test` 环境跑通提交、审核、争议、暂停、恢复、撤销、管理权回退和审计不可变；使用本机 Edge 跑通创作者与管理员双账号审核、状态回显、审计读取和移动端无横向溢出；截图保存在 `.runtime/project-claim-acceptance/`；
- **生产已确认**：用户已在线确认统一来源状态、社区收录标记与认领入口已部署可用；真实作者是否完成首例认领仍属于运营验证，不反推技术状态；
- **发布候选已完成**：公共目录接口返回进入平台方式、权益关系、认领状态、开放属性与固定 GitHub Commit；发现页提供开放源码、可二创、待认领、运行方式和来源筛选，卡片统一展示来源与权益，详情页可跳转到固定 Commit；
- **保守标注原则**：开放源码只接受平台显式支持的 SPDX 开源许可证；“可二创”采用更窄的宽松许可证列表，未知或自定义许可证只显示“权益待核验”，不自动承诺开放或可二创；
- **仍待发布验收**：本次发现页发布候选合并部署后，需要检查真实目录筛选、GitHub 固定 Commit 跳转及桌面/移动端布局；
- **O1 剩余工作**：准备并逐款审核 10—20 款首批内容，完成许可证、素材、作者、固定版本、运行质量与认领状态核验，并邀请首批真实作者。

因此，代码完成不等于已经部署，也不等于已经发生真实作者认领。

## 7. 社区共建闭环

社区不优先发展泛聊天，而应围绕具体作品和可完成事项组织参与。

目标循环为：

```text
作者授权或发布开放游戏
  → GameHub 生成可直接体验的作品页
  → 玩家免费试玩、收藏和分享
  → 玩家提交结构化反馈或领取贡献任务
  → 作者确认反馈并回流到原仓库
  → Issue、Pull Request、翻译、测试或 Remix 产生
  → 新版本发布，平台保留来源并再次传播
```

社区内容优先级：

1. 试玩报告和兼容性反馈；
2. Bug、建议和玩法讨论；
3. 攻略、挑战和成绩分享；
4. 翻译、文档、美术和测试招募；
5. `good first issue` 和开发任务；
6. 作者开发日志；
7. 保留来源的 Remix 展示。

社区项目、动态和贡献履历必须与作品及原仓库建立可追溯关系，避免成为与产品脱节的信息流。

## 8. 传播产品能力

推广前必须先保证作品链接在外部渠道能够正确表达作品，而不是所有链接都显示同一个 GameHub 标题。

### 8.1 公开链接

- 为作品、开放游戏专题、社区项目和创作者主页提供不依赖 URL Hash 的公开地址；
- 为每个公开页面输出独立的标题、摘要、canonical URL 和社交分享元数据；
- 作品撤下或版本失效时，分享页必须明确显示状态，不能静默指向其他内容。

### 8.2 分享素材

- 自动生成包含封面、标题、作者、玩法标签和品牌标识的分享图；
- 提供“复制链接”“复制 README 徽章”“下载分享图”三个清晰动作；
- 为作者提供可嵌入的在线体验按钮；
- 分享链接保留来源渠道参数，但不暴露用户隐私或敏感标识。

### 8.3 作者共同传播

平台不把作者只视为供给方，而应与作者共同发布：

- 作者在 README、Release 或个人主页加入体验入口；
- 平台发布作品故事、试玩片段和贡献机会；
- 作者确认事实、版本和署名后共同发布；
- 新版本和贡献成果再次形成传播内容。

## 9. 内容推广计划

固定运营栏目建议为：

### 9.1 每周一个开放游戏

- 30—60 秒真实录屏；
- 一句话说明玩法；
- 明确作者和开放许可证；
- 直接落到免费试玩页面；
- 同时展示一个可参与的反馈或贡献动作。

### 9.2 GitHub 宝藏游戏

- 介绍作者、创作背景和技术亮点；
- 解释平台如何将仓库转换为可体验作品；
- 不以平台口吻覆盖原作者故事；
- 链接原仓库、作者主页和赞助入口。

### 9.3 一起完善这个游戏

- 每期选择一个明确问题；
- 提供测试、翻译、设计或开发任务；
- 展示完成条件和作者验收方式；
- 后续公开感谢贡献者并展示结果。

### 9.4 阶段性活动

- 开放游戏周；
- 小型在线 Game Jam；
- 老游戏网页化或多语言计划；
- 无障碍和移动端兼容改进周；
- 新手第一次开源贡献活动。

活动必须以真实作品和可完成任务为中心，不以空泛签到、刷榜或奖励驱动虚假参与。

## 10. 渠道策略

首期以作者共同传播和开发者社区为主，不先购买泛流量。

中文渠道可按内容形态选择：

- B站：试玩录屏、作者访谈、开发过程；
- V2EX、掘金：技术实现、作者招募和开放项目案例；
- 知乎、少数派：开放游戏故事、体验方式和平台理念；
- 社交平台短内容：单款作品亮点和直接试玩链接。

英文材料成熟后再进入：

- GitHub Discussions 与相关仓库社区；
- Show HN；
- Product Hunt；
- 与 open source、web games、indie games 相关的 Reddit 社区。

不同渠道使用对应语言和内容结构，不进行同文案批量发布，不在未征得作者同意时冒用作者身份推广。

## 11. 增长指标

平台不以收录仓库数、页面浏览量或社交曝光作为唯一成功标准。首阶段重点观察四条漏斗：

### 11.1 玩家激活

```text
作品页访问 → 点击开始 → 成功启动 → 有效试玩 → 收藏或分享 → 复访
```

### 11.2 作者发布

```text
收到邀请或访问作者页 → 连接仓库 → 生成草稿 → 构建验证 → 公开发布
```

### 11.3 社区共建

```text
试玩 → 提交反馈 → 作者确认 → Issue/任务 → 提交成果 → 验收
```

### 11.4 作者传播

```text
生成徽章/分享素材 → 作者发布 → 外部访问 → 有效试玩 → 新作者申请
```

建议核心指标：

- 作品页到成功启动的转化率；
- 启动到有效试玩的转化率；
- 有效试玩后的收藏、分享和七日复访；
- GitHub 导入到成功发布的转化率和耗时；
- 作者认领率；
- 反馈被作者确认的比例；
- 被确认反馈到贡献任务或 Issue 的比例；
- 首次贡献完成率；
- 作者徽章与分享链接带来的有效试玩数。

所有指标应按作品规模设置最小样本量，不用少量数据公开评价作者或影响新作品曝光。

## 12. 商业边界

开放游戏的基本体验应持续免费。未来商业化可以围绕增值服务，而不是关闭开放内容入口。

可探索：

- 作者赞助、打赏和悬赏任务；
- 更高资源额度和高级托管；
- 私有作品、团队协作和组织空间；
- 品牌活动、比赛和专题策展；
- 创作者数据与自动化工具；
- Agent 增强能力和专业服务。

平台不得默认截留作者赞助入口，不得以付费排名伪装自然精选，也不得因商业合作弱化许可证、来源和作者身份展示。

## 13. 分阶段实施

### 阶段 O1：发现页开放属性与来源基础

- 固定计划名称、口号和作者原则；
- 在“发现”的统一游戏目录中增加免费、开放源码、可二创和运行方式等筛选与专题；
- 为所有游戏标注平台官方、发布者直传、GitHub 导入或社区收录来源；
- 完成作者、许可证、仓库、Commit 和认领状态展示；
- 完成认领申请、验证、审核、授权、暂停、撤销和争议处理机制；
- 准备作者邀请材料，真实作者邀请与认领作为运营验证并行推进；
- 准备首批 10—20 款候选作品并完成审核。

完成条件：至少 10 款作品可以稳定免费游玩，来源与许可均可核查；所有作品明确显示认领状态；一条测试申请能够完整经过提交、证据记录、审核、授权和撤销。真实作者完成认领是后续运营指标，不阻塞 O1 技术验收。

当前进度（2026-10-10）：来源与认领机制已上线；发现筛选、卡片来源权益和详情固定 Commit 已完成发布候选。O1 是否完成不再取决于新增机制，而取决于发布验收和首批 10—20 款内容审计是否达到完成条件。

### 阶段 O2：传播基础

- 独立公开 URL 和社交元数据；
- 作品分享图、短链接和 README 徽章；
- 作者数据看板生产验收；
- 渠道归因和基础漏斗指标；
- 三个端到端示范案例。

完成条件：外部分享能正确显示对应作品；作者可以看到由自己传播带来的聚合效果。

### 阶段 O3：共建闭环

- 结构化反馈；
- 作者确认后的 GitHub Issue 预填；
- 公开贡献任务和 `good first issue` 映射；
- 领取、提交、验收和公开贡献履历；
- 作者开发日志和 Remix 来源展示。

完成条件：至少出现一条真实的“试玩 → 反馈 → 任务/Issue → 被接受成果 → 新版本”完整链路。

### 阶段 O4：持续推广

- 每周一个开放游戏；
- 作者共同发布；
- 开放游戏周或小型 Game Jam；
- 中英文内容矩阵；
- 基于有效试玩、复访和共建质量的策展优化。

完成条件：新增有效玩家和新增作者中，有可测量比例来自作者传播、作品分享和社区共建，而非平台单向投放。

## 14. 风险与停止条件

出现以下情况时应停止自动收录或公开推广，先完成复核：

- 许可证缺失、冲突或不允许当前分发方式；
- 第三方素材来源不清；
- 原作者提出异议或身份无法核验；
- 构建内容与固定 Commit 不一致；
- 作品请求超出声明的网络、存储或设备权限；
- 平台修改导致作品行为、署名或许可证发生误导；
- 作品包含恶意行为、违法内容、钓鱼或隐私风险；
- 推广数据出现刷量、虚假互动或对作者形成骚扰。

## 15. 当前建议

平台下一阶段应以“开放游戏计划”作为品牌与增长主线，而不是继续优先扩展排行榜、泛聊天、复杂积分或付费系统。

近期执行顺序建议为：

1. 合并并部署发现页开放属性、来源标签与固定 Commit 展示，完成真实目录冒烟验收；
2. 审核首批 10—20 款精选游戏，逐款校验许可证、素材、作者、版本、运行质量与认领状态；
3. 邀请首批作者认领或确认发布关系，同时开始独立分享链接与社交卡片；
4. 作者数据、README 徽章和联合发布；
5. 结构化反馈与贡献任务；
6. 首次公开专题活动。

最终需要证明的不是平台收录了多少仓库，而是：玩家确实更容易玩到优秀开放游戏，作者确实获得了用户和贡献，共建结果也确实回到了原项目。
