# 小墨鱼 QQ 后台管理

入口：网站后台 → Agent 管理 → 小墨鱼 → QQ 接入。

后台支持登录状态、手机 QQ 扫码及刷新、唯一群白名单、最多 20 个用户、暂停/恢复回复，以及每日调用和预留 Token、每人调用和消息速率设置。暂停保留登录、队列和历史；恢复时重新检查权限与预算。换群不重置预算，不把旧任务发到新群，也不混用旧群上下文。

当前问答范围仍为白名单测试群中的 @文字消息。图片、语音和私聊不进入模型。后台没有开启论文、访问他人聊天或执行服务器命令的能力。

## 权限与一致性

每次管理请求都验证网站当前管理员、账号有效性、机器人运营者归属及唯一绑定的机器人 ID。仅有管理员角色但不是运营者不能访问。内部请求使用独立随机密钥 HMAC，限制时效、请求大小和速率，不向浏览器暴露网关 Token。控制端口只在内部 Docker 网络，不发布公网端口，不挂载 Docker socket。

设置使用数据库版本号与事务锁；并发冲突不会覆盖其他人的修改。相同请求 ID 可以重试；不同内容复用 ID 会拒绝。二维码刷新先持久化意图，结果不确定时要求查看当前状态，不自动重复刷新。审计记录操作者、请求 ID、版本及设置前后值；二维码和密钥不写入审计。

QQ 历史数据库只做新增表、列与旧任务来源群回填。调用账本、任务、历史和不可变事件保留。新旧 worker 的策略标记不同，旧 worker 无法无声绕过新白名单。管理已启用后不能用旧 `--init` 覆盖设置。

## 发布与回滚

首次后台升级使用离线更新包，替换网站 API、网页和 QQ worker；不替换 NapCat，不执行网站数据库迁移，不导入本机历史，不覆盖现有四份配置文件，不改变论文开关。预检要求线上源码基线和工作区符合要求；不符合就停止，绝不 reset/clean。

更新前备份 QQ schema，保留原镜像及私有 Compose 环境快照。新增覆盖文件在 `/www/mooyu-qq/admin/`，内部网络为 `mooyu-qq-admin-control`。原 `.env`、`worker.env`、`config.json` 内容必须校验保持不变。重建服务需要保留新覆盖文件（实际容器 Compose 标签会记录文件列表）；不要只使用旧 compose.yml 重建 worker，也不要对已管理的数据库执行旧初始化。

每步命令的完整输出存入更新记录的 `command-NNN.log`，权限 0600；这些私有文件可能含 Compose 环境信息，勿公开上传。终端和 `deploy.log` 只显示步骤、退出码及脱敏状态。出现错误时提供 `deploy.log`，先不要重新安装或清空数据。

首次线上预检发现：统一发布时临时导出的 `DESKTOP_DOWNLOADS_DIR` 和 `AGENT_DOWNLOADS_DIR` 不在原 `.env` 中。单独重新解析原 Compose 会失败。安装器现从运行中的 web 容器 `/srv/desktop-downloads` 和 `/srv/agent-downloads` 两个唯一只读 bind 挂载恢复变量，验证其来源为 `/www/` 下的现有真实目录，拒绝缺失、重复、可写或数据卷挂载。恢复值仅用于子进程环境并记录到私有回滚状态，不写原 `.env`，不使用猜测路径。新增实际 Compose 覆盖文件的缺变量复现和恢复解析测试，以及回滚环境恢复测试。

后续线上执行暴露网页验收遗漏：web 原本没有 Docker HEALTHCHECK，不能等待不存在的 `healthy` 状态。安装器对运行中的 web 改用本机 HTTPS 探测首页和 `/ready`，保留 TLS 校验，固定解析到 127.0.0.1 并禁用代理；首页必须返回 HTML。有 HEALTHCHECK 且不健康仍不能接受。测试覆盖无 HEALTHCHECK 的实际探测路径、HTTP 失败、非 HTML、显式 unhealthy。此次失败已执行回滚，重试前需核对当前镜像、控制策略标记与管理覆盖文件，不能重新覆盖首次安装目录。

### 回滚后的接续更新

`update-admin.py --resume ORIGINAL_RECORD NEW_RECORD` 只允许从可核验的首次回滚状态接续：api/web/worker 镜像必须与原回滚材料一致，业务镜像清单和源码基线一致，唯一 QQ 管理设置与登录版本均为 1，策略标记已回到 bootstrap hash，且没有完成安装标记。重新备份当前 QQ schema，生成新的回滚快照；不重载镜像、不创建网络、不替换密钥或覆盖管理文件。既有控制网络必须为本工具创建的 internal 空闲网络，管理覆盖文件必须与当前运行配置重新计算的结果完全一致。

接续过程对原四份配置和既有密钥、两份覆盖文件记录前后校验值。网站 HTTPS、API 健康、QQ worker 健康以及网站到 QQ 的签名状态调用均通过后，才快进源码并写完成标记。失败继续使用新记录中的原镜像快照恢复；不会恢复旧数据库快照或清理历史。

新增接续流程成功/失败保护测试和实际 Caddy 镜像 HTTPS 测试。实际镜像测试使用隔离的 localhost 证书和显式测试 CA，不使用 `--insecure`；Windows 测试夹具仅对没有吊销服务的测试 CA 采用吊销 best-effort。线上 Linux 探测使用系统信任链，不增加该参数。

自动回滚恢复原网站镜像，不恢复旧数据库快照。如果管理员尚未修改设置，可以恢复原 worker 的策略标记与镜像；如果已存在新设置版本，保留新 worker 和设置，防止旧版本忽略权限。手动 `rollback.sh` 也遵守同一规则。历史数据库和审计均不删除。

## 本地验收

- 全量 382 个文件：1,650 项通过、0 失败、105 项条件跳过。
- 单独真实 PostgreSQL：管理 8 项、原 QQ 故障恢复 16 项通过，包括并发、暂停、换群、重试、旧 worker 拒绝、断库与进程中断恢复。
- 实际 Edge 浏览器：StrictMode、二维码隐私、编辑期间轮询、版本冲突、暂停预算、权限撤销清屏、手机布局通过。
- 三个生产镜像与实际 NapCat 网关隔离联通：真实二维码读取、网站权限、内部签名、CAS、重试和 worker 重启持久化通过。测试没有登录真实 QQ 号。
- 实际 deepseek-flash + 隔离 PostgreSQL：合成消息两次调用、历史回忆、暂停恢复、重复消息不增加调用通过；回复由测试发送器捕获，未发往 QQ。
- 部署配置保留/回滚守卫测试通过；生产更新命令尚需在用户服务器执行，生产扫码及群消息验收需由用户完成。

任何网关发送在确认响应前中断，都无法仅靠 OneBot 保证恰好一次。此时任务进入待核对，不会盲目重发。后台显示待核对数量，本轮未增加自动重发开关。
