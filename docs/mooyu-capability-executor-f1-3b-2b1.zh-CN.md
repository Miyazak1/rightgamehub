# F1.3b-2b-1：引擎组件解析与只读沙箱投影

状态：已完成
日期：2026-10-29
边界：这是生产 OCR 适配前的执行链闭环，不代表 PaddleOCR / PP-StructureV3 已经运行或可供用户下载。

## 1. 目标

F1.3b-2a 已能从签名目录下载、内容寻址安装并复验模型组件，但“安装在本机”不等于“可以安全交给能力进程”。本阶段补齐：

```text
冻结引擎计划
  → 本机可信目录提供者
  → 执行租约内按需下载/复验
  → 组件身份绑定
  → Windows 沙箱只读 ACL
  → 能力进程按明确角色读取组件
```

服务端仍只保存合同、任务、租约、预算和审计状态；PDF、模型文件和计算都留在用户电脑。

## 2. 已实现

### 2.1 执行租约内解析

通用执行器新增可选 `componentResolver`。解析发生在运行日志已经进入 `running`、续租定时器已经启动之后，因此大组件下载不会静默耗尽租约。解析失败走现有失败上报和恢复语义，不会启动原生能力进程。

论文版面解析器只接受：

- `research.paper.layout@1`；
- 恰好一个成功的 `paper-layout-engine-plan` 前置阶段；
- 能通过 `paper-layout-engine-plan-v1` 严格验证的输出；
- 由本机可信目录提供者重新取得的签名组件目录。

它不会信任任务输入携带的下载地址或本地路径。

### 2.2 原生请求最小披露

每个组件在进入 runner 前再次验证：

- 组件 ID、角色、版本；
- SHA-256 和字节数；
- 绝对路径、普通文件且不是符号链接；
- Windows 卷序列号、文件 ID 和长度。

能力进程只得到组件角色、版本、摘要、大小和必要的本地源路径，不得到组件仓库根目录、活动/回退状态或 Windows 文件身份。租约令牌仍不进入能力进程。

### 2.3 Windows 只读投影

沙箱宿主协议升级为 `windows-sandbox-host-request-v3`。升级是失败关闭的：旧 helper 不会把新请求误当成已经支持组件 ACL 的请求。

helper 在启动 AppContainer 前：

1. 用 `FILE_FLAG_OPEN_REPARSE_POINT` 打开组件；
2. 比较卷序列号、文件 ID 和长度，阻止同内容换文件与路径替换；
3. 在整个子进程生命周期内保持验证句柄；
4. 只授予组件文件 `Read`，不授予写入或执行；
5. 退出后撤销临时 ACL，并由 Job Object 回收进程树。

组件摘要、大小或文件身份发生变化时，能力进程不会启动。

## 3. 恢复与不确定性

- 在组件解析或下载期间重启：日志处于 `resolving-components`，可以重新复验缓存并安全恢复；
- 在原生进程启动前发生确定性组件错误：安全失败；
- 结果已经产生但提交失败：继续复用 `result-pending` 幂等重交，不重跑 OCR；
- 续租失败：取消组件解析或原生进程，并按不确定结果上报。

## 4. 验证

- 组件解析、runner、租约和论文引擎定向回归：22/22 通过；
- 组件目录/存储与 Windows host 协议回归：9 通过、6 条需要普通用户真实 AppContainer 环境而跳过，零失败；
- 更新后的 C# helper 已真实编译，产物 SHA-256 为 `117bcb6f464255b74f01ad299d324699946ede5ee9b4e59ec4b06207fe55d3a7`。该摘要只证明本次本地构建，不是生产发布摘要。

## 5. 仍未完成

当前组件存储绑定的是单个内容寻址文件。PP-StructureV3 的模型和本地 Python/推理运行时通常是多文件目录，不能把“一个模型 ZIP 已下载”直接当作“引擎已可执行”。因此以下工作仍属于 F1.3b-2b-2：

1. 冻结可验证多文件组件包合同，逐文件绑定路径、大小和摘要；
2. 安全解包并阻止路径穿越、链接、特殊文件、重复条目和解压炸弹；
3. 建立独立的引擎子进程协议，不把 PaddleOCR 临时 Python API 写进通用执行合同；
4. 接入 PDF 页面渲染和 PP-StructureV3/PaddleOCR CPU 适配器；
5. 对开放论文坐标金标测量阅读顺序、区块、表格、公式、CPU、内存和耗时；
6. 质量不达标、模型缺失、资源不足或超时继续失败关闭。

- https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/quick_start.md
