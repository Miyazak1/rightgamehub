# GameHub 社区、分享与共建完整改造方案

状态：设计定稿并完成 C0—C4 首轮实施；生产启用需执行迁移 `0056`、`0057` 并完成双账号线上验收。
更新日期：2026-10-10。
适用分支：`codex/game-services-foundation`，设计基线提交 `ac1cd01d181f41ee72ca5c681de20fc667581e5c`。

## 1. 决策摘要

GameHub 应取消导航中的两个并列顶级入口“分享”和“共建”，合并为一个顶级入口“社区”。这是信息架构合并，不是功能删除：

- 现有 `/community` 分享板块保留，改为社区内的“动态”；现有投稿、图文、来源链接、点赞、私人收藏、审核、举报与媒体处理全部复用。
- 现有 `/contribute` 共建板块保留，改为社区内的“一起做”；现有任务领取、GitHub Issue / 成果地址、提交、验收、通知与贡献履历全部复用。
- 新增“活动”“游戏组队”“我的参与”，让社区不只展示内容，也能组织用户一起完成事情。
- 游戏运行态分享 `/s/{code}` 与社区内容分享不是同一能力，必须继续独立保留。

改造后的顶级导航为：

```text
发现    社区    游戏库
```

社区内部一级导航为：

```text
首页    动态    一起做    活动    游戏组队    我的参与
```

核心定位：

> 发现负责“找到作品”，社区负责“找到人和正在发生的事”，游戏库负责“回到自己的内容”。

## 2. 当前代码事实与边界

当前线上分支已经存在三类容易混淆的能力：

| 当前入口 | 路由与实现 | 实际职责 | 改造后位置 |
| --- | --- | --- | --- |
| 分享 | `/community`，`CommunityPage.jsx` | 游戏、AI、计算机图文分享；草稿、审核、点赞、收藏、举报 | 社区 / 动态 |
| 共建 | `/contribute`，`ContributionCenter.jsx` | 从玩家反馈形成公开任务，领取、提交、验收、贡献履历 | 社区 / 一起做 |
| 游戏内容分享 | `/s/{code}`，`GameSharePage.jsx` | 打开某个游戏生成的特定可玩内容或状态 | 保持独立，不进入社区信息架构 |

现有 `PlatformNavigation.jsx` 把“分享”和“共建”同时放在 `playerLinks`。本方案最终只保留 `/community` 顶级入口；旧地址继续兼容，不能因导航改造破坏已有外部链接、通知或浏览器历史。

已有专项设计继续有效：

- 分享底座、审核、图片与配额以[游戏 AI 与计算机分享板块设计](./community-sharing-foundation-design.zh-CN.md)为准。
- 贡献任务状态、隐私、GitHub 边界与验收以[G3.3 共建任务与贡献履历](./69-g3-contribution-tasks.zh-CN.md)为准。
- 本文负责两者之上的产品组织、视觉体验以及新增项目、活动、组队能力，不重新定义已经验证的底层安全约束。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 用户进入社区后，10 秒内能找到一个值得阅读、参加或响应的对象。
2. 内容分享不再是孤立信息流；一条动态可以导向项目、活动、组队或作品。
3. 共建不再只是零散 GitHub 任务；用户能先理解项目目标、成员与进度，再领取具体任务。
4. 活动和组队具备明确时间、人数、参与状态与下一步，而不是普通帖子里的一段自由文本。
5. 页面保持 GameHub 现有深色/浅色/高对比主题、紫色行动色与现代像素风，同时减少大面积边框堆叠，增加层次、人物感和正在发生的氛围。
6. 移动端与 Agent 侧栏都能完成浏览、加入、退出、签到和任务处理，不把关键动作藏在 hover 中。
7. 用有意义的回访理由提高停留和复访，不依赖无限滚动、虚假在线人数或成瘾式通知。

### 3.2 非目标

- 首版不自建音视频会议、屏幕共享或语音频道；活动使用经过验证的外部 HTTPS 会议链接。
- 首版不做私信和开放群聊；项目更新、活动留言采用受控讨论，降低骚扰和内容治理成本。
- 首版不把任意帖子都转换成任务、活动或组队；创建入口明确选择类型并验证专属字段。
- 首版不做用户自定义社区/频道、复杂群组权限、付费活动、票务、虚拟货币或贡献积分商城。
- 首版不以停留时长作为唯一成功指标，也不制造“有人正在输入”等无法可靠证明的实时感。

## 4. 体验原则

### 4.1 先展示“能参与什么”，再展示“大家说了什么”

社区首页首屏优先呈现即将开始的活动、仍缺人的项目和可加入的游戏组队；普通动态位于其后。用户进入社区应先看到行动机会，而不是一堵按时间排列的文字墙。

### 4.2 每张卡片都回答四个问题

1. 这是什么？
2. 谁发起的？
3. 什么时候或进展到哪里？
4. 我现在可以做什么？

缺少明确行动的卡片只进入动态流，不进入“正在发生”区域。

### 4.3 人比数字重要

头像、发起人、成员角色和共同参与关系优先于总点赞数。卡片只展示帮助决策的数字，例如“还缺 2 人”“周六 20:00”“3/7 个任务完成”；不在首页放大虚荣指标。

### 4.4 状态必须诚实

“已加入”“等待发起人确认”“活动已取消”“任务等待验收”“房间已满”等状态必须来自服务端。客户端不能凭按钮点击伪造成功，也不能把外部会议链接可填写等同于会议可用。

### 4.5 细节服务于理解

像素装饰、微动效和颜色只用于表达类型、状态和反馈；不能牺牲正文可读性。信息密度通过留白、字号层级、分组和渐进披露控制，而不是通过把所有文字缩小。

## 5. 信息架构与路由

### 5.1 顶级导航

| 导航 | 路由 | 范围 |
| --- | --- | --- |
| 发现 | `/discover` | 作品与游戏发现 |
| 社区 | `/community` | 动态、项目、活动、组队与个人参与 |
| 游戏库 | `/library` | 用户收藏与最近游玩 |

创作中心继续位于账号菜单和创作者工作台中，不重新加入玩家顶级导航。

### 5.2 社区内部路由

| 页面 | 新路由 | 旧路由兼容 |
| --- | --- | --- |
| 社区首页 | `/community` | 当前分享首页内容迁入“动态”区域 |
| 动态 | `/community/feed` | `/community/game` 等频道地址重定向或映射到 feed 筛选 |
| 一起做列表 | `/community/projects` | `/contribute` 兼容跳转 |
| 项目详情 | `/community/projects/{projectId}` | 现有 `/contribute/{taskId}` 继续打开任务详情，并显示所属项目 |
| 活动列表/详情 | `/community/events`、`/community/events/{eventId}` | 无 |
| 游戏组队列表/详情 | `/community/parties`、`/community/parties/{partyId}` | 无 |
| 我的参与 | `/community/me` | 合并“我的分享”“私人收藏”“我的任务”，通过分段筛选切换 |
| 管理入口 | `/community/manage` | 仅显示用户有权限管理的项目、活动和组队 |
| 审核入口 | `/community/review` | 保留现有管理员审核能力 |

旧地址至少保留一个完整发布周期；服务端 API 不因路由变化改名。通知中的旧任务地址仍可解析。

## 6. 社区对象模型

社区不应只由“帖子”构成。首版统一展示五种对象，但每种对象保持自己的业务表和状态机。

| 对象 | 生命周期 | 必填信息 | 主要行动 |
| --- | --- | --- | --- |
| 动态 | 草稿、待审、公开、撤回、隐藏 | 标题、频道、正文/链接/图片 | 点赞、收藏、举报 |
| 项目 | 草稿、招募中、进行中、完成、归档 | 目标、发起人、角色需求、关联作品 | 申请加入、查看任务、关注更新 |
| 任务 | 草稿、公开、领取、提交、验收、关闭 | 完成标准、难度、技能、项目/作品 | 领取、提交、验收 |
| 活动 | 草稿、开放报名、即将开始、进行中、结束、取消 | 时间、形式、人数、参与方式 | 报名、取消、打开会议、查看回顾 |
| 游戏组队 | 招募中、已满员、准备中、游戏中、已结束、取消 | 游戏、开局时间、人数、房间类型 | 加入、退出、准备、进入房间 |

“项目”表示持续协作容器；“活动”表示在一个时间发生的聚会；“游戏组队”表示围绕指定游戏和房间的短时协作。三者不能只用一个含大量空字段的通用表代替。

## 7. 页面与交互设计

### 7.1 社区首页

桌面端采用最大 1120px 的两栏布局，主栏约 720px，右栏约 320px；窄屏合并为单栏。首页结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 社区                                                   ＋ 发起 │
│ 一起发现、一起做点东西，也一起玩。                           │
├──────────────────────────────────────────────────────────────┤
│ 首页  动态  一起做  活动  游戏组队  我的参与                │
├─────────────────────────────────────┬────────────────────────┤
│ 今晚正在发生                         │ 我的下一步             │
│ [20:00 试玩会] [缺 2 人的组队]       │ 待验收 / 已报名 / 通知  │
├─────────────────────────────────────┼────────────────────────┤
│ 值得加入的项目                       │ 本周社区节奏           │
│ [项目卡] [项目卡]                    │ 3 场活动 · 4 个开放任务 │
├─────────────────────────────────────┴────────────────────────┤
│ 最新动态                                                     │
│ [动态卡]                                                     │
└──────────────────────────────────────────────────────────────┘
```

首屏模块：

- “正在发生”：最多 3 个在未来 24 小时发生或当前可立即加入的对象；无真实内容时不展示假卡片。
- “值得加入”：最多 4 个仍有明确角色空缺或开放任务的项目。
- “我的下一步”：登录用户展示待处理动作，游客展示加入社区的价值与登录入口。
- “最新动态”：继续使用现有审核后公开的分享流；首页只显示摘要，进入“动态”查看完整筛选。

排序首先满足可参与性和时间有效性，再参考关注关系、关联游戏和最近更新。点赞数不得单独决定首页排序。

### 7.2 社区“发起”入口

页面右上角只有一个主按钮“＋ 发起”，打开类型选择面板：

```text
一起做一个项目      适合持续协作、分工和任务
组织一场活动        试玩会、线上聚会、讨论或会议
发起游戏组队        现在或预约找人一起玩
发布一条动态        分享游戏、AI、计算机新发现
```

选择类型后进入独立表单。不能使用同一张万能表单通过下拉框切换所有字段。用户未登录时先说明需要登录，不先让用户填写完再丢失内容。

创建成功后显示清晰的下一步：邀请成员、创建第一个任务、复制活动链接或等待队友；不只显示“发布成功”。

### 7.3 动态

现有分享页改名为“动态”，保留频道“游戏 / AI / 计算机”，增加以下展示细节：

- 卡片顶部由频道标签、作者头像/昵称、相对时间组成；标题下显示两到四行正文摘要。
- 首张图片使用 16:9 或 4:3 有界封面，其余图片显示数量角标，不让不同图片尺寸造成页面跳动。
- 来源链接显示域名、用户填写的链接说明和外链图标；不伪造成平台背书。
- 点赞、收藏、举报保留；分享按钮复制帖子稳定链接。评论在真正实现前不显示空计数。
- 与项目、活动或游戏组队关联的动态显示轻量上下文条，例如“来自项目：像素迷阵移动端适配”，点击进入对应对象。
- “我的分享”和“私人收藏”移入“我的参与”，减少动态页内部导航层级。

### 7.4 一起做

“一起做”首页先展示项目，再展示独立开放任务。现有任务不是被隐藏，而是获得项目上下文。

项目卡需要显示：

- 项目名称、简短目标与关联作品封面。
- 发起人以及最多 3 个成员头像，更多成员显示 `+N`。
- 当前阶段：招募中 / 进行中 / 等待发布 / 已完成。
- 进度：已验收任务数 / 总任务数，不用手动填写百分比。
- 所需角色：例如“像素美术 ×1”“前端 ×2”；满员角色弱化显示。
- 最近一个可信更新和明确主行动：“查看项目”“申请加入”或“领取任务”。

项目详情使用四区结构：

1. 概览：目标、范围、关联作品、公开仓库、状态与发起人。
2. 成员：角色、加入时间、公开技能和当前负责内容。
3. 任务：复用现有 Contribution Task 卡片和完整状态机。
4. 更新：使用社区动态的受限正文块发布里程碑、试玩结果和发布说明。

申请加入和领取任务是两个动作。用户可以先加入项目再领取任务，也可以领取明确允许外部贡献者参与的任务。加入项目不自动获得 GitHub 权限。

### 7.5 活动

活动列表默认按时间分为“即将开始”“本周”“以后”“已结束”。活动卡显示：

- 月/日视觉日期块、开始时间和用户本地时区。
- 活动类型：线上聚会、试玩会、讨论、工作坊、项目会议。
- 主办人、报名人数/容量、预计时长。
- 关联项目或游戏。
- 状态按钮：“报名”“已报名”“名额已满”“查看回顾”。

活动详情必须在报名之前明确展示时间、时区、参与平台、是否录制、行为规则和取消政策。外部会议地址仅向满足条件的报名用户在合理时间窗口显示；公开页面不直接暴露永久会议密码。

活动结束后允许主办人发布回顾动态并关联成果，但不能修改过去的实际开始时间来伪造记录。

### 7.6 游戏组队

游戏组队卡比活动卡更紧凑，突出游戏封面、模式、人数和开局时间：

```text
[游戏封面]  HexGL 竞速
             今晚 21:00 · 2/4 人 · 新手友好
             发起人头像  ○ ○ ＋
             [加入队伍]
```

若游戏已接入 GameHub 房间，详情页使用现有房间创建/加入能力；未接入时只允许外部房间说明，明确标记“外部组织，平台不托管对局”。

组队状态变化必须事务化限制人数。重复加入幂等；退出释放名额；发起人取消要通知已加入成员。开始后不再出现在“可加入”列表，但参与者仍能在“我的参与”找到记录。

### 7.7 我的参与

“我的参与”不是第二个账号中心，而是一个行动收件箱。默认按“需要我处理”排序：

- 待验收、待修改和即将到期的共建任务。
- 即将开始的活动和已经加入的游戏组队。
- 项目加入申请与项目角色邀请。
- 我的分享审核结果。

下方分段切换“项目 / 活动 / 组队 / 分享 / 收藏 / 历史”。已结束内容默认折叠，避免活跃事项被历史记录淹没。

## 8. 视觉系统

### 8.1 总体风格

沿用 GameHub 的“现代像素工具界面”：清晰的矩形、细边框、等宽标签、像素化状态符号和克制阴影。社区比创作中心更有人情味，但不改变全站视觉语言。

视觉关键词：安静、有生命、可信、可加入、轻量像素感。

避免：大面积霓虹渐变、圆角社交媒体克隆、每张卡都发光、过多小字号、所有内容都装在相同粗边框中。

### 8.2 颜色使用

所有基础颜色继续来自现有主题变量：

- `--gh-canvas`：页面底色。
- `--gh-panel`：主要卡片与分区。
- `--gh-raised`：卡片内次级区域、筛选与表单。
- `--gh-primary` / `--gh-secondary`：主次文字。
- `--gh-action`：主行动、当前导航、可加入状态。
- `--gh-success`：已完成、已确认、已签到。
- `--gh-warning`：即将到期、等待处理、容量紧张。
- `--gh-danger`：取消、失败、治理警告。

对象类型不新增固定品牌色，使用图标、标题和 `color-mix()` 生成的轻量底纹区分。状态不能仅靠颜色表达，必须同时带文字或形状。

### 8.3 排版与密度

- 页面标题：30–36px；详情主标题可到 40px。
- 分区标题：18–22px。
- 卡片标题：15–18px；动态长标题 18–22px。
- 正文：桌面 13–14px、行高 1.65；窄屏不低于 13px。
- 辅助信息：10–11px；只有英文 kicker、短状态码可使用 8–9px。
- 中文正文使用现有无衬线字体；导航、状态、时间和短标签继续使用 `ui-monospace`。

空间以 4px 为基础单位，常用间距 8 / 12 / 16 / 24 / 32。卡片内部留白不低于 16px；核心内容卡桌面使用 20–24px。

### 8.4 卡片层级

建立三种卡片，而不是所有对象共用一个 `.panel`：

1. **行动卡**：项目、活动、组队；2px 主边框、3px 像素阴影，底部固定行动区。
2. **内容卡**：动态；1px 边框、更轻阴影，正文阅读优先。
3. **状态卡**：我的下一步、空状态、通知；使用左侧状态条，不与内容卡竞争。

卡片 hover 只抬升 1–2px并加强边框；按下回落。`prefers-reduced-motion` 下取消位移，只改变颜色。整个卡片可以点击时，内部按钮和链接必须保持独立键盘焦点，不能嵌套交互元素。

### 8.5 让页面有“正在发生”的细节

- 活动日期使用独立月/日块；临近 30 分钟显示“即将开始”，但不使用持续闪烁。
- 项目头像栈显示真实成员，不够数据时留空，禁止生成假头像。
- 项目进度使用分段像素条，每段代表一个真实任务；任务多于 12 个时改为数字和普通进度条。
- 组队人数用座位点阵表达，实心为已加入、描边为可用、叉号为关闭。
- 新更新用小型紫色方块和“新”文字，用户查看后消失；不使用永久红点。
- 空状态配一个由 CSS/SVG 构成的小型像素场景，并给出一个主行动，不使用大面积占位插画。

### 8.6 反馈与动效

- 加入、报名、领取等按钮成功后在原位变为已确认状态，旁边出现可撤销的次级动作。
- 乐观更新只用于可安全幂等撤销的点赞和收藏；人数、报名、任务领取必须等待服务端确认。
- 加载使用与最终卡片尺寸一致的骨架，避免页面跳动。
- 列表刷新保留当前内容并在顶部显示细进度条，不把整页替换成加载文字。
- 错误尽量局部出现；一张卡失败不能让整个社区首页不可用。

## 9. 响应式与多宿主

### 9.1 桌面网页

- 页面最大宽度 1120px。
- 社区首页可使用主栏 + 侧栏；列表页保持单主栏或两列行动卡。
- 固定顶级导航，社区子导航可在滚动后吸顶，但不得覆盖宿主标题栏。

### 9.2 窄屏和 Agent 侧栏

- 760px 以下改为单栏；社区子导航水平滚动并保留当前项可见。
- 480px 以下顶部只显示页面标题与“发起”图标按钮，文字说明折叠到标题下方。
- 行动卡始终先显示标题、时间/进度和主按钮；长描述折叠为两行。
- 活动报名、任务领取等关键按钮最小点击高度 40px；相邻交互控件保持足够间距。
- 抽屉和对话框在侧栏中使用全宽底部面板，避免宽度不足导致双层滚动。

### 9.3 主题与无障碍

- 深色、浅色、高对比三种主题使用同一语义 token，不在组件中写死只适用于深色的颜色。
- 正文、按钮、状态文字满足 WCAG 2.2 AA 的对比要求。
- 所有互动可通过键盘完成，焦点顺序与视觉顺序一致；筛选、分页和分段导航使用正确的 `aria-current`、`aria-selected` 或 pressed 状态。
- 时间使用 `<time>` 与机器可读 datetime；界面显示用户本地时区，详情同时说明原始时区。
- 头像和装饰图标不重复朗读；对象类型、人数和状态不能只靠图形。
- 200% 缩放下不出现横向页面滚动，允许卡片内部文字换行。

## 10. 关键用户流程

### 10.1 从动态加入项目

```text
浏览项目更新动态
→ 打开项目上下文条
→ 阅读目标、成员与角色空缺
→ 申请加入或领取开放任务
→ 服务端确认
→ “我的参与”出现下一步
```

### 10.2 发起试玩会

```text
社区“＋ 发起”
→ 选择“活动”
→ 填写时间、时区、容量、关联游戏、参与方式
→ 预览公开信息与报名后信息
→ 发布
→ 复制稳定活动链接邀请
→ 开始前提醒
→ 结束后发布回顾动态
```

### 10.3 游戏组队

```text
选择游戏和模式
→ 设置现在开始或预约时间
→ 设置人数与新手友好等要求
→ 发布招募
→ 玩家加入，人数事务化更新
→ 满员后进入准备状态
→ 打开 GameHub 房间或外部组织说明
→ 结束并进入历史
```

### 10.4 从玩家反馈形成项目任务

```text
作者查看反馈
→ 创建现有私有共建任务
→ 选择加入已有项目，或保持独立任务
→ 完成标准确认后公开
→ 玩家从项目或开放任务列表领取
→ 提交、退回、验收沿用现有流程
→ 项目进度自动更新
```

## 11. 数据设计

沿用现有 `community_posts`、媒体、互动、审核和 contribution task 表。本轮新增明确领域表，不建立无约束的全局 `target_type + target_id`。

### 11.1 项目

| community_project_members | project_id、user_id、role_id、membership_state、joined_at、left_at；唯一有效成员关系 |

## 12. 状态机

### 12.1 项目

```text
draft → recruiting → active → completed → archived
  └──────────────→ cancelled
recruiting ↔ active
```

完成项目不自动验收未完成任务；取消项目关闭新的加入和任务领取，但保留成员、提交与审计记录。

### 12.2 活动

```text
draft → open → live → ended
          └──────→ cancelled
```

定时任务可以辅助把过期开放活动标记为 ended，但每次读取和写入仍要根据时间纠正状态，不能完全依赖常驻调度器。

### 12.3 游戏组队

```text
open → full → ready → playing → ended
  │      │       └────────────→ cancelled
  └──────┴────────────────────→ cancelled
```

成员退出可使 `full` 回到 `open`；进入 `playing` 后不再接受新成员，除非对应游戏模式明确支持中途加入。

## 15. 治理、隐私与安全

- 项目、活动、组队均提供举报入口，并记录不可变治理事件。
- 发起人可以管理自己创建的对象，但不能删除成员已经提交的贡献证据；关闭和取消保留历史。
- 屏蔽关系在列表分页前生效。公开对象不能被描述为对被屏蔽用户“绝对保密”。
- 外部会议和外部组队链接只允许 HTTPS，拒绝带凭据 URL、本机地址和明显内网目标；服务端首版不抓取目标页面。
- 活动取消和时间重大调整通知已报名成员。普通文案编辑不发送高优先级通知。
- 游戏组队不公开未同意展示的外部账号、语音账号或房间密码。
- 未成年人、骚扰、仇恨、赌博、侵权和恶意链接沿用统一社区规则；活动和组队增加“线下见面风险”提示，即使首版定位线上。
- 不公开精确在线状态、最后上线时间或私密项目成员关系。

## 16. 通知策略

只通知需要行动或时间敏感的变化：

- 项目申请通过/拒绝、角色邀请、任务提交/退回/验收。
- 活动报名确认、取消、开始前提醒和关键时间变更。
- 组队加入结果、满员、取消、即将开始和房间就绪。
- 分享审核结果和治理决定。

点赞不逐条通知；普通浏览、收藏和成员查看不产生通知。相同事件使用稳定事件键去重。通知中心只显示用户有权继续打开的对象；权限变化后不泄露历史正文。

## 17. 发现与排序

社区首页使用可解释的轻量排序：

1. 时间有效且用户可参与。
2. 用户关注的人、已收藏/游玩作品的关联对象。
3. 角色或人数仍有空缺。
4. 最近有真实更新。
5. 内容质量与治理状态正常。

冷启动阶段允许编辑精选，但必须显示“官方精选”。不显示虚假的“热门”“附近很多人”或无法解释的个性化标签。

动态页默认最新发布；以后增加热门排序时使用有时间衰减、可重算的排序投影，不覆盖原始互动事实。

## 18. 指标

### 18.1 核心指标

- 社区访问后产生有效行动的比例：加入项目、领取任务、报名、加入组队、打开对象详情。
- 项目从招募到首次任务领取的时间。
- 活动报名到实际签到/打开参与方式的转化。
- 游戏组队从创建到满员或开始的时间。
- 任务领取后的提交率、验收率和平均完成时间。
- 7 日内再次参与社区对象的用户比例。

### 18.2 体验与安全指标

- 空结果率、首页各模块可用率和列表请求尾延迟。
- 创建表单放弃率与字段错误分布。
- 活动取消率、组队失约率和任务过期率。
- 举报率、成立率、处理时长和重复违规率。
- 通知点击后的有效行动率与关闭通知比例。

不把总停留时长、无限滚动深度或点赞总数作为唯一成功指标。

## 20. 验收清单

### 产品

- 顶级导航没有并列“分享”和“共建”，只有“社区”。
- 现有分享、收藏、投稿审核、任务领取、提交和验收一个不少。
- 动态、项目、活动和组队在文案与视觉上可一眼区分。
- 首页无内容时不出现空白大框或伪造推荐。

### 视觉

- 深色、浅色、高对比主题均无写死颜色造成的不可读区域。
- 卡片标题、正文、辅助信息至少形成三级清晰层次。
- 1120px、760px、480px、320px 与宿主侧栏没有遮挡、溢出和双层横向滚动。
- hover、active、focus、disabled、loading、empty、error、success 状态齐全。
- `prefers-reduced-motion` 下没有非必要位移动画。

### 工程

- 旧 `/community*`、`/contribute*` 与 `/s/{code}` 链接继续工作。
- 加入、报名、组队人数、任务领取在数据库并发下保持上限和唯一性。
- 所有写操作幂等，版本冲突返回可恢复状态。
- 首页聚合接口有界，不产生 N+1 请求。
- 公共列表、详情、媒体、通知和“我的参与”使用一致权限策略。

### 线上验收

- 使用游客、普通用户、项目发起人、创作者和管理员五种身份检查。
- 至少以两个真实账号完成项目申请、活动报名、组队加入和任务验收。
- 在 Web 与至少一个 Agent 宿主验证导航、表单、返回路径和通知跳转。
- 生产部署后检查旧收藏、旧分享、旧任务、贡献履历和游戏专属分享链接。

- GitHub 的 Discussions、Issues 与 Projects 分别承载开放讨论、可执行任务和协作规划，说明交流与执行应有关联但不能混成同一对象。  
  <https://docs.github.com/en/get-started/using-github/communicating-on-github>  
  <https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/best-practices-for-projects>
- Meetup 将群体作为持续关系、活动作为特定时间发生的参与对象，可作为未来是否增加长期小组的观察参考。  
  <https://help.meetup.com/hc/en-us/articles/41258405762957-Can-I-Create-Events-Without-Creating-a-Group>

这些参考只用于验证信息架构原则；GameHub 的视觉、状态和安全边界仍以现有代码、主题 token、多人房间与贡献流程为准。
