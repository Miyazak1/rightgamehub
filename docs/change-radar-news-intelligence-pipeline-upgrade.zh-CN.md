# 墨鱼变更雷达：新闻情报流水线升级设计

版本：Design v1.0  
日期：2026-10-22  
状态：**实施中；在总设计既有证据、账号隔离、成本与恢复门禁下推进**

实施进度（2026-10-22）：

- P0 已补充空账号浏览器回归用例，并确认生产前端可构建；源码已防止无选中专题时访问 `selectedTopic.id`，也不再调用遗留来源表单 setter。浏览器用例在配置 Playwright 的验收环境中执行。
- P1 第三增量已实现：复用 `tool_research_source_discoveries`，新增追加式 `tool_research_candidate_assessments`、账号隔离评估 API、客户端调用和候选收件箱人工相关性判断。
- 搜索候选归档时现会在同一事务内运行 `tier0-prefilter-v1`：冻结输入哈希、理由代码，以及专题相关性、新颖性、潜在影响、可证据化程度、时间线价值和内容质量评分；规则判断只用于排序与复核，不会激活来源或接纳证据。
- 候选列表 API 现支持按最新判断、评估方式、来源状态和最低专题相关性过滤，并可按规则优先级排序；新增账号隔离的候选统计 API，汇总最新判断、评估方式、来源状态和平均维度评分。
- 候选相关性判断与来源激活现已分离；判断“相关”不会自动追踪来源，更不会把搜索标题或摘要提升为证据。
- P1 的候选网页正文采用 `discard-after-extraction-v1` 零持久化策略：正文只在本次获取的进程内存中生成最长 1,200 字证据摘录，来源版本保存哈希、字节数和丢弃策略，持久化 TTL 为 0 秒；存储评估接口同步披露该策略。RSS 摘要和 ChangeRadar 自有页面快照沿用各自既有保留规则。
- Tier 1 候选价值评估已实现但默认关闭：每轮最多评估 1—10 条（默认 6 条）通过 Tier 0 的候选，只向模型发送专题、标题、摘要、发布者、发布时间和 Tier 0 元数据，不发送候选网址或正文；结果以 `model/value` 追加写入评估账本，并以独立 `candidate-assess` 行动接受预算、熔断、回执与费用审计。
- Tier 1 只判断后续研究价值，不判断新闻真假，不激活来源、不获取全文、不接纳证据。模型不可用或输出不合规时，本轮降级为部分完成，规则判断和人工收件箱继续可用。
- P3 评测门禁第一增量已实现：账号隔离的只读报告会选定同一 Tier 1 `evaluationKey`，将模型判断与每条候选的最新人工复核配对，报告决策覆盖率、一致率、相关类精确率/召回率、弃权数、混淆矩阵，以及按启发式语言和发布来源的切片。少于 50 条正负人工标签时固定为“样本不足”；达到样本量但未同时达到覆盖率、精确率、召回率和一致率门槛时固定为“仅影子运行”。
- P3 固定评测集第一增量已实现：可从当前专题已有人工正负标签中确定性抽样并创建不可修改的开发集或保留集，同一候选由数据库约束保证不能跨分区复用；冻结标题、短摘要、来源元数据、人工标签引用、输入哈希和内容哈希，不保存新闻正文。每次运行会选择评测集中最近已记录的 Tier 1 `evaluationKey` 并保存不可修改的评测快照；它只评估已落账结果，不会借评测接口绕过预算账本重新调用模型。
- P3 外部审计样本第一增量已实现：用户可导入 1—500 行 JSONL，把独立整理的候选标题、短摘要、来源元数据、人工正负金标、引用 URL 与溯源说明冻结为开发集或保留集；不保存新闻正文。同一语义样本以稳定哈希标识，数据库保证它不能跨开发集和保留集复用。导入后生成样本量、正负标签、已知语言数、来源数、最大单一来源占比和未知语言占比的结构覆盖报告。
- P3 外部样本离线预测第一增量已实现：外部开发集或保留集可运行当前确定性的 `tier0-prefilter-v1`，逐条预测、理由码、维度分数和输入哈希会不可修改地冻结，再生成与站内评测一致的精确率、召回率、覆盖率及语言/来源切片。该运行不联网、不调用模型、不产生供应商费用，重复运行同一版本幂等。
- 门禁即使通过也只返回“可申请受控试运行”，`automationAllowed` 永远为 `false`；它不会自动接纳事实、确认来源或打开 Tier 2。结构覆盖达标明确保持 `representative=false`，不证明抽样独立、总体代表性或事实真实性。外部样本的 Tier 1 模型专用预算账本与离线运行器、独立抽样审核、统计代表性验收和受控放量开关尚未实现，因此 P3 仍未完成。
- Tier 2 独立复评、语义事件关系判断和自动证据网关仍未启用，不得将当前增量描述为完整候选流水线。

## 1. 目的与结论

本方案把墨鱼变更雷达从“定时检查若干网址”继续升级为面向一个关注对象的长期新闻观察系统。升级重点不是制造另一个新闻门户，而是建立一条可持续运行的新闻情报流水线：自动发现候选报道、去重和筛选、识别同一现实事件、取得可验证证据，再交给现有 Researcher 形成事实、指标、主张、修订与长期比较。

本方案借鉴 [AIHOT](https://github.com/KKKKhazix/AIHOT) 在多来源采集、分层筛选、独立评分、语义归组、后台 Worker、成本控制和离线评测方面的工程思路，但不复制其“自动新闻编辑部/公开出版物”定位。雷达继续以用户专题、证据谱系和长期研究账本为中心。

核心决策：

1. 新闻文章是候选输入，不是事实；摘要、搜索片段和模型判断也不是证据。
2. 同一事件的报道数量不等于独立信源数量，更不等于事实可信度。
3. 自动化可以完成发现、排序和提出关系建议；事实接纳、来源独立性和结论修订必须保留可审计过程。
4. 全文仅在获取和解析所需的最短周期内受控保存；长期保存的是来源版本、必要引文、哈希、结构化事实和分析结论，而不是新闻全文仓库。
5. 第一阶段先打通 RSS、公开网页、JSON 列表和现有搜索能力，不把 X、微信公众号或付费内容作为首发依赖。

## 2. 与现有总设计的关系

本方案是《墨鱼变更雷达：自主长期研究系统设计》的配套实施设计，服从以下既有边界：

- 研究专题、不可变契约版本和研究运行仍是顶层对象；
- `source_discoveries`、`source_versions`、`evidence`、`events`、`facts`、`metrics`、`claims` 及其修订链仍是权威研究账本；
- 候选新闻流水线只负责把互联网信息转化为“可进入证据流程的候选”，不得直接写成已接纳事实；
- 现有账号隔离、租约恢复、配额、付费调用凭据、质量报告和人工复核机制继续复用；
- 新能力必须渐进启用、可回滚，并能在无模型或模型不可用时降级运行。

如本文与总设计在证据、权限、隐私、恢复或成本规则上冲突，以总设计为准。

## 3. 产品边界

### 3.1 要解决的问题

对每个长期研究专题，系统应持续回答：

- 最近出现了哪些真正相关的新报道？
- 多篇报道是在重复同一件事、跟进同一故事，还是提供不同背景？
- 哪些报道来自独立信源，哪些只是转载、聚合或引用同一原始消息？
- 哪些候选值得获取全文并转化为正式证据？
- 新证据改变了哪些既有事实、指标或结论？
- 与上周、上月、去年同期相比，发生频率、规模、方向和不确定性如何变化？

### 3.2 明确不做

- 不以生成公开首页、热点榜或自动出版日报为核心目标；
- 不把模型评分包装成事实置信度或来源真伪判断；
- 不因为“多家媒体都报道”就自动确认事实；
- 不默认长期保存受版权保护的新闻全文；
- 不在首期接入需要绕过登录、验证码、付费墙或访问控制的来源；
- 不让单一模型同时完成筛选、归组、事实裁决和结论写作而无独立校验。

## 5. 目标架构

```text
来源注册表 / 搜索计划
        │
        ▼
Collector 适配器 ──► 原始候选暂存（有 TTL、非证据）
        │
        ▼
确定性规范化与去重
        │
        ▼
分层预筛选与价值评估
        │
        ▼
相似事件召回 ──► 事件关系判定 ──► 临时事件簇
        │                              │
        └──────── 未归组候选 ◄────────┘
                                       │
                                       ▼
                              证据获取与资格门禁
                                       │
                                       ▼
                  现有来源版本 / 证据归档 / Researcher
                                       │
                                       ▼
                   候选事实 / 指标 / 主张 / 修订 / 人工确认
                                       │
                                       ▼
                        时间线 / 对比 / 统计 / Agent 查询
```

架构原则：页面只显示状态和发起明确操作，定时采集、模型调用、重试与恢复全部在后台 Worker 完成。页面关闭后专题继续运行。

## 6. 端到端状态机

候选新闻采用以下主状态，所有迁移写入追加式历史：

```text
discovered
  -> normalized
  -> duplicate | prefilter_rejected | prefilter_passed
  -> assessed
  -> grouped_provisional | ungrouped
  -> acquisition_queued
  -> acquired | acquisition_failed
  -> evidence_ready | evidence_rejected
  -> research_queued
  -> archived
```

约束：

- `duplicate` 必须记录指向的规范候选和判定依据；
- `prefilter_rejected` 可被规则版本升级或人工操作重新评估，但原判定不可覆盖；
- `grouped_provisional` 不表示同一事实，只表示当前最可能属于同一新闻事件；
- 只有 `evidence_ready` 才能进入 Researcher 的事实提取；
- 任何失败都必须区分可重试、永久拒绝、预算阻断和需要人工处理；
- 重试使用同一幂等键，不重复计费或生成重复账本记录。

## 7. 来源与采集适配器

### 7.1 统一契约

每个 `NewsSourceAdapter` 至少提供：

```ts
interface NewsSourceAdapter {
  kind: 'rss' | 'web_list' | 'json_api' | 'search' | 'external_push';
  preview(input: SourceDraft): Promise<SourcePreview>;
  collect(input: CollectRequest): Promise<CollectResult>;
  estimateCost(input: CollectRequest): Promise<CostEstimate>;
  validateCursor(cursor: unknown): CursorValidation;
}
```

`preview` 必须在启用前返回：可识别条目数、样例标题、最新时间、语言、分页/游标能力、robots/版权提示、预计频率与失败原因。预览不得创建正式监控任务。

`collect` 必须返回规范化候选以及新的不透明游标，不得直接写事实或事件。Adapter 不负责模型分析。

### 7.2 首期来源

| 优先级 | 类型 | 能力 | 首期限制 |
| --- | --- | --- | --- |
| P0 | RSS/Atom | 增量条目、发布日期、规范链接 | 处理失效 Feed 与时区异常 |
| P0 | 公开网页列表 | 列表页发现、详情页获取 | 仅显式允许域名与安全解析器 |
| P0 | JSON API | 游标/时间窗口采集 | 必须有稳定契约与速率限制 |
| P0 | 现有搜索适配器 | 补充未知来源与漏报检查 | 搜索结果只创建候选，不作证据 |
| P1 | 外部推送 | 接受受信系统提交的结构化候选 | 签名、幂等、账号归属必填 |
| 后续 | X、微信公众号、付费内容 | 仅通过合规提供商或官方能力 | 不作为核心链路依赖 |

### 7.3 来源健康

来源健康是运行状态，不等于来源权威度。系统记录：最近成功时间、连续失败数、候选产出、相关率、重复率、解析漂移、延迟和预计成本。自动降频只能影响采集计划，不能静默删除来源或改变历史权威度快照。

## 8. 候选新闻数据契约

建议新增 `research-news-candidate-v1`：

```json
{
  "candidateId": "uuid",
  "accountId": "uuid",
  "topicId": "uuid",
  "runId": "uuid",
  "sourceId": "uuid",
  "sourceDiscoveryId": "uuid",
  "canonicalUrl": "https://example.com/news/1",
  "publisher": "Example News",
  "title": "...",
  "publishedAt": "2026-10-22T02:00:00Z",
  "retrievedAt": "2026-10-22T03:00:00Z",
  "language": "zh-CN",
  "contentHash": "sha256:...",
  "excerpt": "受长度和版权策略限制的候选片段",
  "collectionMethod": "rss",
  "rights": { "retainFullText": false },
  "rawRef": "ephemeral://...",
  "expiresAt": "2026-10-29T03:00:00Z"
}
```

规则：

- `rawRef` 指向隔离、限时的原始获取结果，不对 Agent 暴露；
- `excerpt` 只用于筛选和定位，不能成为已接纳事实的唯一证据；
- `contentHash`、规范 URL 和来源版本用于幂等与追溯；
- 来源权威度必须保存运行时快照，后续评级变化不得改写历史；
- 所有候选查询强制包含 `accountId` 与 `topicId` 边界。

## 9. 去重、筛选与价值评估

### 9.1 确定性去重优先

按以下顺序执行，命中后停止昂贵步骤：

1. 规范 URL 与重定向终点；
2. 来源内稳定 ID；
3. 正文哈希或清洗正文哈希；
4. 标题、发布时间、发布者的严格指纹；
5. 近似重复仅进入语义关系判断，不直接删除。

### 9.2 分层评估

为避免给每条新闻做两次昂贵调用，采用三级策略：

- Tier 0：语言、时间范围、关键词/实体、域名、重复和最低内容质量规则；
- Tier 1：一次结构化模型判断，输出 `irrelevant | needs-review | relevant`、理由代码和维度评分；
- Tier 2：仅对高影响、边界分数、来源冲突或需自动进入证据流程的候选做第二次独立判断。

价值维度建议为：专题相关性、新颖性、潜在影响、可证据化程度、时间线价值。它们用于排序和预算分配，不代表真实性。

所有评估必须冻结并保存：规则版本、Prompt 版本、模型与提供商、输入哈希、结构化输出、调用凭据、成本、延迟和降级原因。

## 10. 语义事件归组

### 10.1 两阶段流程

1. 召回：在专题、实体和时间窗内，以标题/摘要向量或词元重合找出少量候选事件；
2. 判定：用规则或模型判断新报道与候选事件的关系。

建议关系类型：

| 关系 | 含义 | 是否自动合并 |
| --- | --- | --- |
| `SAME_OCCURRENCE` | 同一时间、地点和动作的同一发生 | 高阈值下可临时合并 |
| `SAME_STORY_UPDATE` | 同一持续故事的后续进展 | 进入同一故事线，但保留独立事件节点 |
| `RELATED_CONTEXT` | 背景、评论、历史或同类事件 | 不合并，只建关系边 |
| `ROUNDUP` | 汇总多件事情的综述 | 不作为单一事件来源 |
| `UNRELATED` | 无实质事件关系 | 不合并 |
| `INSUFFICIENT_EVIDENCE` | 当前信息不足 | 保持分离，等待更多证据 |

错误合并会污染后续趋势和事实，因此默认原则是“宁可漏合并，不可错合并”。自动归组只创建临时簇；一旦事实、指标或报告引用该簇，拆分/合并必须写修订记录而不是覆盖。

### 10.2 来源独立性与转载谱系

系统同时维护两个计数：报道数和独立来源数。独立性判断至少考虑：

- 明示引用或转载关系；
- 发布时间先后与正文高度重合；
- 相同通讯社/新闻稿/研究报告来源；
- 发布者所有权与内容分发关系；
- 无法确认时标为 `unknown`，不得默认独立。

“热度”只能描述传播与关注，不得进入事实可信度公式。可信度来自证据质量、来源独立性、原始材料和交叉验证。

## 11. 证据资格门禁

候选进入现有研究账本前必须通过：

1. 成功获取可引用的来源版本；
2. 记录获取时间、最终 URL、内容哈希和解析器版本；
3. 确认必要引文可定位到来源版本；
4. 标注原始报道、转载、评论、新闻稿或二手摘要类型；
5. 满足专题允许的来源和时效契约；
6. 不把搜索摘要、社交卡片或模型复述作为唯一证据；
7. 权限或版权不允许长期保存全文时，只保存必要引文、结构化摘要、定位信息和哈希。

通过门禁后，系统复用既有 `source_version -> evidence -> candidate fact/metric/claim` 流程。Researcher 的产物仍需满足结构 Schema、引用覆盖率和人工/规则接纳门槛。

## 12. 数据模型增量

避免复制既有权威表，建议只增加以下表：

| 表 | 类型 | 用途 |
| --- | --- | --- |
| `tool_research_candidate_assessments` | 追加式 | 记录候选每次规则/模型筛选与评分 |
| `tool_research_event_relation_decisions` | 追加式 | 记录两个候选/事件之间的关系判定 |
| `tool_research_event_cluster_revisions` | 追加式 | 记录临时簇合并、拆分和人工纠正 |
| `tool_research_source_collection_state` | 可变运行态 | 保存游标、下次采集时间、退避状态 |
| `tool_research_source_health_samples` | 追加式 | 保存来源健康时间序列 |
| `tool_research_candidate_retention` | 可变运行态 | 管理原始内容 TTL 和删除结果 |

候选主体优先扩展现有 `tool_research_source_discoveries`，只有在现有字段与状态约束无法兼容时才新增 `tool_research_news_candidates`。实施前必须先完成迁移兼容性 ADR，避免形成两套候选真相。

索引至少覆盖：

- `(account_id, topic_id, discovered_at desc)`；
- `(account_id, canonical_url_hash)`；
- `(topic_id, content_hash)`；
- `(topic_id, assessment_status, score desc)`；
- 关系对的规范顺序唯一键；
- Worker 领取所需的 `(status, available_at, lease_expires_at)`。

## 13. API 设计

沿用账号级 `/v1/me/research-topics/:topicId` 前缀：

| 方法与路径 | 用途 |
| --- | --- |
| `POST /sources/preview` | 预览来源，不创建任务 |
| `POST /sources` | 启用通过预览的来源 |
| `GET /sources/health` | 查看来源健康、退避和最近产出 |
| `GET /news-candidates` | 按状态、时间、来源、分数和事件筛选收件箱 |
| `POST /news-candidates/:id/review` | 接受、拒绝、重新评估或请求获取 |
| `GET /event-clusters` | 查询临时/确认事件簇和独立来源统计 |
| `POST /event-relations/:id/review` | 确认、纠正关系，必要时拆分/合并 |
| `POST /evaluation-runs` | 管理员运行离线评测集 |
| `GET /evaluation-runs/:id` | 返回指标、阈值、成本和错误样本 |

所有写接口要求幂等键；自动动作与人工动作使用同一审计格式，并明确 `actor_type`。

## 14. Worker 作业

| 作业类型 | 输入 | 输出 | 幂等键核心 |
| --- | --- | --- | --- |
| `research-source-collect-v1` | 来源契约、游标、窗口 | 来源发现项 | 来源版本 + 窗口 + 游标 |
| `research-candidate-prefilter-v1` | 候选、规则版本 | 预筛选判定 | 候选哈希 + 规则版本 |
| `research-candidate-assess-v1` | 候选、评分契约 | 结构化评分 | 输入哈希 + Prompt/模型版本 |
| `research-event-relate-v1` | 候选与事件候选集 | 关系判定 | 规范关系对 + 判定版本 |
| `research-evidence-acquire-v1` | 候选与获取策略 | 来源版本/拒绝原因 | URL + 来源版本策略 |
| `research-candidate-retention-v1` | 过期原始引用 | 删除证明 | 原始引用 + 到期策略版本 |

每个作业必须使用现有公平领取、租约续期、陈旧 Worker 恢复和账号容量门禁。模型/搜索付费结果先写凭据，再提交业务结果；重试优先复用同一凭据。

## 15. 成本与降级

### 15.1 预算顺序

1. 先做 URL、ID、哈希和时间窗去重；
2. 再做本地规则预筛选；
3. 对剩余候选做一次模型评估；
4. 仅对关键或边界样本做独立复评；
5. 只给最有价值的候选获取全文和做事件关系判断；
6. 最后才进入 Researcher 的事实/指标提取。

### 15.2 强制限额

每个专题契约必须声明：单次最大候选数、每小时搜索次数、全文获取数、模型调用数、关系比较数、费用上限和原始内容 TTL。达到上限时暂停低优先级步骤并生成可见的 `budget_blocked` 状态，不静默丢弃。

### 15.3 降级路径

- 模型不可用：保留规则筛选和确定性去重，候选进入人工收件箱；
- 向量服务不可用：使用词元重合召回，禁止低置信自动合并；
- 搜索服务不可用：继续 RSS/已知来源采集并标记覆盖缺口；
- 全文获取失败：保留发现记录，不生成正式证据；
- 预算耗尽：保存已付费结果和游标，下周期从安全点继续。

## 16. 质量评测体系

### 16.1 离线金标集

维护三个版本化数据集：

- `candidate-relevance.jsonl`：相关、边界、不相关；
- `event-relations.jsonl`：上述六类关系；
- `evidence-eligibility.jsonl`：可作为证据、仅作线索、必须拒绝。

每个数据集分开发集与保留集。阈值调整只能看开发集；阶段发布必须在未参与调参的保留集上通过。样本要覆盖中英文、多地区、转载、更新稿、综述、标题党和时间相近但无关事件。

### 16.2 发布门槛

首期门槛：

- 确定性重复检测在金标集上不得产生已知误删；
- 自动事件合并的精确率优先，保留集目标不低于 0.97；未达标则只给建议、不自动合并；
- 候选预筛选需报告精确率、召回率和按来源/语言切片结果，不允许只报平均分；
- 证据门禁不得把搜索摘要或无定位模型文本判为正式证据；
- 每个线上模型判断可追溯到输入哈希、模型、Prompt 和调用凭据。

### 16.3 线上指标

- 候选产出率、相关候选率、证据接纳率；
- 每个已接纳事件/事实的搜索、抓取、模型成本；
- 来源新鲜度、连续失败、解析漂移；
- 临时簇被人工拆分/合并的比例；
- 转载被误判为独立来源的纠正率；
- 从首次发现到证据就绪、事实接纳的延迟；
- 外部对照集漏报率。

## 17. 页面与用户流程

### 17.1 四个工作区

1. **来源**：来源包、搜索计划、预览、健康和频率；
2. **候选收件箱**：筛选结果、评分解释、重复关系和获取状态；
3. **事件**：临时簇、故事线、独立来源、拆分/合并和时间线；
4. **研究账本**：证据、事实、指标、主张、修订、比较和 Agent 输出。

默认界面只展示“创建专题—选择来源—开始首次观察—查看事件”主路径；评分阈值、Prompt 版本和关系判定细节放在高级设置与审计抽屉中。

### 17.2 新账号首次使用

```text
打开长期新闻观察
  -> 显示产品说明和“新建专题”，不得出现黑屏或要求先填网址
  -> 输入关注对象、长期问题、地区/语言、观察频率
  -> 选择预置来源包或搜索发现
  -> 预览来源和预计成本
  -> 启用并运行一次 dry-run
  -> 查看候选收件箱和预计事件归组
  -> 用户确认后开启长期计划
```

空状态必须是合法产品状态。React 渲染期间不得假设存在选中专题、来源或事件；任何 `selected*.id` 访问前必须有显式空值分支。当前已出现的空账号页面异常应作为 P0 阻断项处理。

## 18. 分阶段实施路线

### P0：入口稳定与验收基线

范围：

- 修复新账号/无专题时的页面异常和黑屏；
- 建立浏览器错误捕获、空状态 E2E 和生产静态资源校验；
- 固定现有数据库、队列、恢复和成本基线；
- 建立三类离线评测集的格式与最小样本。

完成定义：

- 新账号直接打开独立控制台 `/apps/change-radar` 无控制台异常；旧地址 `/tools/change-radar` 仅负责兼容跳转；
- 不输入网址也能创建新闻观察专题；
- 本地、测试和生产构建均通过同一冒烟流程；
- 评测脚本可在零外部提供商下复现固定结果。

### P1：统一候选流水线

范围：候选契约、状态历史、确定性去重、TTL、列表 API 和候选收件箱。

完成定义：同一批输入重复执行不产生重复候选；跨账号查询不可见；过期原始内容可删除且保留删除证明。

### P2：来源适配器与健康

范围：RSS/Atom、公开网页列表、JSON API、现有搜索、来源预览、游标和健康采样。

完成定义：每类来源都有契约测试；解析漂移会告警并停止错误写入；搜索结果不会直接成为证据。

### P3：分层筛选与价值评估

范围：Tier 0/1/2、结构化理由、缓存、预算、调用凭据和候选排序。

完成定义：离线相关性评测按来源和语言报告；重试不重复付费；无模型时仍可进入人工收件箱。

当前状态：Tier 0、默认关闭的 Tier 1、人工复核对照、只读影子门禁、从已有人工标签确定性冻结开发集/保留集、外部 JSONL 审计样本导入、结构覆盖报告，以及外部样本的零费用 Tier 0 离线评测已经实现；Tier 2、外部样本的 Tier 1 模型专用预算账本与运行器、独立抽样与统计代表性审核、受控放量开关尚未实现，所以本阶段保持进行中。

### P4：语义事件关系与临时簇

范围：候选召回、六类关系、来源谱系、临时簇、拆分/合并修订和评测工具。

完成定义：保留集达到自动合并门槛；未达门槛时系统自动降级为建议模式；每次簇变更可回放。

### P5：证据网关与 Researcher 接入

范围：全文获取、来源版本、必要引文、证据资格、事实/指标/主张候选和人工接纳。

完成定义：任何已接纳事实都能反查来源版本和定位引文；候选片段不能绕过门禁；失败恢复不产生重复事实。

### P6：长期分析与 Agent 产品化

范围：事件/故事线时间轴、周期比较、来源与地区切片、趋势指标、Agent 查询和订阅摘要。

完成定义：统计基于已定义分母和时间归属；报告能区分报道热度、独立来源数和事实可信度；Agent 返回查询条件与证据引用。

## 19. 第一实施切片

在继续扩大来源前，建议立即实施以下闭环：

1. 完成 P0，确保空账号、新专题和生产构建稳定；
2. 复用现有 `source_discoveries`，增加追加式评估与关系判定，不新建第二套事件/事实表；
3. 只接 RSS、HTTP 公开页面和现有搜索适配器；
4. 实现确定性去重、Tier 0 规则筛选和候选收件箱；
5. 用词元重合做关系召回，模型只在可配置的影子模式输出六类关系；
6. 建立关系金标集，在达到门槛前不自动合并；
7. 将用户确认的候选送入现有证据获取和 Researcher 链路；
8. 先以默认关闭的 Tier 1 建立影子评估与成本基线，验证成功后再逐步放量；Tier 2 与高置信临时归组仍需单独门禁。

本切片不包含：X/微信采集、公开新闻门户、自动发稿、全自动事实接纳、跨专题全局事件图谱。

## 20. 功能开关与上线策略

已实现与建议增加的开关：

- `RESEARCH_NEWS_PIPELINE_ENABLED`：启用统一候选流水线；
- `RESEARCH_CANDIDATE_ASSESSMENT_ENABLED`：已实现；启用一次 Tier 1 模型价值评估，默认 `false`；
- `RESEARCH_CANDIDATE_ASSESSMENT_MODEL`：已实现；默认 `deepseek-chat`，模型标识会进入不可变评估键；
- `RESEARCH_CANDIDATE_ASSESSMENT_TIMEOUT_MS`：已实现；单次调用超时，默认 45 秒；
- `RESEARCH_CANDIDATE_ASSESSMENT_MAX_PER_RUN`：已实现；每轮 1—10 条，默认 6 条；
- `RESEARCH_CANDIDATE_ASSESSMENT_PRICE_USD_MICROS_PER_REQUEST`：已实现；部署方维护的每请求美元微单位价格快照；
- `RESEARCH_NEWS_DUAL_ASSESSMENT_ENABLED`：启用关键候选独立复评；
- `RESEARCH_SEMANTIC_GROUPING_ENABLED`：允许语义关系判断；
- `RESEARCH_SEMANTIC_AUTO_MERGE_ENABLED`：允许达到门槛的临时自动合并；
- `RESEARCH_NEWS_EVIDENCE_GATEWAY_ENABLED`：允许候选进入正式证据流程。

上线顺序为：离线回放 → 影子运行 → 内部专题建议模式 → 小流量自动化 → 默认开启。每一步都保留旧 URL 监控路径和回滚开关，不回写或重算既有事实账本。

当前 Tier 1 的启用条件是同时设置 `RESEARCH_CANDIDATE_ASSESSMENT_ENABLED=true` 和服务端 `DEEPSEEK_API_KEY`。密钥不得进入浏览器、候选记录、行动回执或模型输出；首次上线应保留默认每轮 6 条上限，并先核对部署方价格快照和账号/全局月度预算。关闭该开关不会影响 Tier 0、候选列表或人工复核。

## 21. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 错误合并污染趋势 | 高精确率门槛、临时簇、追加式修订、人工拆分 |
| 来源偏差导致结论偏差 | 地区/语言/所有权切片、覆盖缺口和外部对照集 |
| 模型漂移 | 冻结版本、影子评测、保留集、逐步放量 |
| 转载被当成独立证实 | 来源谱系、独立来源计数、未知状态 |
| 成本失控 | 规则先行、分层调用、缓存、凭据、专题预算 |
| 版权与隐私 | 原始内容 TTL、必要引文、权限标记、删除证明 |
| 页面功能多而难用 | 默认主路径、高级设置折叠、可解释空状态 |
| Worker 重复执行 | 幂等键、租约、付费结果复用、追加式账本 |

## 22. 阶段验收总门禁

任何阶段不得仅以“页面出现功能”或“某次手工演示成功”宣布完成。至少验证：

- 新账号、空数据、无网址输入和刷新直达均可用；
- 账号/专题隔离和权限测试通过；
- 数据库迁移可在真实旧快照上执行，已应用迁移不得改写；
- 重复运行、超时重试、陈旧租约与 Worker 重启保持幂等；
- 付费调用均有可复用凭据和预算阻断；
- 原始内容 TTL、删除和恢复演练通过；
- 离线保留集达到当前自动化级别要求；
- 线上指标能区分候选、事件、独立来源、证据和事实；
- 生产静态资源与 API 版本匹配，浏览器无启动期异常；
- 所有“自动”描述都注明边界、降级方式和是否需要人工确认。

## 23. 决策记录

1. 采用“新闻发现层 + 雷达研究账本”组合，不把雷达改造成 AIHOT 克隆。
2. 延续现有权威数据模型，新增表优先保存评估、关系和运行状态。
3. 引入六类事件关系，取代仅按标题和日期精确指纹归组的最终形态。
4. 双重评估只用于高价值/边界候选，避免成本随候选总量线性翻倍。
5. 自动合并以高精确率为门槛，未达标时只给建议。
6. 搜索和聚合内容是发现线索，不是正式证据。
7. 第一实施目标是可验证的闭环，不是一次性覆盖所有新闻平台。
