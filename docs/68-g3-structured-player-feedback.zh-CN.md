# G3.2 结构化玩家反馈与作者 Issue 草稿

状态：代码完成，待生产部署验收
更新日期：2026-10-02

## 1. 本阶段交付

G3.2 为公开社区作品增加一条明确区分于“内容举报”的产品反馈链路：

1. 已登录玩家可在作品详情页提交问题、玩法建议、兼容性或其他反馈。
2. 作者可在创作中心的“玩家反馈”收件箱查看、标记、归档和重新打开反馈。
3. 作者可显式生成 GitHub Issue 预填页，检查后再在 GitHub 手动提交。
4. 已提交 Issue 可由作者粘贴地址关联回反馈记录。

GitHub App 继续保持只读仓库权限。GameHub 不调用 GitHub 写接口，不自动创建 Issue，也不替作者公开玩家填写的内容。

## 2. 数据与权限边界

迁移 `0043_creator_feedback.sql` 增加：

- `creator_feedback`：反馈正文、作品、状态和可选 Issue 地址；
- `creator_feedback_events`：提交、查看、归档、重新打开、生成草稿和关联 Issue 的仅追加事件；
- 玩家与作品的 24 小时速率索引，以及作者队列索引；
- 事件表更新和删除阻断触发器。

服务端约束：

- 只接受仍公开发布的 UUID 作品，不接受官方内置作品；
- 玩家不能给自己的作品提交反馈；
- 同一账号对同一作品最多每 24 小时提交 5 条；
- 作者只能读取和更新自己名下作品的反馈；
- 返回作者收件箱的数据不包含反馈者账号 ID；
- Issue 地址必须精确属于作品关联的 GitHub 仓库。

玩家填写的“运行环境”只是普通文本。平台不会自动采集本地路径、令牌、项目内容或浏览器指纹。

## 3. API

```text
POST  /v1/works/{workId}/feedback
GET   /v1/creator/feedback?status=all|new|reviewed|archived|issue_drafted|issue_linked
POST  /v1/creator/feedback/{feedbackId}/issue-draft
PATCH /v1/creator/feedback/{feedbackId}
```

`issue-draft` 返回标题、正文、可复制 Markdown，以及在已关联 GitHub 仓库时的 `issues/new` 预填地址。该请求只记录“作者生成过草稿”，不会向 GitHub 发送写请求。

状态操作包括：

- `review`：标记已查看；
- `archive`：归档；
- `reopen`：重新打开；
- `link_issue`：保存作者已经手动提交的同仓库 Issue 地址。

## 4. 界面行为

作品详情页同时保留两个不同入口：

- “反馈给作者”：产品问题与建议，进入作者私人收件箱；
- “举报这个作品”：安全、违法、骚扰、恶意代码或版权问题，进入管理员审核队列。

作者生成 Issue 草稿时，客户端先请求平台生成受控文本，再打开 GitHub 预填页。没有关联 GitHub 仓库时复制 Markdown。界面会明确提示作者必须检查并手动提交。

## 5. 部署与验收

生产更新必须先运行数据库迁移，再重建 API 与 Web。验收至少覆盖：

- 普通玩家可以提交结构化反馈，未登录用户被要求登录；
- 玩家不能给自己作品反馈，非公开作品拒绝接收；
- 作者只能看到自己作品的反馈，且看不到反馈者账号身份；
- 反馈状态转换和仅追加事件约束有效；
- GitHub 预填页指向正确仓库，跨仓库 Issue 地址被拒绝；
- GitHub App 权限没有增加，仓库没有被自动写入；
- 移动端反馈表单和作者收件箱可用；
- 合约生成、API/客户端测试、数据库集成测试和 Web 构建通过。

## 6. 后续路线

下一步建议进入 G3.3：作者把已确认反馈整理为公开的新手贡献任务，映射 `good first issue`，并与贡献者公开资料连接。该阶段仍应保持“作者明确确认后公开”的边界。
